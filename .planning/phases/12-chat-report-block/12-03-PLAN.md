<objective>
Build the chat navigation skeleton end to end: the thread and Report & Block keys, the app-scoped hand-off slot that every Message entry point and the in-call control will post to, `Navigator.openChatThread`, the shells consuming the slot, the Chats tab root slot, route registration from the chat package, Chats origins on the keys a thread can push, and the thread navigation helpers.

Purpose: CHAT-05 / D-13 ("every Message tap switches to the Chats tab and pushes the thread"). The in-call Chat control lives in `CallOverlayHost` above both shells and the shells are Hilt-free, so a one-shot slot consumed by the Hilt-aware `HomeClientScreen` / `HomeExpertScreen` is the hand-off (RESEARCH Pattern 3; precedent `BookingsLaunchRequest`, `ExpertLaunchRequest`). Like 11-02, this plan is the only Phase 12 plan that edits the shells: later plans fill `ConversationsRoute`, `ChatThreadRoute` and `ReportAndBlockRoute`.
Output: keys, slot, launch ViewModel, routes with placeholder bodies, Navigator method, origins, shell wiring, two strings files, four test classes.
</objective>

<assumption_delta_decision>
Detector signal (pluralization, "report another user" in the ROADMAP criteria): no-change. The peer is identified by the backend user id everywhere (initiate `peer_id`, report `users/{id}`, thread `partner.id`); no second identity model is introduced.
Real pluralization found while planning: a route key that used to live on one tab stack can now also be pushed on a second stack (the Chats stack, from a thread). Primary noun: "route key plus owning stack". Decision: add-alongside (a defaulted `origin` on the affected keys, as `AvailabilityOrigin` / `ExpertBookingOrigin` already do). Accepted debt: keys pushed further down a Chats-origin flow (`BookingKey`, `CancelBookingKey`) carry no origin; a promote (stack-scoped content keys in `NavigationState.toDecoratedEntries`) would be forced if a third stack starts sharing routes or testers hit a duplicate-key crash. Suggested invariant test (included in Task 3): a Chats-origin key never equals the same key with the default origin.
</assumption_delta_decision>
