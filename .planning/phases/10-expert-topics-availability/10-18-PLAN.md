<objective>
Close two Topic Editor warnings from 10-REVIEW.md.

- **WR-02:** `TopicEditorRules.seedDuration` rounds stored durations to the 30-minute grid and clamps them to 30..480. The Android PATCH is a full body, so any unrelated edit silently rewrites a legacy or out-of-cap session length.
- **WR-05:** when the profile tags fail to load, `TopicTagPicker` shows only the error row. The topic's selected tags are hidden, but Save still sends them.

**WR-02 design (Claude's discretion; backend contract checked).** The backend `patchTopicSchema` has `duration_mins: durationMinsSchema.optional()` with int, `>= 30`, `<= 1440` and `% 30 === 0`. `expertTopics.controller.js` writes it only when present (`if (body.duration_mins !== undefined)`). Sending a stored off-grid value back (for example a legacy 45) would therefore fail with a 422, and clamping it rewrites it. The safe rule is to show the stored value unchanged and leave `duration_mins` out of the PATCH unless the user changed it. A changed value always comes from the +/- buttons, which now snap onto the 30-minute grid inside 30..480, so the server always accepts it. The 480 cap stays for the buttons (iOS parity, CONTEXT "duration from 30 to 480 minutes in 30-minute steps"). Stored values are never altered.

**WR-05 design.** In the failed state, still render the selected tags as removable chips above the Retry row. Disabling Save would block unrelated edits (a title typo) whenever `GET /expert/profile` fails. Showing the chips lets the expert see and remove what will be sent. The server's profile-subset check (`422 VALIDATION_ERROR`) stays authoritative.

Purpose: an edit can no longer change what clients book (EXP-01), and the price/tag form never sends data the expert cannot see (EXP-01, EXP-02 editor integrity).
Output: a nullable PATCH duration, the adapter change, the seed and step rules, failed-state chips, and regression tests.

Out of scope (deferred, recorded in 10-20): WR-03 and IN-01..IN-07. IN-02 (locale-default `lowercase()` in `TopicTagPicker`) is not fixed here, but new code in that file uses `Locale.ROOT`. Plans 10-01..10-16 are not modified.
</objective>
