Build the pure, Android-free decision units for the booking lists and status display, plus the one-shot cross-stack launch holder used after a cancel.

Purpose: RESEARCH Pattern 1: keep decisions out of composables and `viewModelScope` so JVM tests cover them. Output: three main files, three JVM test files.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend -> app | Raw status strings decide which tab a booking shows in and whether Cancel is offered |
| Cancel screen -> My Bookings | A process-wide holder carries a one-shot launch between ViewModels |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-06 | Tampering | Unknown or new server statuses | mitigate | Past drops unknown statuses; the details pill shows a neutral humanized raw label; Cancel is gated on an explicit allow-list, and the server re-checks (409) |
| T-08-07 | Denial of service | Duplicate booking ids crashing LazyColumn keys | mitigate | `distinctBy { bookingId }` on both lists (tested) |
| T-08-08 | Information disclosure | Launch holder outliving a logout | accept | It holds only a tab and a formatted amount, no ids or names; it is consumed by the next My Bookings open |
| T-08-09 | Elevation of privilege | Client-side Cancel gate | accept | The UI gate is convenience only; the server enforces allowed statuses and ownership (RESEARCH Security V4) |
</threat_model>
