# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope.** Requirements POL-01..POL-04 (CONTEXT D-01..D-17). This is a hardening pass, not a feature phase: it adds **no new screens and no new tokens**. It defines the one shared standard that every existing screen and data-loading sheet must meet, so the planner can audit and fill gaps against a single bar:
> 1. **State standard (POL-01).** Loading, empty, first-load error with Retry, and failed-refresh snackbar, per screen archetype.
> 2. **Orientation and large-screen policy (D-01..D-03).** Portrait lock, and "usable, not optimized" at sw600dp+ (a 600 dp max content width, never clipped, input kept).
> 3. **Insets standard (POL-03, D-17).** Edge-to-edge, system bars, display cutouts and the IME, with the rules the `check-design-rules.sh` guard enforces.
> 4. **Restoration standard (POL-02, D-09..D-13).** What the user sees after Activity recreation or process death.
> 5. **TalkBack standard (POL-04).** Reading order, names, roles, states and announcements for the four SC-4 flows (log in, book a session, join a call, send a chat message), plus the global rules every other screen follows.
> 6. **Device checklist shape (D-14, D-15).** The layout of the one consolidated, non-blocking human checklist.
>
> Out of scope and must not appear in the UI (CONTEXT Deferred and D-06): an offline banner or any `ConnectivityManager` / `NetworkCallback` UI, tablet or list-detail layouts, a navigation rail, a draft-persistence indicator, per-screen orientation exceptions, debug-only rotation, a new loading idiom (spinners replacing skeletons, shimmer libraries), new theme tokens, and any new feature copy.
>
> **Baseline.** `01-UI-SPEC.md` (tokens, shapes, motion, shell), `08-UI-SPEC.md` (quiet-reload snackbar, destructive rule A5, `AuthErrorDialog`), `12-UI-SPEC.md` (empty/error pattern, footer bar, thread semantics), `13-UI-SPEC.md` (`EmptyState` use, `NotificationRow`), `14-UI-SPEC.md` (named error headings, "Retry" exception E1, accessibility contract, UI Considerations format) are locked and not restated. Dark only, Material 3, Nunito 400 / 600, exactly four text sizes (12 / 16 / 20 / 28 sp), `Spacing` xs..xxxl, `ClickMeShapes`, `MaterialTheme.extras`, Outlined icons, `AutoMirrored` Outlined back arrows. **Every value below is an existing token unless marked "(new)".**
>
> **Design source.** Google Stitch is not accessible. The stand-in is `ios-reference/ClickMe2026/Views/Screens/` for per-screen empty/error behavior and copy where it exists, and `ios-reference/ClickMe.xcodeproj/project.pbxproj` (`UISupportedInterfaceOrientations = Portrait`) for D-01. Layout is adapted to Material 3, not pixel-matched.
>
> **Source of decisions.** CONTEXT D-01..D-17 are locked and not re-asked. This spec fills "Claude's Discretion": the orientation mechanism, the snackbar and ErrorState copy, the `ErrorState` extension, the large-screen width rule, the TalkBack semantics for the four flows, and the checklist structure. The run was non-interactive; every assumption is recorded under "Assumptions and Open Items".

## Spacing Scale

Phase 1 tokens, all multiples of 4: xs 4, sm 8, md 16, lg 24, xl 32, xxl 48, xxxl 64. Nothing is added.

| Token | Value | Used for in this phase |
|-------|-------|------------------------|
| xs | 4px | Gap between a state heading and a one-line sublabel inside compact section errors |
| sm | 8px | `EmptyState` heading-to-body gap (inherited); `SectionError` icon-to-message gap (inherited); gap between skeleton rows' inner blocks |
| md | 16px | Horizontal screen padding for every state block (inherited); gap between skeleton rows; `SectionError` message-to-Retry gap |
| lg | 24px | `EmptyState` body-to-action gap (inherited); top padding of a first-load `ErrorState` under the app bar on detail screens (matches ExpertProfile); skeleton-to-first-section gap |
| xl | 32px | `EmptyState` icon-to-heading gap (inherited); bottom scroll padding added to the navigation-bar inset (see Insets) |
| xxl | 48px | Minimum touch target for every interactive control, including Retry, snackbar action and the composer Send button |
| xxxl | 64px | Not used |

Exceptions (component dimensions and platform minimums, not layout spacing):
- `ContentMaxWidth` = **600dp** (new constant, a multiple of 4): the maximum width of a single-column content block on windows wider than 600 dp. Not a spacing token.
- `EmptyState` body max width 320 dp and icon size 48 dp (inherited). `SectionError` icon 24 dp (inherited).
- Sheet loading placeholder: `heightIn(min = 240.dp)` so a data-loading sheet does not collapse and jump when its rows arrive.
- Snackbar: M3 default (48 dp action target, 16 dp edge margin from the host); not customized.
- Skeletons copy the real row dimensions of the screen they stand in for.

## Color

Inherited from `ClickMePalette`, unchanged. This phase adds no color and no literal.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `surface` `#131313` | Screen background behind every state block |
| Secondary (30%) | `surfaceContainer` `#201F1F` (also `surfaceContainerLow` `#1C1B1B`, `surfaceContainerHigh` `#2A2A2A`) | Cards, sheet bodies, skeleton block fill (`surfaceContainerHigh`) |
| Accent (10%) | `primary` `#44F697` | See reserved list |
| Destructive | `destructive` `#FF4D4D` | Not used by any state in this phase. Existing inline field errors keep it |

Accent reserved for (this phase): the filled Retry button inside `EmptyState` / `ErrorState`; the tonal Retry in `SectionError` (container `secondaryContainer`, label `primary`); the pull-to-refresh indicator and the 4 dp `LinearProgressIndicator` of a Loud refresh; the focused-field border (inherited). **Not** accent: skeleton blocks, state icons (muted), snackbar background (`inverseSurface`), snackbar action (M3 default `inversePrimary`).

Contrast rules (computed against the tokens, WCAG relative luminance; these are binding for the accessibility tests):
- `onSurfaceMuted` `#999999` reads 6.5:1 on `surface`, 5.8:1 on `surfaceContainer`, 5.0:1 on `surfaceContainerHigh`: allowed for body text on those three.
- `onSurfaceMuted` reads **4.3:1 on `surfaceContainerHighest`** and **4.0:1 on `surfaceBright`**: it must not be used for informative text on those two surfaces. Use `onSurface` there.
- `onSurfaceFaint` `#6E6E6E` reads 3.7:1 on `surface`: decorative or disabled content only, never an informative label, hint, timestamp or error.
- `destructive` reads 5.7:1 on `surface` and 5.0:1 on `surfaceContainer`: allowed for inline errors.
- Color is never the only signal: an error or disabled state also changes text, an icon or `stateDescription`.

## State Standard (POL-01, D-04..D-08)

### Screen archetypes

Every `*Screen.kt` destination and every data-loading sheet maps to exactly one archetype. The planner assigns archetypes during the audit; the contract per archetype is fixed here.

| Archetype | Screens (non-exhaustive) | Loading (first load) | Empty | First-load error (nothing to show) | Failed refresh (content showing) |
|-----------|--------------------------|----------------------|-------|-------------------------------------|----------------------------------|
| **A. List** | Conversations, My Bookings (Upcoming, Past), Expert Bookings, Incoming Requests, Topics, Notifications, Activity, Payment Methods, Help categories | `SkeletonGroup` of row-shaped skeletons that copy the real row height; fill the viewport (5 rows at 100% scale; the same row count at larger scales) | `EmptyState` (icon, heading, body, action only if a one-tap next step exists on the same tab) | `ErrorState` filling the content area, vertically centered | Keep rows; snackbar (below) |
| **B. Detail** | Expert Profile, Upcoming Booking, client and expert Booking Summary, Request Decision, Write Review, Request Sent, Booking Confirmed, Cancel step screens | `SkeletonGroup` mirroring the real layout (hero block, card blocks, button pills) | None. A missing record is "unavailable" (below), not "empty" | `ErrorState` top-aligned with `Spacing.lg` top padding under the app bar | Keep content; snackbar |
| **C. Composite** | Explore, Expert Dashboard, Signup Overview hub | One skeleton per section; sections appear independently with `SectionAppear` | Per-section `EmptyState`/inline empty copy as shipped | Per-section `SectionError` + Retry. A section that loaded is never replaced by an error | Keep every loaded section; snackbar |
| **D. Form / wizard step** | Signup steps, Make a Booking, Topic Editor, Availability, Cancel reason steps, Profile Settings, Expert Settings, Account Security, Delete Account, Tax & Payout Info, Login, Forgot, Set New Password | Skeleton fields only if the form prefetches (Settings, Tax, Topic Editor edit mode, Availability). A blank form has no loading state | None. A blank field is valid | Prefill failure: `ErrorState` replaces the form body, app bar stays | Not applicable (a form has no refresh). A re-prefill failure keeps the user's edits and shows the snackbar |
| **E. Data-loading sheet** | `PickerSheet` (topic picker, country, language), All Categories sheet, Expertise editor tags, Make a Booking time slots card | Skeleton rows inside the sheet, `heightIn(min = 240.dp)` | `EmptyState` inside the sheet (no action) | `ErrorState` **inside the sheet**; the sheet stays open and any typed search text is kept | Keep rows; inline `SectionError` is not used here, use the snackbar on the host screen |
| **F. Live / transient** | Meeting Call layer and pill, Splash, Onboarding, Mode Switch, Password Changed, Farewell | Call: existing joining states. Others: none | Not applicable | Call: existing `AuthErrorDialog` "Couldn't join session" with "Got it". Others: not applicable | Not applicable |

Rules that apply to every archetype:
1. **One loading idiom.** First load shows skeletons; a quiet or loud reload never swaps content back to skeletons (inherited from Phases 5 to 14).
2. **Skeleton shape equals content shape.** Same paddings, row heights and shapes as the loaded layout, so nothing shifts on arrival. Skeletons are decorative; the screen exposes one "Loading" node via `SkeletonGroup`.
3. **Retry never discards.** Retry re-runs the same load; it does not clear typed input, a selected tab, a search query or a scroll position.
4. **Compliance bar (D-08).** A screen is compliant if it already shows, for each applicable cell above, the described structure with a retry control and a heading that names the object. Do not rewrite compliant screens just to call `ErrorState`. Screens that currently show ad-hoc text or an `AlertDialog` for a failed first load are converted.
5. **Unavailable is not an error.** When the server says the record cannot be shown (404, suspended or deleted expert, removed booking), render `EmptyState` with the "unavailable" copy and **no Retry**. The back arrow is the exit. This keeps Retry from looping on a permanent condition.

### ErrorState extension

```
ErrorState(
    onRetry: () -> Unit,
    modifier: Modifier = Modifier,
    heading: String = stringResource(R.string.error_state_heading),     // "Something went wrong"
    body: String = stringResource(R.string.error_state_body),           // "Check your connection and try again."
    retryLabel: String = stringResource(R.string.error_state_retry),    // "Retry connection"
)
```

- Existing callers keep their text (their tests assert "Something went wrong" and "Retry connection").
- Every screen converted or added in this phase passes `heading` that **names the object** ("Couldn't load bookings") and `retryLabel = stringResource(R.string.section_retry)` ("Retry"), the project-wide retry label under Phase 14 exception E1. The generic default is for screens where no object name is sensible.
- Layout is `EmptyState` unchanged: `CloudOff` 48 dp muted, `Spacing.xl`, heading, `Spacing.sm`, body (max 320 dp), `Spacing.lg`, one filled `PressScaleButton`. No second button, no "Contact support".
- Body rule (D-06, adopted): server message from the error envelope if there is one, shown as plain text; else, for a connectivity failure (`IOException`), "Check your connection and try again."; else, for any other failure with no message, "Something went wrong on our end. Try again in a moment." Reuse the existing `ApiException.toSectionMessage()` mapping; do not add a second classifier.

### Failed refresh with content showing (D-05)

- Content stays exactly as it was. No full-screen error, no state reset, no scroll jump.
- Show one snackbar through the screen's existing `SnackbarHost`: message "Couldn't refresh. Check your connection and try again.", action **"Retry"**, `SnackbarDuration.Long` (10 s; M3 extends it automatically when TalkBack or another accessibility service is on). `withDismissAction = false`.
- Action `Retry` runs the same Loud refresh as pull-to-refresh. Dismissed or timed out: nothing happens.
- At most one refresh-failed snackbar at a time. Before showing, dismiss the current one with `snackbarHostState.currentSnackbarData?.dismiss()`; do not queue duplicates. A realtime-triggered refetch that fails while a refresh-failed snackbar is already visible is silent.
- **Quiet tab-return reloads fail silently**, with no snackbar and no change to the screen.
- Progress feedback for Retry: screens with `PullToRefreshBox` show its indicator. Screens that have a Loud refresh path but no pull-to-refresh show a 4 dp indeterminate `LinearProgressIndicator` (`primary` on `surfaceContainerHigh`) directly under the app bar while the refresh runs, and nothing when idle. Do not add a refresh path to a screen that has none.
- The snackbar sits in the Scaffold `snackbarHost` slot so it clears the navigation inset, the tab bar and any pinned footer. It must stay visible above the IME.

### Submit errors and in-flight (forms and dialogs, D-07)

- In flight: the submit button shows the `AsyncSaveButton` spinner with no layout shift; repeat taps are ignored (one in-flight flag per action); controls that would change the payload are disabled; system Back is ignored where an in-flight request cannot be cancelled (existing behavior from Phases 6 and 8).
- Field-specific server error (validation, wrong password, price below minimum): inline under the field via `ValidatedField.error`, and focus moves to the first failing field.
- Anything else (network, 5xx, rate limit, conflict): `AuthErrorDialog` with a title that names the failed action ("Couldn't update password") and the body rule above; one button "Got it". The form and every typed value stay intact.
- Static form with no prefetch has no loading and no empty state; only in-flight and submit-error are audited (D-07).

## Orientation and Large Screens (D-01..D-03)

**Orientation.** Lock phones to portrait with `android:screenOrientation="portrait"` on `MainActivity` only. One policy for the single Activity, including the call layer (it is an overlay in the same Activity). Rejected: a runtime `requestedOrientation` setter (it flickers on cold start and can race the splash). `ConnectReturnActivity` is a translucent no-UI activity and **must not** receive an orientation attribute (Android throws for translucent activities that request one). Do not declare `android:configChanges`: the Activity must stay recreatable because restoration and the SC-2 reading depend on it. Lint may flag the lock (`LockedOrientationActivity`); suppress at the manifest line with the reason "iOS parity, CONTEXT D-01".

**What D-03 means for the UI.** At targetSdk 37 the system ignores the lock on windows of sw600dp and up, so on tablets, foldables and resizable windows the Activity rotates and resizes. "Rotation" in SC-2 is therefore tested as any recreation: dark or font-scale change, window resize, "Don't keep activities", and process death.

**Large screens: usable, not optimized.**
- Single column at every width. No navigation rail, no list-detail, no two-pane (Deferred).
- `Modifier.contentMaxWidth()` (600 dp, centered horizontally, content aligned top) wraps the content column of: every Form / wizard screen, every Detail screen, the Settings and hub screens, Login and Signup screens, and the inner content of pinned footers (the footer *background* stays full width). Lists (archetype A) apply it to the list container so rows do not stretch across the window; the list's scroll area and pull-to-refresh stay full width.
- Full-bleed decoration (glow backgrounds, call background, hero imagery) is drawn full width behind the constrained content.
- App bars and the bottom tab bar stay full width. Bottom sheets keep the M3 default maximum width (640 dp), centered.
- Chat: the message list and the composer are both constrained to 600 dp; bubbles keep their own maximum.
- Call layer: the existing hero width cap stays. In a window shorter than 480 dp the hero avatar shrinks (never below 96 dp) so that Mute, Speaker and End call remain on screen and reachable without scrolling.
- Never clipped or unreachable: any column that can exceed the window height scrolls (`verticalScroll` or `LazyColumn`); pinned footers use `heightIn(min = …)`, not fixed heights; at heights under 480 dp a footer and its content may scroll together instead of leaving no room for the form.
- Resize keeps input: all restoration rules below apply to a resize recreation.
- Verification is on a resizable emulator (CONTEXT specifics); the layout is not restyled per width.

## Insets Standard (POL-03, D-17)

`enableEdgeToEdge(...)` with transparent dark `SystemBarStyle` is already set in `MainActivity`, and `adjustResize` is declared. At targetSdk 35 and up the system also enforces edge-to-edge, and on API 30+ `adjustResize` no longer resizes the window, so **Compose must apply the IME inset itself**. Light status and navigation icons on a dark surface are the only style; no screen may draw a light surface under a bar.

Rules (R1 to R9). The first seven are what the design-rules script and the Robolectric inset tests check.

| # | Rule |
|---|------|
| R1 | A `Scaffold` uses the default `contentWindowInsets` and applies the `innerPadding` it hands out to its content. Setting `contentWindowInsets = WindowInsets(0, 0, 0, 0)` is allowed only when the same file also handles the nav bar and IME itself (`navigationBarsPadding`, `imePadding`, `windowInsetsPadding`, `safeDrawing` or `WindowInsets.navigationBars`). Four screens do this today (Make a Booking, Availability, Topic Editor, Tax & Payout Info) |
| R2 | Scrolling content ends with bottom padding of `Spacing.xl` plus the navigation-bar inset, so the last item can scroll fully clear of the gesture bar or 3-button bar |
| R3 | A pinned bottom bar (footer CTA, chat composer, sheet footer) applies `navigationBarsPadding()` **then** `imePadding()` in that order, and only once per path from the field to the bar. Insets consumed by an earlier modifier are not counted again, so there is no doubled gap when the keyboard opens (Phase 13-13 removed one such duplicate). Where a parent `Scaffold` already consumed the nav inset (tab shell), add only `imePadding()` |
| R4 | A focused text field, its helper line and its error line are fully visible above the IME, and the pinned footer stays visible above the IME. Multi-line fields (bio, notes, comments, report details, decline reason) scroll into view on focus and as the caret moves |
| R5 | Display cutouts: handled **once**, at the two roots that host screens (the navigation host and the call overlay host), with `windowInsetsPadding(WindowInsets.displayCutout.only(WindowInsetsSides.Horizontal))`. Because the modifier consumes the insets, descendants do not pad again. Full-bleed decoration is drawn outside that padding. In portrait on phones the cutout sits inside the status bar inset, so this only has a visible effect on large or resized windows |
| R6 | `ModalBottomSheet` content keeps the sheet's default bottom system-bar inset and, for any sheet with a text field (Report details, Decline reason, Accept message, Expertise search, picker search), applies `imePadding()` at the content root inside a scrollable container. The sheet must not open covered by the keyboard |
| R7 | No `AlertDialog` contains a text field. An input that needs a keyboard is a sheet or an inline form. (If one is found, convert it; dialog windows do not follow R3.) |
| R8 | The status bar region carries the app bar background or the screen background; text never sits under the status bar. App bars use `TopAppBar` default insets |
| R9 | The Snackbar host is inside the Scaffold `snackbarHost` slot (clears bars and pinned footers) and stays above the IME |

**Guard (D-17).** Extend `scripts/check-design-rules.sh` with an insets rule, fail-on-hit with an opt-out comment `// insets-ok: <reason>` on or directly above the flagged line, using these tests (the exact grep is the planner's; the rule meaning is fixed here):
- (a) A file containing `Scaffold(` and neither `innerPadding` nor `paddingValues` nor `contentWindowInsets` is flagged.
- (b) A file containing `contentWindowInsets = WindowInsets(0` and none of `navigationBarsPadding`, `imePadding`, `windowInsetsPadding`, `safeDrawing`, `WindowInsets.navigationBars` is flagged.
- (c) A `*Screen.kt` or sheet file that contains `TextField(` or `ValidatedField(` and none of `imePadding`, `verticalScroll`, `LazyColumn` is flagged.

**Robolectric inset tests (D-17).** Apply IME and cutout insets to: the chat composer (composer fully above the IME, Send reachable, list still scrolls), the Login form, the Make a Booking footer, one Settings form, and one sheet with a text field (Report details). Assert bounds against the inset, not pixel values.

## State Restoration Standard (POL-02, D-09..D-13)

What the user must see after Activity recreation (config change, resize, "Don't keep activities") and after process death. Booking is the reference pattern (D-13): `SavedStateHandle` plus assisted injection.

| Surface | Restored | Not restored | Visual rule after restore |
|---------|----------|--------------|----------------------------|
| **Signup steps** | Current step (back stack keys are serializable), unsaved field text (name, city, etc.), chip and picker selections | Passwords, OTP codes, any secret: **never written to the saved-state Bundle** (D-09). Verify Email resend cooldown (server throttles) | The step reopens where it was. Restored text wins over server-hydrated values; hydration of the app-scoped `SignupDraft` fills only fields the user has not edited. Secret fields come back **empty with no error text and no focus ring**; an error appears only after the user interacts |
| **Chat composer** | Unsent text per thread (D-10), caret at end | Failed bubbles (Phase 12 D-02). Anything across an app restart | Text is back in the composer; focus is **not** forced and the keyboard does **not** reopen on restore |
| **Booking** (reference) | Topic, day, month, slot, meeting type, notes | The 3DS bank step returns an idle form (accepted, Phase 7 D-17) | Request Sent animation is not replayed (existing) |
| **Forms** (profile settings, Account Security non-secrets, Topic Editor, Availability, Tax non-secrets, Cancel reason + comment, Write Review rating + text) | Typed text, selections, step | Current password, new password, TIN, deletion password and token | Same as Signup secrets: empty, no error |
| **Sheets and dialogs that hold input** (D-12): Report details, Decline reason, Accept message, Time range, Professional Details, Expertise editor, picker search | Open/closed flag and every input inside | Nothing | The sheet reopens already expanded with its input; no re-entrance animation is required |
| **Confirm-only dialogs** (cancel booking, delete topic, log out, block, discard) | Nothing | Everything | They simply close. A restored app never auto-confirms and never shows a confirm that was already executed |
| **Lists and scroll** | Best effort (D-12): kept where the data loads synchronously (the saveable holder keeps `LazyListState` per back stack entry) | Not guaranteed otherwise | Content may start at the top after a reload; never a blank screen or a skeleton that never resolves |
| **Live call** (D-11) | Nothing is auto-resumed | The audio session and mic state | See "Process death during a call" |
| **Activity recreation during a call** (not a process kill) | Everything: the call is held by the foreground service and `CallCenter` | None | No re-join, no flash back to "Connecting", timer continuous (it is anchored to the scheduled start), mute and speaker state kept, the pill or full layer shows the same state |

**Process death during a call (D-11).** Relaunch goes through Splash and routes to the booking detail for that call (client Upcoming Booking Details, or expert Booking Summary). It never opens the call layer and never opens the mic.
- The Join Call button is the primary action on that screen, labeled "Join Call" (the existing label; rejoin uses the same control). The mic permission and the Agora token are fetched again on tap, through the existing dialogs.
- (Android, Assumption A4) If the app can tell that a call was in progress, show one `bodyLarge` line above the join card: "You were on a call. Tap Join Call to rejoin." as a polite live region. If it cannot tell, show the plain screen with no note.

**Back stack.** Navigation 3 keys must stay `@Serializable`; any new key added in the future must be too. A restored back stack must put the user on the same screen with Back leading to the same previous screens.

## Accessibility Contract (POL-04)

### Global rules (every screen)

1. **Touch targets** at least 48 dp in both dimensions (use `minimumInteractiveComponentSize`); visually smaller icons keep a 48 dp hit area.
2. **One node per row or card**: merge descendants for rows, cards and list items; icons that repeat adjacent text are `contentDescription = null`; icon-only buttons have a string-resource `contentDescription`.
3. **Roles**: `Role.Button` for buttons and rows that act, `Role.Switch` for toggles (mute, speaker), `Role.RadioButton` inside `selectableGroup()` for single-choice rows, `Role.Tab` for tabs, `Role.Checkbox` for multi-select chips and rows.
4. **Headings**: each screen title, section caption and state heading is `heading()`. `EmptyState`'s heading gets `semantics { heading() }`.
5. **State**: `stateDescription` for anything whose state is not in its text: selected day or slot, disabled-with-reason (Join Call "Available closer to the session start"), busy ("In progress"), expanded or collapsed, muted or unmuted.
6. **Announcements**: error and result text that appears without a user action is a polite live region (`SectionError` already is; `ErrorState` heading and body become one polite region). Do **not** put a live region on anything that updates continuously (call timer, typing indicator, character counters).
7. **Text fields** expose a name (the visible label or placeholder) separate from the value; password values are masked; the field's `error` semantics carry the error text; when a submit fails, focus moves to the first failing field so TalkBack reads its error.
8. **Initial focus**: result and terminal screens (Request Sent, Booking Confirmed, Password Changed, Farewell) move TalkBack focus to the headline on entry. Other screens start at the app bar title.
9. **Font scale to 200%**: no clipped text, no truncated essential content, controls reflow (rule in Typography).
10. **Contrast** per the Color section. **Motion**: with animations off the final state shows at once (inherited).

### The four SC-4 flows (acceptance bar)

For each flow, the traversal order is the order listed; a node named in quotes is exact copy from the existing strings unless marked (new).

**Flow 1: Log in** (`LoginScreen`, plus Forgot Password, Set New Password, Password Changed)
- Order: screen title or wordmark (heading) -> tagline -> "Email" field -> "Password" field -> password toggle -> "Forgot Password?" -> "Log in" button -> "Don't have an account? Sign Up" row (one node, one action).
- The password toggle's name flips between "Show password" and "Hide password" (existing); its state is not also in `stateDescription`.
- Inline errors (wrong password message under the password field) are announced when they appear: the field carries `error()` and the error text is a polite live region; focus returns to the failing field.
- In flight: the Log in button has `stateDescription` "In progress" (new string `a11y_in_progress`), taps ignored.
- Network failure dialog ("Check your connection and try again.") is announced by the dialog window; "Got it" returns focus to the Log in button.
- Landing on the home screen: initial focus on the app bar title.

**Flow 2: Book a session** (Expert Profile -> Make a Booking -> Request Sent)
- Expert Profile: the "Book Session" button is a normal `Role.Button` after the expert's name, rating and About, with the expert name in its description ("Book Session with {name}", new `contentDescription`).
- Make a Booking order: app bar title -> "Topic" row (one node: label + chosen topic, `Role.Button`, opens the picker sheet) -> calendar group (month title as heading, "Previous month", "Next month", then day cells in date order) -> time slots group -> meeting type group -> "Notes" field -> "Book Now".
- Day cell: one node reading the full date ("Tuesday, 3 November"), with `stateDescription` one of "Available", "No availability", "Selected". Past days and months before today are disabled and say so. The calendar and the slot list are separate traversal groups so a swipe does not wander between them.
- When a day is chosen, the slots card heading is a polite live region that announces the result ("{n} times available" or "No times this day").
- Slot cell: one node "{start} to {end}", `stateDescription` "Available", "Held, unavailable" or "Selected".
- Meeting type: `selectableGroup()` of `Role.RadioButton` rows. The notes counter is readable on focus but is not a live region.
- "Book Now": disabled state carries the reason via `stateDescription` ("Choose a time to continue" while no slot is selected, new string if absent); in flight "In progress". Paid flows hand off to Stripe's own sheet, whose accessibility is Stripe's.
- Success: Request Sent takes focus on its headline; "View My Bookings" and "Back to Home" are buttons after the summary card.
- The topic picker sheet: rows are `Role.RadioButton` in a `selectableGroup()`; the sheet title is the sheet's first heading; closing returns focus to the Topic row.

**Flow 3: Join a call** (Join Call entry points -> Meeting Call layer -> pill)
- Entry points (Upcoming Booking Details, My Bookings card, Today's Sessions card, expert Dashboard / Bookings / Summary): "Join Call" is `Role.Button`. Disabled outside the window: `stateDescription` "Available closer to the session start" (existing). Starting a call: `stateDescription` "In progress".
- Permission rationale and recovery dialogs are announced by the dialog; their buttons follow the existing labels.
- Call layer order (inside the existing `isTraversalGroup`): connection status line (polite live region: "Connecting", "Waiting for the other person", "Connected") -> peer name (heading) -> timer (text, **not** a live region; reads "{m} minutes {s} seconds" form already defined in `call_timer_a11y_*`) -> Mute (`Role.Switch`, `stateDescription` "Muted" / "Unmuted") -> Speaker (`Role.Switch`, "Speaker on" / "Speaker off") -> Chat -> Minimize ("Minimize call", existing) -> End call (last, so it is never hit by accident while swiping).
- Moments announced once as a polite live region: peer joined, peer left ("Waiting for the other person"), the final-5-minutes banner (existing copy, announced when it appears, not every second), connection lost and restored.
- Entering the layer moves TalkBack focus to the status line. Predictive back / Minimize returns focus to the control that opened it.
- The minimized pill keeps its merged `Role.Button` node "Return to call with {name}" and is the **first** focusable node on every screen while a call is active (give the pill host `traversalIndex = -1f` inside its own traversal group; Assumption A8). Tapping it opens the layer.
- Ending: End call announces nothing extra; the result screen takes focus on its headline.

**Flow 4: Send a chat message** (Conversations -> Chat thread)
- Conversations: one node per row: "{name}, {last message}, {time}" plus ", {n} unread" when the badge shows. Filter or tab controls (if any) are `Role.Tab`.
- Thread order: app bar title (peer name, heading) -> messages from oldest to newest as laid out top to bottom -> composer. Each bubble is one node "{speaker}: {text}", then time, then status ("Sent", "Read", "Failed to send"). The speaker is "You" or the peer's name (existing).
- The newest own bubble's status text is a polite live region ("Sent", then "Read"); a newly arrived peer message is a polite live region announcing "{name}: {text}". Neither fires for history loaded with the page.
- A failed bubble has custom actions "Retry sending" and "Delete" (existing) and its description says it failed.
- Composer: text field named "Message" (existing placeholder), then the "Send message" button (existing description). Send is `enabled = false` with `stateDescription` "Type a message to send" when empty. After a send, the field clears and **focus stays in the field**; the IME stays open.
- The character counter appears only near the limit and is not a live region; reaching the limit announces "Message length limit reached" once (existing copy, polite).
- The typing indicator is not announced.
- Blocked-thread banner and Report & Block screens follow the same rules (banner is a polite live region on entry).

### Other screens
Every other screen follows the Global rules and the Phase 14 contract. Per D-16 the order of effort is: the four flows above, then remaining client screens, then expert screens, then settings. TalkBack coverage of Phase 13 (notifications list, Write Review, Feedback block, Past card pill) and Phase 14 (every screen) is required by their hand-offs.

| # | Assumption | Basis |

| A11 | New strings: `common_refresh_failed`, `common_load_error_body_server`, `a11y_in_progress`, "Choose a time to continue" and "Type a message to send" only if no equivalent already exists | Planner greps first; reuse beats adding (D-08) |
