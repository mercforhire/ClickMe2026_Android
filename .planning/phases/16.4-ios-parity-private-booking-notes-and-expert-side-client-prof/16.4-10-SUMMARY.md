# Phase 16.4 Plan 10: Expert chat View profile, shell route proof and the phase gate Summary

An expert in a chat thread now taps View profile and lands on the read-only Client Profile on the Chats stack, both expert routes are proven in the shell, the full gate is green, and every manual check for the phase is an open row in the Phase 16 matrix.

## What was built

- **Task 1 (tracer).** `openChatPeerProfile(key, mode)` takes a required `mode`. Client mode pushes the existing `ExpertProfileKey`; expert mode pushes `ExpertClientProfileKey(peerId, ExpertBookingOrigin.Chats)`; no peer id pushes nothing. The thread menu shows View profile with `if (mode == AppMode.Client) state.peerIsExpert == true else !state.isSelfThread`, enabled once the peer id is known. `ChatThreadRoute` passes its own `mode`. Tracer `<verify>` passed (ChatThreadScreenTest 52 tests and ChatNavigationTest 10 tests, ktlint clean) and was not re-run before expansion because it had just passed on the committed code; `⚡ Tracer verified end-to-end — expanding`.
- **Task 2.** Four `HomeShellsTest` tests drive the real `expertBookingNoteEntry` and `expertClientProfileEntry` inside `HomeExpertShell`: bar hidden and Back pops for each, and Bookings-origin vs Chats-origin content of each coexists with no crash, Back from the Chats one shows the Chats root, and selecting Bookings shows the Bookings one. No main code needed to change.
- **Task 3.** Gate commands all exit 0 on the final tree: `:app:testDevDebugUnitTest ktlintCheck` (5019 tests, 0 failures, 0 skipped), `:app:lintDevDebug`, `scripts/check-design-rules.sh` ("Design rules: OK"). Runbook sections `2f-N` and `4e-N`, rows `D1.PN1`-`D1.PN5`, `D2.PN1`-`D2.PN2`, `D2.CP1`-`D2.CP3`, `FS.PN1`, `FS.CP1`, and one Session log line were added. No existing row was edited.
