## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Leaving with unsaved changes shows a Material `AlertDialog` ("Discard changes?" with Keep editing / Discard). It covers both the TopAppBar back arrow and system back, and doesn't appear when nothing has changed. Deliberate deviation: iOS silently discards.
- **D-02:** The note field has a hard 5,000-character cap using `capText` (`screens/chat/TextCap.kt`), which matches the backend's zod `max(5000)` on UTF-16 code units. A character counter appears near the limit (from about 4,500). A long paste is cut at the cap. Deliberate deviation: iOS has no cap, so an over-long note only fails on save.
- **D-03:** Save follows iOS. A TopAppBar Save action, disabled when nothing has changed. While saving it shows a spinner and ignores further taps. On success it shows a saved state for 1.5 s and stays on the screen. On failure it shows a Material `AlertDialog` titled "Couldn't save note" with the server message, and keeps the text.
- **D-04:** A whitespace-only note is sent as an empty string, which clears the note. Cards then show no blank preview. Otherwise the text is sent as typed. Deliberate deviation: iOS saves it as typed.
- **D-05:** One shared editor serves both roles with a client key and an expert key, as the audit proposes. Title "My Note". The header shows the other party's name, the topic and the date, passed in through the key because the note endpoints don't return them.
- **Carried from iOS:** a 404 on load means "no note yet" and shows an empty editor (uniform-404 contract), not an error. A null note is an empty field. A loaded editor isn't reloaded over unsaved edits.
- **D-06:** The client Booking Summary "My Note" card opens the editor from every route into Booking Summary (My Bookings, chat, push and any other). The note key must be registered on each stack that can show the summary. Deliberate fix: on iOS the card only works when opened from My Bookings.
- **D-07:** Notes appear only where iOS shows them. Client: past card, upcoming card, Booking Summary. Expert: past card, upcoming card, Expert Booking Summary. Upcoming Booking Details gets no note card (iOS has none).
- **D-08:** A saved note shows up on return. Summaries show the full note from the details payload (`private_note`, `expert_private_note`) and cards show the server's 140-character `private_note_preview`, relying on the existing quiet refresh on return (16.3 D-09). If a screen doesn't refresh on return today, this phase adds that. Deliberate fix: iOS can go stale here.
- **D-09:** Each history row shows the expert's real net earnings on the right, using the existing `netEarningsText` logic (`upcomingbookings/subviews/ExpertUpcomingCard.kt`). Show nothing when there's no net amount or currency, for example on free sessions. Deliberate fix: iOS always shows "$0" because its amount is a stub. Rows in the cancelled bucket (cancelled, declined, missed, expired) show no amount, so the screen never implies money that wasn't earned. Research must confirm what the breakdown contains for these statuses. Revisit this rule if the data shows otherwise.
- **D-10:** Rows are read-only, as on iOS. They aren't tappable.
- **D-11:** History comes from the same requests as iOS: `GET /expert/bookings` with `type=upcoming` and `type=past`, page 1, `limit=50` each, merged, filtered to `client.id == clientId` (compare case-insensitively, since iOS and Android UUID casing differs), sorted newest first. No further paging. A very busy expert can see fewer rows than the server's session count. This is accepted.
- **D-12:** If the profile or either bookings request fails, the whole screen shows the error state with Retry, as on iOS. It never shows a partial history as if it were complete. This doesn't apply to the D-14 and D-15 states.
- **Carried from iOS:** the status bucket mapping per `ClientProfileViewModel.mapStatus`. The history section is hidden when empty. Dates use the `MMM d, yyyy` pattern, topic falls back to "Session".
- **D-13:** View Profile is always offered in expert-mode chat threads, as on iOS, and is disabled only until the peer id is known. It isn't gated on `peerIsExpert` because every signup has the expert role. Client mode keeps its current rule and still opens Expert Profile. The self-thread case keeps today's behaviour.
- **D-14:** On `403 NO_RELATIONSHIP` the screen shows a friendly state such as "No bookings with this person yet", with no Retry, because retrying can't help. Reachable because `GET /chats` isn't filtered by mode. Deliberate deviation: iOS shows a generic error with Retry.
- **D-15:** On `404` the screen shows a "Profile unavailable" state with no Retry, like Android's Expert Profile (`DetailsState.Unavailable`). Other failures use "Couldn't load profile" with Retry (D-12).
- **Carried from iOS:** Expert Booking Summary shows a "View Profile" link under the client's name. TopAppBar title "Client Profile" with a back arrow. Layout order: avatar, name and "Client" badge, About (Bio, Location, Timezone, Languages, Member since; each row hidden when empty), "Your Sessions Together" (sessions, Client since, Last session, "—" when null), booking history.

## Summary

The backend is complete for all of this. Four note endpoints exist with a uniform 404 (not-found and not-owned look identical), independent client and expert columns, and a zod `max(5000)` strict body. `GET /expert/clients/:id` exists with 404 and 403 `NO_RELATIONSHIP`. Android needs: 5 Retrofit methods, 4 small DTOs plus 3 optional fields on existing DTOs, one note repository, one shared editor (VM + screen) with two keys, one Client Profile feature (key, repository/VM, screen, subviews), a small shared set of note composables used by six surfaces, and entry plumbing in both shells. No new Gradle dependency and no new package.

**D-09 answer (confirmed, with one nuance).** `earnings_breakdown` is derived only from `amount_paid_minor_units`, which is written once at booking creation (status `pending_approval`) and never changed by cancel, decline, miss or expiry. So the expert feed returns a fully populated `net_amount` for cancelled, declined, missed and expired rows: the breakdown does NOT go to null or zero. Showing it would imply money that was never earned. The `expert_earnings` ledger is written only on completion. The "no amount in the cancelled bucket" rule is therefore confirmed. Nuance: a `missed` booking where `no_show_party = 'client'` IS captured (the expert is paid), but the list payload does not carry `no_show_party`, so the list cannot tell the two apart. Keeping the rule (omit for `missed`) is the safe direction; flag it to the user (Open Question 1).

**D-08 answer (confirmed).** All four screens already reload quietly on return, with the three-effect wiring (`ON_RESUME`, `ON_PAUSE`/dispose, `LaunchedEffect(Unit)`): client Booking Summary, Expert Booking Summary, My Bookings and the expert Bookings tab. Nothing needs adding for refresh; the new work is only reading the new fields.

**Primary recommendation:** Build in this order: (a) network + DTOs + repositories + `FakeClickMeApi` + fixtures + wire tests; (b) shared editor + note keys; (c) shared note composables and the six entry points (flip the existing tests that assert notes are absent); (d) Client Profile; (e) one wiring plan for `HomeClientScreen.kt`, `HomeExpertScreen.kt`, chat menu, `HomeShellsTest`. This matches the audit's "Phase D" four plans.

### Pattern 1: Shared note editor
- `enum class NoteRole { Client, Expert }`; `BookingNoteRepository` (`@Singleton`, `apiCall { }`): `get(role, id): String?` and `save(role, id, note): String?` switch on role. Throws `ApiException` only (project rule: [VERIFIED: ExpertBookingsRepository KDoc, "Every call throws ApiException only"]).
- `BookingNoteViewModel` via `@AssistedInject` taking a small `BookingNoteArgs(role, bookingId)`; each key's entry builds the args. State: `noteText`, `load` (Loading/Loaded/Failed), `isSaving`, `didSave`, `saveError: FieldError?`, `showDiscardPrompt`.
- Behaviour to implement (all JVM-testable):
  - `load()`: skip when already `Loaded` (never reload over edits). `ApiException.Http` with status 404 or code `NotFound` => empty `Loaded` (use `ApiException.isNotFound()`, `screens/clientmode/makeabooking/BookingErrors.kt:80`). Any other failure => `Failed` with Retry. `note == null` => `""`.
  - `onTextChange(raw)`: `noteText = capText(raw, 5_000)` (`screens/chat/TextCap.kt`). Counter shown when `noteText.length >= 4_500`.
  - **Normalize rule (see Pitfall 4):** `normalize(s) = if (s.isBlank()) "" else s`. `lastPersisted = normalize(loadedOrSaved)`. `hasChanges = normalize(noteText) != lastPersisted`. The body sent is `normalize(noteText)`.
  - `save()`: `if (isSaving || !hasChanges) return`; set `isSaving`; on success `lastPersisted = normalize(sent)`, `didSave = true`, `launch { delay(1_500); didSave = false }`; on `ApiException` set `saveError` (server `userMessage` else the string-resource fallback), keep `noteText`. A 404 on POST is an ERROR (alert), not an empty note.
  - `requestLeave(): Boolean`: false and `showDiscardPrompt = true` when `hasChanges`; true otherwise. `BackHandler(enabled = hasChanges)` and the TopAppBar arrow both call it; `BackHandler(enabled = isSaving) {}` registered after swallows Back during a save (Phase 8 convention, [VERIFIED: WriteReviewScreen.kt:81-82]).
- UI: `AuthTopAppBar(title = "My Note", onBack, actions = { Save | spinner | check })` ([VERIFIED: screens/login/AuthTopAppBar.kt:27-34]); body is a `verticalScroll` column with `imePadding()` (design-rule (c)), header (name, topic, date line), an `OutlinedTextField` min height ~260 dp with placeholder "Jot down your thoughts about this session — only you'll see this." Reuse `AuthErrorDialog(message, onDismiss, title = "Couldn't save note")` ([VERIFIED: screens/login/AuthErrorDialog.kt:20-26]); the discard dialog is a plain `AlertDialog` with no text field (design-rule R7). Loading = Phase 15 skeleton; failure = `ErrorState(onRetry, heading = "Couldn't load note", body = message)` ([VERIFIED: components/EmptyState.kt:92-98]).
- Date line from the key's `startMillis`/`endMillis`: `formatShortDate` + `formatSessionTimeRange` joined with `R.string.my_bookings_date_time` (`"%1$s, %2$s"`), exactly as the cards do, so it matches the card the user came from. Device zone and device 12/24h format.

### Pattern 3: Entry points (six surfaces) with shared composables

- Treat the preview as absent when `isNullOrBlank()` (stricter than iOS `isEmpty`; a note saved as whitespace from iOS yields preview `"   "`).

## Common Pitfalls

### Pitfall 1: Duplicate Nav3 content keys
**What goes wrong:** `NavDisplay` crashes when two stacks hold equal keys (`toDecoratedEntries` flattens the start stack with the selected one).
**How to avoid:** `origin` on all three new keys, copied from the opener (see Pattern 2). Add `ChatNavigationTest`-style assertions that `ClientBookingNoteKey(..., Chats) != ClientBookingNoteKey(..., Default)` and likewise for the expert keys, plus a `kotlinx.serialization` round-trip test (precedent: `ExpertNavigationTest.kt:153-154`).
**Warning signs:** crash only when the same booking is open on two tabs.

### Pitfall 2: `FakeClickMeApi` and existing tests stop compiling / flip
Adding 5 methods to `ClickMeApi` breaks `FakeClickMeApi` (89 test files use it); add handler lambdas + call counters + recorded requests in the same plan as the interface change. Existing tests that encode the OLD behavior must be changed deliberately (each is a plan task):
- `MyBookingsScreenTest.kt:467-480` `content_neverOffersExcludedActions` asserts "Private Note" absent on Upcoming and Past.
- `BookingSummaryScreenTest.kt:283` `privateNoteDoesNotRender` asserts "My Note" absent.
- `ExpertBookingSummaryScreenTest.kt:422-426` `noRescheduleNoteReportOrBlockControls` lists "Private Note" and "My Note" as absent.
- `ChatThreadScreenTest.kt:414-419` `viewProfileIsAbsentInExpertMode` (now present in expert mode). Keep `selfThreadHidesMenu` (`:423-427`, expert mode + `isSelfThread` => no menu) passing, which is what A2 preserves.
- Keep as-is: `UpcomingBookingScreenTest.kt:751` `noPrivateNoteActionExists` (D-07, Upcoming Details gets no note).
- `HomeShellsTest.kt:1736-1738` registers stub entries per key; add stubs for the new keys.
- Also extend `testing/ExpertBookingFixtures.kt` and the client booking fixture with a `privateNotePreview` parameter.

### Pitfall 3: Reusing the Bookings list builder for history
`buildExpertBookingLists` excludes `pending_approval` and drops statuses without a Past label, and moves rejoinable `completed` rows into Upcoming. [VERIFIED: ExpertBookingBuckets.kt:41-60 KDoc]. iOS history keeps everything for the client. Write a separate merge.

### Pitfall 4: Whitespace-only note vs `hasChanges`
With D-04 (send `""` for whitespace-only), a naive `hasChanges = noteText != lastPersisted` stays true after saving `"   "` (server answers `note: null`), so Save re-enables forever and the discard prompt appears. Use the normalize rule in Pattern 1 on BOTH sides; also normalize a loaded note (a whitespace note written from iOS loads as `"  "` and must not count as a change). `lastPersisted` should be what was SENT, not `response.note ?: noteText` as iOS does.

### Pitfall 5: POST vs GET 404
Only the GET 404 is "empty". A POST 404 (booking vanished) must show the "Couldn't save note" dialog.

### Pitfall 6: Process death / rotation
State in the VM survives rotation. A typed draft is lost on process death unless mirrored to `SavedStateHandle` (precedent `ReportAndBlockViewModel`). CONTEXT does not require it (A4); if added, store only the text under one key and never log it.

### Pitfall 7: Client Profile id casing
iOS UUIDs are upper-case, Android/Postgres lower-case: compare with `equals(ignoreCase = true)` (D-11) and test it.

### Pitfall 8: Preview strings
`private_note_preview` is `slice(0, 140)` on UTF-16 units, so it can end in half a surrogate pair; harmless (renders a replacement glyph) but do not assert exact equality on emoji in tests. Show at most 2 lines with ellipsis.

### Pitfall 9: Parallel 16.5 work
`.planning/phases/16.5-*` is open in the working tree and will also touch `ClickMeApi.kt`, `ApiRequestUrls.kt`, `FakeClickMeApi.kt`, `ApiRequestUrlsTest`, strings and the hubs. Keep new API methods in a clearly delimited block and expect trivial merge conflicts if the two phases run in parallel worktrees.

### Pitfall 10: Layout fit on cards
The Past card is one tappable `Surface` with a `FlowRow`; add the note action as a second nested target without breaking the card's merged semantics. The Upcoming cards already have three layouts from 16.2 (Join + icon Message; Join + Reschedule/Message pair; pending banner + Reschedule/Message pair); the note zone is a separate last child in the card's `Column`, so it does not interact with them. Test at large font scale (cards use `FlowRow` and `heightIn(min)` for this reason).

### Applicable ASVS Categories

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Reading another party's note (client reads expert note) | Information disclosure | Separate columns and endpoints; uniform 404; Android picks endpoint from role key only |
| Existence enumeration of bookings/clients | Information disclosure | Server returns the same 404; Android shows the same empty note / "unavailable" for 404 |
| Client-only account silently converted to expert by `ensureExpert` | Elevation of privilege | Offer View Profile only in expert mode (D-13) |
| Note text leaking via logs or crash reports | Information disclosure | Redacted `toString`; never interpolate note into log/exception messages |
| Oversized body | DoS | 5,000 cap client-side, zod server-side |
