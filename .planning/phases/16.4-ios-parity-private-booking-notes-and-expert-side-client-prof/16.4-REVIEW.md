## Summary

The phase is in good shape. I traced each area you flagged and found no incorrect behavior against D-01 to D-15 in the main paths:

- **Note privacy.** `BookingNoteUiState`, `BookingNoteRequest`, `BookingNoteData`, `ClientBookingItem`, `ClientBookingDetail`, `ExpertBookingItem`, `ExpertBookingDetail`, `BookingSummaryDetails`, `ExpertSummaryDetails` and `ExpertClientProfileData` all override `toString` and omit note text. Navigation keys carry no note text. There is no `HttpLoggingInterceptor` anywhere in the app, so request bodies are not logged.
- **Role separation.** The role is fixed in `ClientBookingNoteRoute` and `ExpertBookingNoteRoute`. `BookingNoteRepository` picks the endpoint pair from the role only. The client summary reads `private_note` and the expert summary reads `expert_private_note`. Cards read each side's own `private_note_preview`.
- **Discard gate.** Both back paths (the TopAppBar arrow and system back) go through `requestLeave`. An in-flight save swallows both. Typing during a save stays dirty, and the saved check shows only while the text is unchanged.
- **Save state.** `canSave` gates repeated taps, and a failed save keeps the text. A POST 404 is an error, while a GET 404 is an empty editor.
- **403 and 404 states.** `NO_RELATIONSHIP` and 404 map to their own terminal states with no Retry. A bookings-call 404 is a generic failure, and a failed pull over loaded content keeps the content.
- **History rules.** The merge is filtered to `client.id` ignoring case, de-duplicated and sorted newest first, with the bucket mapping matching iOS `mapStatus`. The amount gate hides amounts for the cancelled bucket and for unknown statuses. Zero net shows "$0.00" deliberately, and `16.4-RESEARCH.md` line 131 records that a free request path sends no amount, so it yields a null net.
- **Navigation keys.** The origin is copied from the opener, so the note and Client Profile keys stay distinct per stack. `ExpertClientProfileKey` is registered in the expert shell only.
- **Chat menu.** Expert mode uses `!isSelfThread` and ignores `peerIsExpert`. It is disabled until `peerId` is known. Client mode keeps its old rule. `openChatPeerProfile` has no default for `mode`, which is the right guard against `ensureExpert` conversion.
- **Refresh on return.** `MyBookingsScreen`, `ExpertBookingsScreen`, `BookingSummaryScreen` and `ExpertBookingSummaryScreen` all refresh quietly on resume, so D-08 holds.

I found two quality-level warnings and three informational items. There are no blockers.

## Warnings

### WR-01: Note preview and My Note text are not trimmed, so a note that starts with blank lines can render as an empty strip

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/components/booknote/PrivateNoteParts.kt:232-239` (also `:192-196`)
**Issue:** `PrivateNoteZone` and `NotePreviewFooter` only gate on `isNullOrBlank()`. They pass the raw `preview` to `NotePreviewStrip`, which renders it with `maxLines = 2`.

D-04 sends the text "as typed". The server preview is the first 140 UTF-16 units of that text. A note such as `"\n\nCall about pricing"` gives a preview whose first two lines are blank. The strip then shows a pencil next to an empty two-line block, and the real text is clipped away. A user cannot tell that a note exists or what it says. `MyNoteCard` has the same leading-whitespace problem but is not clipped, so it only wastes space.

**Fix:** Collapse whitespace for the preview only. Do not change what is saved:
```kotlin
val shown = preview.trim().replace(Regex("\\s*\\n\\s*"), " ")
Text(text = shown, /* ... */ maxLines = PREVIEW_MAX_LINES, overflow = TextOverflow.Ellipsis)
```
Apply `trim()` to the `MyNoteCard` body as well. Add a `PrivateNotePartsTest` case with a leading-newline preview.

### WR-02: Save failures that `toDialogError()` maps to null leave the user with no feedback

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/bookingnote/BookingNoteViewModel.kt:99-102`
**Issue:** The catch block sets `saveError = e.toDialogError()`. The test `suspendedSaveShowsNoDialog` shows that this returns null for `ACCOUNT_SUSPENDED`. `isSaving` then resets, the text stays, and Save becomes enabled again. If the global suspension handler does not visibly interrupt the screen, the user sees the spinner stop and nothing else, which breaks D-03's "on failure show the dialog" for that class of error. Other global-handled codes may behave the same way. This is probably the app-wide convention, so I rate it WARNING and not BLOCKER. Confirm that the suspension flow always takes over the UI.

**Fix:** If the global handler is not guaranteed to navigate away, show a generic "Couldn't save note" message when `toDialogError()` is null:
```kotlin
val error = e.toDialogError() ?: FieldError.Res(R.string.login_error_generic)
_uiState.update { it.copy(isSaving = false, saveError = error) }
```
If the handler is guaranteed to take over, record that guarantee in a comment instead.

## Info

### IN-01: Client Profile history row shows an empty title for a blank topic

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/expertmode/clientprofile/subviews/ClientProfileBookingHistory.kt:75`
**Issue:** `row.item.topic ?: stringResource(...)` falls back only on null. The carried iOS rule ("topic falls back to Session") uses `??` too, but every other Android card in this phase treats a blank topic as missing, for example `BookingNoteScreen.kt:341` uses `takeIf { it.isNotBlank() }`. A `""` or whitespace topic from the server gives a blank row title and a spoken description that starts with ". ".
**Fix:** `val title = row.item.topic?.takeIf { it.isNotBlank() } ?: stringResource(R.string.client_profile_session_fallback)`
