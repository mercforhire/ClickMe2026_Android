<objective>
Close gap G-11-5 (major). After 11-16, the Android expert's join reaches CONNECTED. The Android expert and the iOS client both reach the call screen for the same booking, but both stay at "waiting for the other person". The Android SDK raised no remote-user callback in three joins, one of them 2 min 14 s long.

The diagnosis is `.planning/debug/android-ios-call-peers-never-meet.md`, at about 65% confidence. It found one code-level difference between the platforms:
- iOS creates its engine in the COMMUNICATION channel profile and also joins with COMMUNICATION.
- Android's `buildRtcEngineConfig` never sets `RtcEngineConfig.mChannelProfile`, so the engine and its connection run the SDK default 1 (LIVE_BROADCASTING). Android sets COMMUNICATION only as a per-join option, and the device's agoraapi.log shows no profile change after joinChannel.
- App ID, channel (the booking id), PUBLISHER token, broadcaster role, int uid and backend are equivalent on both sides.
- The residual alternative (about 25%) is that the iOS tester was in a different booking.

This plan applies the iOS-parity fix and makes the next device run decisive. The engine is created in COMMUNICATION, and the per-join COMMUNICATION option stays. Both are guarded by JVM tests, including one through `join()` to the SDK factory. Remote presence becomes visible in logcat without logging the uid, token or channel. Two follow-ups from the 11-16 review are folded in because they sit in the same two files:
- IN-01: the per-join options are built without a receiver scope.
- WR-01: an engine whose setup fails is destroyed, so a retry cannot meet a leaked engine and confuse the device evidence.

The two-sided device re-test is deferred to the user as a non-blocking open item. Its ready-to-paste STATE text is below.
