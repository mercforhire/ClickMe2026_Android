## Summary

All five new endpoints are **authenticated**: `routes/index.js:75` is `router.use(authenticate);` and `clientTransactions`, `notificationHistory` and `feedback` are all mounted below it (lines 121, 123, 164). None is in `ApiRequestUrls.publicPaths`, so the allowlist is untouched and `assertEquals(5, ApiRequestUrls.publicPaths.size)` stays true. The phase only adds four path constants and an `...areAuthed` test, matching `phaseSixteenFourConstants_areAuthed`. The backend contracts in CONTEXT.md match the code. The disagreements that matter are below (see "Disagreements with CONTEXT / UI-SPEC").

Three findings change the plan:

1. **D-03 needs a code fix.** `UpcomingBookingScreen` is safe for Reschedule and Cancel on terminal bookings (both are allow-lists), but **Join Call is not**: `isWithinJoinWindow` falls through to a pure time test for every status that is not `pending_approval` or `completed`, so a `cancelled`, `declined`, `missed` or `expired` booking inside its +/-1 h window shows an **enabled** Join Call button, and outside it a disabled one with a misleading hint. The server does not backstop this: `POST /bookings/:id/join` checks participation and the time window only, never `status` (`call.controller.js:57-71`). Payment History is the first surface that opens these statuses on that screen.
2. **D-09 is not a missed-call risk.** There is no ringing or incoming-call concept on Android or iOS. Calls are user-initiated from a booking. A live call survives the splash (singleton `CallCenter`, foreground service) and the expanded call overlay sits above the route switch, so it is visible over the splash. A push destination is held in an in-memory slot until a home route exists. The one real effect is up to 3 s of added latency before a resumed booking's Join button appears.
3. **The UI-SPEC's system-splash handoff deadlocks as written.** "Keep the system splash until the Compose splash's first frame is drawn" cannot work, because core-splashscreen's keep condition cancels the first draw in an `OnPreDrawListener` (`SplashScreen.kt:279-295` and `431-449`). Gate on "Compose splash composed and laid out" instead.

**Primary recommendation:** Build the three screens by adapting existing precedents (`TransactionsViewModel`, `AutoSaver`, `ReviewTextField`, `AuthErrorDialog`) with no new dependencies. Implement the splash as a view-model-owned 3 s hold that is applied to the route the UI shows (`shownRoute = if (held) Splash else route`), leaving `AppViewModel.route` and `destinationResolved` semantics, and therefore all existing `AppViewModelTest` cases, unchanged. Fix `isWithinJoinWindow` and the Join card gating as part of D-03.

### Question 2 (D-09): cold start behind the fixed 3 s splash

**Verdict: no call can be missed or fail, no push destination is lost, and push navigation runs after the splash. No blocking user decision.**

Facts, each read this session:

- **There is no ringing.** No incoming-call UI, full-screen intent or ringtone exists on Android: `grep -i -E "ringing|incoming|ringtone|CATEGORY_CALL|fullScreenIntent|USE_FULL_SCREEN"` over `app/src/main` returns only the "Incoming Requests" booking-request strings and chat-thread reducer variables; the manifest lists only `INTERNET, ACCESS_NETWORK_STATE, RECORD_AUDIO, MODIFY_AUDIO_SETTINGS, FOREGROUND_SERVICE, FOREGROUND_SERVICE_MICROPHONE, POST_NOTIFICATIONS`. iOS has no CallKit/PushKit/ringing either (`grep -rli "CallKit|CXProvider|PushKit|ringing" ios-reference/ClickMe2026` is empty). Calls start only when the user taps Join Call (`UpcomingBookingViewModel.join()` -> `CallStarter.startCall`). CONTEXT D-09's "a call keeps ringing and stays answerable" describes a feature that does not exist; the real call paths are the next two bullets.
- **Live call + ongoing-call notification tap after a task swipe** (Phase 9 D-14: "The foreground service outlives the task, and its notification reopens the app with the call expanded"). `MainActivity.kt:59` runs `if (intent.consumeExpandCallExtra()) callCenter.expand()` in `onCreate`. `CallCenter` is `@Singleton` and owns the session (`CallCenter.kt` class doc: "the UI mounts and unmounts freely while this singleton keeps the session"); `expand()` sets `_isMinimized = false` when a session exists (`CallCenter.kt:~424-427`). The audio and the service never depend on the activity. The expanded layer is drawn by `CallOverlayHost`, which wraps the whole route switch (`ClickMeApp.kt:55`), so it draws **above** a Compose splash. The new splash therefore shows the call earlier than today (STATE.md notes 09-13: "a cold start after a task swipe shows Splash / auth first and the call layer appears once the route resolves", because the OS splash was held until `destinationResolved`). Cutoff and join-window logic live in `CallCenter`, not in the UI route.
- **Process killed during a call** (`CallResumeMarker`). `ClickMeApplication.kt:46` calls `callResumeMarker.start()`; a stored marker is routed through `pushLaunchRequest.destination.postIfAbsent(destination)` (`CallResumeMarker.kt:83`) as a `BookingDetail` with the Either audience, unless the booking is more than `CUTOFF_SECONDS = 3600L` past its scheduled end (`CallResumeMarker.kt:76,135`). This runs at process start, before the splash, so the cutoff test is unaffected by the 3 s. The user lands on the booking's detail screen where Join Call is the primary action; nothing joins automatically.
- **Push destination is held.** `MainActivity.kt:61-62` posts `intent.consumePushDestination()` into `PushLaunchRequest.destination`, a memory-only `OneShotSlot` ("It is memory only, so it survives the splash and the session restore but not a process death", `PushLaunchRequest.kt` doc). `PushRoutingViewModel` collects `combine(route, launchRequest.destination.pending)` and only consumes when `mode != null && pending != null`, where `mode` is non-null for `ClientHome`/`ExpertHome` only (`PushRoutingViewModel.kt` init block and `homeMode()`). On `Splash` neither branch runs, so the slot is retained; on `Login`/`SignupSetup` it is dropped, which is existing behaviour. A later `onNewIntent` tap replaces it (newest wins). Resolved routes wait in `ShellRouteRequest` until a shell of that mode is composed (`ShellRoute.kt` doc), and no shell is composed while the splash is on screen.
- **Navigation runs after the splash only if the splash is gated at the UI layer.** Because `AppViewModel.route` leaves `Splash` as soon as auth resolves (`AppViewModel.kt` `resolveInitialRoute`), a gate that only delays the visible content would let the push router start resolving at ~0.5 s. That is harmless for routing (the shell is not mounted) but would let `PushPermissionRequester` raise the system notification dialog, and the suspended-account dialog show, on top of the splash. Pass the **shown** route (Splash while held) to `PushRoutingHost`, `PushPermissionRequester` and the suspended-dialog condition.
- **Cost of D-09:** a resumed-call landing or a time-sensitive push opens up to 3 s later (plus any `/me` time beyond 3 s, capped at `SPLASH_HOLD_CAP_MS = 5_000L`). That is the accepted trade-off, not a failure.

**User decision needed: none blocking.** Two plan-level items worth a line in the plan, neither a call failure:
1. Same-process new activity (task swipe with a live call, user taps the ongoing-call notification): a per-activity `AppViewModel` would replay the whole 3 s splash even though the process is warm. UI-SPEC A10 says "not replayed ... when the activity is recreated in the same process"; storing the played flag only in `AppViewModel` does not deliver that. See "Splash design" for the process-level flag recommended.
2. `STATE.md` / UAT note: the call overlay will now be visible over the splash during auth. Verify on device in the Phase 16 matrix (the existing 09-13 note says only the pure intent test covers this path).

### Pattern 6 (Splash design)
```kotlin

const val SPLASH_MIN_DISPLAY_MS = 3_000L     // D-08 reversible constant, next to SPLASH_HOLD_CAP_MS
private val _splashComposed = MutableStateFlow(false)

    _splashComposed.value = true
    holdJob = viewModelScope.launch { delay(SPLASH_MIN_DISPLAY_MS); _splashHeld.value = false }

```

`MainActivity`: `splash.setKeepOnScreenCondition { appViewModel.keepSystemSplash() }` and `splash.setOnExitAnimationListener { it.remove() }` (UI-SPEC: remove immediately on API 31+).

Process-level "already played" flag (resolves disagreement 4): a small `@Singleton` (or `object`) holder, set when the hold starts. When already played, or when `MainActivity` sees `savedInstanceState != null` and the hold has not started in this VM, treat the hold as served: `_splashHeld = false`, `keepSystemSplash()` falls back to the old rule (`!destinationResolved.value`), and `AppRoute.Splash` renders `EmptySurface()` under the OS splash. This preserves today's behaviour for those launches and keeps D-08 "every launch path" for real cold starts.

- **Mixing the hold into `AppViewModel.route`:** breaks the existing VM tests and the push router's contract (`route` = resolved destination).

## Common Pitfalls

### Pitfall 1: Waiting for "first Compose frame drawn" deadlocks the system splash
**What goes wrong:** with `setKeepOnScreenCondition { !composeFrameDrawn }`, the app stays on the OS splash forever (or until the platform gives up).
**Why:** `Impl.setKeepOnScreenCondition` and `Impl31.setKeepOnScreenCondition` add an `OnPreDrawListener` to `android.R.id.content` that `return false` while the predicate is true, which cancels the draw [VERIFIED: core-splashscreen-1.2.0 `SplashScreen.kt:279-295` and `431-449`, quoted: `if (splashScreenWaitPredicate.shouldKeepOnScreen()) { return false }`]. No Compose draw can run until the predicate flips, so a predicate that waits for a draw never flips.
**How to avoid:** flip the signal at composition/layout (a `LaunchedEffect(Unit)` or `Modifier.onGloballyPositioned` in `SplashScreen`), which happens before the draw; the next traversal then draws the Compose splash and the OS splash is removed. The 3 s clock starts at that moment, a frame or two before the first visible frame (negligible).
**Warning signs:** device sits on the OS splash; JVM tests cannot catch it (no activity is launched in tests), so it needs the device matrix row.

### Pitfall 2: Join Call enabled on a cancelled booking (Question 1)
See Question 1. Warning sign: `UPCOMING_BOOKING_JOIN_TAG` exists for a `cancelled` detail.

### Pitfall 3: Duplicate `LazyColumn` keys
Rows are per booking, but paging across a changing ledger can repeat a row; a repeated key crashes `LazyColumn`. Dedupe on append (the expert VM does: `appendNew`).

### Pitfall 4: 500 on page 1 swallowed, or on page 2 shown
The rule is by **requested page**, not by position in the list. Pull-to-refresh and Retry are page 1 requests and must show errors; only `nextPage >= 2` swallows a 500 [VERIFIED: ClientTransactionsViewModel.swift `loadNextPageIfNeeded`: `if requestedPage > 1, case let NetworkError.httpError(status, _) = error, status == 500 { hasMore = false; return }`].

### Pitfall 5: `AutoSaver` debounce constant is not injectable today
`onEdited` uses the top-level `AUTO_SAVE_DEBOUNCE_MS = 1_200L` (`ProfileAutoSave.kt:20`). Without the new parameter Notifications would debounce at 1.2 s, not 0.8 s.

### Pitfall 6: Hydration triggers a save
If hydrate goes through `onEdited`, a PATCH fires after every first load (iOS bug). Use `rebase`.

### Pitfall 7: `AutoSaver.flush` is a no-op unless something changed
`flush()` returns when `latest == saved`. Toggling a row back to its original value within the debounce therefore sends nothing (an improvement, but tests must expect it).

### Pitfall 8: Splash side effects behind the Compose splash
`PushPermissionRequester` and `SuspendedAccountDialog` read the raw route / `showSuspendedDialog` and would appear over the splash at ~0.5 s. Use the shown route and gate the suspended dialog on `!held`.

### Pitfall 9: Details length counts
`details.trim().length` counts UTF-16 units, as `z.string().min(10)` counts JS string length [ASSUMED]. Client >= 10 trimmed implies the server's untrimmed-or-trimmed check passes because the client sends the trimmed text.

### Pitfall 10: Hub action data classes are positional
`ClientProfileHubActions` has 7 lambdas and `ExpertProfileHubActions` 9. Construction sites: `HomeClientScreen.kt:430`, `ClientProfileHomeScreen.kt:173` (preview `({}, {}, {}, {}, {}, {}, {})`), `HomeExpertScreen.kt:308`, `ExpertProfileHomeScreen.kt:184` (preview with nine `{}`), `ClientProfileHomeScreenTest.kt:45`, `ExpertProfileHomeScreenTest.kt:49`. Add the new callbacks with named arguments everywhere.

### Pitfall 11: Unknown `payment_status` and empty/`none` amounts
Unknown -> neutral "—" pill; `none` with `amount > 0` -> "Processed", otherwise "No payment" (CLIENT-TRANSACTIONS.md §4, iOS `statusLabel`). A 0 amount is not null: only null shows "—".

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Spoofed push/launch intent extras to the exported `MainActivity` | Spoofing/Tampering | Existing `PushEvent` UUID validation; the splash does not read the intent |
| Mass assignment via extra PATCH fields | Tampering | Request DTO has only the five documented keys |
| Joining a cancelled session (token issued without a status check) | Elevation/Abuse | Fail-closed `isWithinJoinWindow` (Question 1); server-side status check is a backend follow-up to log |
| Information disclosure in Payment History | Information disclosure | Server omits `payment_intent_id` and platform fees (CLIENT-TRANSACTIONS.md §9); render only returned fields |
| Double submit of feedback | Repudiation/DoS | `isSubmitting || sent` guard; server has no limiter on the route |
