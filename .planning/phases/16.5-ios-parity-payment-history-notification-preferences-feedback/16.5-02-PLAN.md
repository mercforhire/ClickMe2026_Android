<objective>
Make Upcoming Booking Details safe for every status Payment History can open it with, and make the cancel flow safe on the Profile stack, before any Payment History row exists.

Purpose: D-03 sends every row to Upcoming Booking Details. Today a cancelled paid booking inside its window shows an enabled Join Call, and the server does not backstop it: `POST /bookings/:id/join` checks the participant and the time window but never the status (`call.controller.js:57-71`). Payment History is the first surface that reaches this. It is also the first surface that opens the details and Cancel screens on the Profile stack, which `showMyBookings` deliberately does not reset. The leading tracer goes from the window rule to the card on screen.
Output: 4 modified main files, 3 extended test classes.
</objective>

Planner finding beyond RESEARCH, recorded here because it changes behavior: `showMyBookings` resets Explore, Search and Bookings but deliberately not the Profile stack (runbook row D1.FV4). A booking opened from Payment History can be cancelled, so without Task 2 the Profile tab would keep a Cancel screen for an already cancelled booking, with its bottom bar hidden. This is the same defect Phase 16.3 CR-01 fixed for Request Sent, and Task 2 uses the same helper. Deliberate trade-off, as in CR-01: after this cancel the Profile tab opens on the hub, not on Payment History, and the list reloads when reopened.

Why `StackOrigin.Profile` matters: `NavigationState.toDecoratedEntries` flattens the start stack with the selected one, so `UpcomingBookingKey(b1)` on Explore (a Today's Sessions card) and an equal key on Profile would be duplicate content keys and crash.

Backend follow-up, not code here: the server's join endpoint does not check `status`, so the client gate is the only status guard. Plan 16.5-12's SUMMARY lists it for the backend owner.
