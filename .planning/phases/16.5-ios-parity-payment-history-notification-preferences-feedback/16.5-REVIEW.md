## Warnings

### WR-01: Payment History can open a past confirmed booking that still offers Cancel Booking

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/upcomingbooking/UpcomingBookingUiState.kt:108` (rendered at `UpcomingBookingScreen.kt:456-473`)
**Issue:** D-03 requires that Upcoming Booking offers no live action on a booking where it can't apply. Plan 16.5-02 closed this for Join (`showsJoinCard`) and Reschedule (`canClientStartReschedule` already checks `end`). Cancel was left as `canCancel = status in CANCELLABLE_BOOKING_STATUSES` (`confirmed`, `pending_approval`, `pending_reschedule`), with no time check.

Payment History lists every payment attempt. It can therefore open a `confirmed` or `pending_reschedule` row whose session ended long ago, for example a session that happened but was never marked completed or missed.

Such a booking shows an enabled "Cancel Booking" button. I read `cancelBooking` in `clientBooking.controller.js` (about lines 800-850). It has only a status guard (`cancellableStatuses`) and no start or end time guard. So the server will cancel a past session, and the client UI now makes that one tap from the ledger.

Before this phase the screen was reachable only from Upcoming lists, which are time-filtered. I could not confirm what the refund preview shows for a past session.
**Fix:** Gate Cancel on the session not having ended, the same way Reschedule does. This needs `now` in the UI model. For example, compute it in `LoadedBody` next to `showReschedule`:
```kotlin
val canCancelNow = details.canCancel && (details.status.raw == STATUS_PENDING_APPROVAL || joinNow.isBefore(details.end))
if (showReschedule || canCancelNow) { /* ... */ }
// and use `if (canCancelNow)` for the Cancel button
```
Add a test next to `terminalStatusesShowNoLiveAction` for a `confirmed` booking whose `end` is in the past. First confirm with iOS and the product owner whether a past `confirmed` booking should be cancellable at all.

## Info

### IN-01: Cross-fade exit frames render the wrong or empty content for the error state

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/payments/ClientTransactionsScreen.kt:164-165`, `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/settings/notifications/NotificationSettingsScreen.kt:154`
**Issue:** Both screens read `state.load` inside the cross-fade content lambda instead of using the `kind` key. When the state moves from Failed to Loading or Loaded (Retry or pull-to-refresh), the outgoing Failed layer is composed during the 150 ms fade, but `state.load` is no longer `Failed`. In Payment History, `(state.load as? Failed)?.let { ... }` renders nothing, so the error layer vanishes instantly. In Notifications, `message?.asString().orEmpty()` renders the ErrorState with an empty body. This is a visual glitch only.
**Fix:** Keep the last failure message in a `remember`ed value, or make the cross-fade key the `state.load` value itself (it is a data class, so `Failed(message)` works as a key).

### IN-02: A recreation before the first composition permanently skips the Compose splash

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/AppViewModel.kt:101-106`
**Issue:** `onActivityRestored()` treats any `savedInstanceState != null` as a process restore when `holdJob == null`. A configuration change that recreates the activity before `onSplashComposed()` has run (rotation, locale or dark-mode toggle in the first frames) takes the same path, because the ViewModel and its `holdJob` are retained but still null. The hold is dropped, `splashPlayed` is set, and the user never sees the splash on that launch. The effect is harmless (the OS splash stays up until the route resolves), but it contradicts the KDoc's claim that the rotation case is a no-op.
**Fix:** Optional. Distinguish a retained ViewModel from a new one, for example with `splashComposed || holdJob != null` as the no-op condition, or drop the early return and only mark restored when `!isChangingConfigurations`.

### IN-03: The `AppViewModel` class KDoc describes the old splash release

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/AppViewModel.kt:35-37`
**Issue:** The first paragraph still says the splash "is released as soon as it answers, or after `SPLASH_HOLD_CAP_MS` at the latest". With this phase, the OS splash is released at the Compose splash's first composition. The route-resolution cap now only bounds how long the Compose splash can outlast the 3 s hold. The last paragraph is correct, so the two paragraphs contradict each other.
**Fix:** Reword the first paragraph to "the Compose splash is held for at least `SPLASH_MIN_DISPLAY_MS`, and never waits on auth longer than `SPLASH_HOLD_CAP_MS`".

### IN-04: The row date format ignores the locale's date ordering and is duplicated

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/payments/ClientTransactionLogic.kt:11,105-113`
**Issue:** `"MMM d, yyyy"` is hard-coded, so a `d MMM yyyy` locale such as en-GB or fr still gets month-first ordering. The same pattern and function body are copied from `EarningsTransactionRow.kt:45,97`, so a future change has to be made twice.
**Fix:** Use `DateTimeFormatter.ofLocalizedDate(FormatStyle.MEDIUM).withLocale(locale).withZone(zone)` in one shared helper. Check the tests that pin the English output first.
