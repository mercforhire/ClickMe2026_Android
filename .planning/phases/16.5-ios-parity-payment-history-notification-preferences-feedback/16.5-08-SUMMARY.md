# Phase 16.5 Plan 08: Payment History screen and row Summary

Payment History renders as a skeleton-first paged ledger with a merged-Button row (status pill, partial-refund line, dashes for unknowns) that reports its booking id on tap for every status.

## What was built

- **Task 1 (tracer):** `ClientTransactionsKey`, the Hilt `ClientTransactionsScreen`, the stateless `ClientTransactionsContent`, `ClientTransactionRow` with `ClientPaymentStatusPill`, and the title, empty, error and row strings. A loaded ledger shows in server order and a tap on any row (captured, canceled, failed, unknown status) reports its booking id.
- **Task 2:** Full state set per D-04: six-row skeleton (no spinner), scrollable-centered empty and failed states so pull works, refresh-failed snackbar with Retry, the last-3-rows `snapshotFlow` trigger, a "Loading more..." footer and an inline Retry page-error footer with stable keys, and silence at the end of the list.
- **Task 3:** Row details covered by tests: null topic/expert/amount dashes (row never dropped, no false zero), zero amount shown, partial refund line, unknown-status neutral dash pill, every pill label, one merged Button node with click label "Open booking" and the full spoken description, "unavailable" for missing parts, and a 360 dp long-text case where the amount stays inside the row.

## Deviations from Plan

**1. [Process] Task 3 logic was written during Task 1**
- The row file was written whole in the Task 1 commit (refund line, null handling, semantics, pill tints), because splitting it would have meant writing code only to rewrite it. Task 3's commit is therefore tests only; its behaviors passed on first run. RED was not run separately (the same approach as 16.5-01 and 16.5-05).

**2. [Rule 1 - Test] `rowTapReportsTheBookingForEveryStatus` first failed**
- The fourth row was below the Robolectric viewport. Fixed by `performScrollToNode` before each tap. Test-only change.

**3. [Plan wording] `pullWorksFromEmptyAndFailed` split in two**
- Implemented as `pullWorksFromEmpty` and `pullWorksFromFailed`, one state per test. Both cover the plan's behavior.
