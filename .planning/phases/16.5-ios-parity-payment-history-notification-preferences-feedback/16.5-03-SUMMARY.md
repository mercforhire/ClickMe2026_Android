# Phase 16.5 Plan 03: Compose splash stage Summary

A 3 s Compose splash after the OS splash, implemented as a hold on the route the UI shows (`shownRootRoute`), with the OS splash released at composition and the whole thing played once per cold process.

## What was built

- **Task 1 (tracer), commit d60f0bdf:** `SPLASH_MIN_DISPLAY_MS = 3_000L`, `splashHeld`, `onSplashComposed()` (idempotent, starts the delay once), and top-level `shownRootRoute(route, held)`. `ClickMeApp` feeds `AnimatedContent` the shown route; the `Splash` branch renders the new `SplashScreen` (mark, wordmark, tagline over the radial gradient, no `Scaffold`, no `BackHandler`). `AppViewModel.route` and `destinationResolved` keep their meaning, so every pre-existing AppViewModelTest case passes unchanged. Auth still starts in `init`, so it runs alongside the 3 s.
- **Task 2, commit fb14d7bd:** `keepSystemSplash()` and `MainActivity` wiring: `setKeepOnScreenCondition { appViewModel.keepSystemSplash() }` and `setOnExitAnimationListener { it.remove() }`. `PushRoutingHost`, `PushPermissionRequester` and the suspended dialog (`showSuspendedDialog && !held`) see the shown route, so a push destination or resumed-call destination stays in its slot until a home route is shown, and a logged-out tap drops only when Login is actually shown.
- **Task 3, commit 637a390c:** `SplashPlayedFlag` singleton, constructor parameter with a default on `AppViewModel`, `showsAnimatedSplash`, `onActivityRestored()` called from `onCreate` when `savedInstanceState != null`. A served or restored launch shows `EmptySurface` under the OS splash and keeps the old keep condition (`destinationResolved`).

## Decisions to call out for UAT

1. **Process restore is treated as already served** (CONTEXT discretion, resolved as RESEARCH recommends). A launcher tap after the system killed a background app can restore the task this way; it then shows only the OS splash until the route resolves, as today. The user can overrule this at UAT.
2. **D-09 wording corrected:** "a call keeps ringing" describes something that does not exist on Android or iOS (no ringing or incoming-call concept in `app/src/main`). The real effect is added latency only, with no bypass; `CallOverlayHost` still wraps the route switch so an in-progress call stays live. CONTEXT's "Phase 11 and 12" test note should read Phase 9 and 13.
3. A rotation that happens before the splash first composes is also treated as restored (holdJob is still null); this is an extremely narrow window and resolves to today's behavior.
