<decisions>
## Implementation Decisions

### Notification preferences
- **D-01: No quiet hours.** `NotificationSettingsView.swift` never instantiates `NotificationQuietHoursCard` (0 references), so iOS users don't see it, and the backend has no quiet-hours field (`notificationPrefs.controller.js`, `notificationPrefs.schema.js`). The audit's open question is answered: quiet hours aren't stored anywhere. This corrects the roadmap goal and the audit's description of #5.
- **D-02: A failed auto-save shows an inline status with Retry, reusing `AutoSaver`** (`screens/settings/clientprofilesettings/ProfileAutoSave.kt`): Saving, Saved and Error in the top bar. Toggles stay as the user set them. Deliberate deviation: iOS shows a "Couldn't save preferences" alert with no retry.
- **Carried from iOS:** 0.8 s debounce, coalescing rapid flips into one trailing PATCH; the PATCH sends every rendered row. One master toggle per row sets `push_enabled`, `email_enabled` and `in_app_enabled` together; on load a row is on if any channel is on, and a missing row defaults to on. Sections and keys per `NotificationSettingsViewModel.defaultSections`: Bookings (`booking`: requests, confirmations, declines, cancellations, reschedules, expirations, refunds), Sessions (`session`: reminder, no_show, ended), Messages (`message`: new_message), Reviews (`review`: received, nudge). Category keys are singular. `payout`, `account` and `promotions` rows aren't shown and are never sent. TopAppBar title "Notifications".

### Payment History
- **D-03: A row tap opens Upcoming Booking details for every row, as on iOS**, including past, cancelled and failed bookings (`ClientTransactionsView.swift:71-79`). Research must confirm that `UpcomingBookingScreen` handles those states sensibly and offers no live action (Join, Reschedule) on a booking where it can't apply. If it doesn't, fixing that is in scope.
- **D-04: Loading and errors follow the Phase 15 standard:** skeleton on first load, inline `ErrorState` with Retry, and pull-to-refresh that keeps rows visible, with `RefreshFailedSnackbar` when a refresh fails over loaded rows. Deliberate deviation: iOS shows a centered spinner and clears the list on reload.
- **Carried from iOS and the spec (`CLIENT-TRANSACTIONS.md`):** page size 20; the next page loads when a row within the last 3 appears; page forward on `has_more` only. A 500 on page 2 or later is end of list and shows nothing; a 500 on page 1 is a real error. Other next-page failures show a small inline Retry footer and keep loaded rows. Amounts are minor units, with decimals taken from `currency`, not a hard-coded 2. A null `amount` shows "—", not "$0.00". `payment_status` stays a raw string with the transaction endpoint's own 11-value mapping: **never share the enum from `/client/bookings/:id`**, and an unknown value must not break decoding. `refunded_at` is always null. A null topic shows "—" and the row stays.

### Send Feedback
- **D-05: Details are validated up front at 10 characters after trimming.** Send with fewer shows an inline error stating the minimum, with no server call. The backend's `details: z.string().min(10)` is the source of the rule. A 422 still maps to its field as a fallback. Deliberate deviation: iOS blocks only empty text.
- **D-06: After a successful send, show a Material `AlertDialog` with the iOS thanks copy; OK returns to the profile hub.** Title "Thanks for your feedback!", body "We really appreciate you taking the time to help us make ClickMe better." Deliberate deviation: iOS stays on a cleared form.
- **Carried from iOS:** types come from the server, never hard-coded (the iOS preview samples differ from the backend list), and the first type is preselected. Email is prefilled from the signed-in user if empty, trimmed, and omitted when empty (the backend's `email` is optional but must be valid when present). Details are sent trimmed. A types-load failure shows the error state with Retry. 429 shows "Too many attempts. Please try again in a moment." Other failures show the server message in a dialog, falling back to "Couldn't send your feedback. Please try again." The form is kept on failure. Repeated taps are ignored while sending. TopAppBar title "Send Feedback".

### Splash
- **D-07: Add an iOS-style splash screen after the system splash**, on every Android version: radial dark background, the mark with a pulsing glow, "ClickMe" wordmark, "Book time with the best minds." tagline. Port `SplashView.swift` timings: logo fade and scale from 0.82 over 0.7 s ease-out, text fade over 0.6 s after a 0.35 s delay, glow pulse 1.6 s ease-in-out repeating. The system splash stays (Android requires it), so users see two stages; make the handoff as seamless as is practical.
- **D-08: The screen shows for a fixed 3 s on every launch path**, matching `SplashViewModel` `displaySeconds = 3.0`. — **Reversibility:** reversible — a duration constant and a route gate.
- **D-09: Push taps and incoming calls get no bypass: the full 3 s always shows.** The user chose this knowing the risk below.
  - **Known risk, research must check:** a cold start from an incoming call or a time-sensitive push sits behind the splash for up to 3 s. Trace `consumeExpandCallExtra` and `consumePushDestination` in `MainActivity.kt`, `CallCenter` and `PushLaunchRequest`. Confirm that a call keeps ringing and can still be answered, that the push destination is held rather than lost, and that its navigation runs after the splash. If a call can actually be missed or fail, raise it to the user at planning instead of silently bypassing or shipping it.
  - Also check Phase 11/12 call and push tests that assume no fixed delay, plus any instrumented or Robolectric test that launches `ClickMeApp`.

### Before-you-go card
- **D-10: Don't build the Pause Account card.** On iOS its action defaults to `{}` and `AccountSecurityView.swift:207` never passes one, so tapping does nothing, and the backend has no pause route. A dead control or an unkeepable promise doesn't belong on the Delete Account screen. Deliberate deviation, as the audit recommends.

### Claude's Discretion
- Whether auth resolution runs alongside the 3 s or after it, as on iOS. Running alongside avoids stacking a slow `/me` on top of the wait; the screen must stay up at least 3 s either way. Keep the existing `destinationResolved` behaviour correct, including the logged-out path and the offline cached path.
- Whether the splash also shows on configuration change or on process restore (it should not replay on rotation).
- Reduced-motion handling for the glow pulse, following Phase 15.
- Notification screen first-load, retry and refresh visuals per Phase 15; flushing a pending debounced save when leaving the screen, using `AutoSaver.flush` so a last-moment toggle isn't lost.
- Row visuals: port `ClientTransactionRow.swift` (status pill tints) and the iOS empty state; the header total count if iOS shows it.
- Feedback layout using `PickerSheet` / `PickerField`, `ValidatedField` and `AsyncSaveButton`, per the audit.
- Hub placement follows iOS. Client: Account gets Payment History after Payment; a new Preferences section holds Notifications; Support gets Send Feedback after FAQ & Help. Expert: same Preferences and Support additions, no Payment History. The iOS "Privacy" row isn't part of this phase.
- Repository shape, DTO and Retrofit naming, key names, entry registration, fakes, fixtures and string names, following the file-organization rule (`screens/clientmode/payments/`, `screens/settings/notifications/`, `screens/settings/feedback/`, `screens/splash/`).
- Test coverage. JVM tests are expected for: the 500-past-end rule (page 1 vs later pages), paging triggers and single-flight, minor-unit formatting and null amounts, unknown payment status, preference hydration with singular keys and defaults, debounce coalescing, the save failure and retry path, feedback validation at 9/10 trimmed characters, 422 and 429 mapping, the thanks dialog returning, and the splash's 3 s gate on normal, push and call launches.

</decisions>
