# Phase 16.2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope.** PARITY-AUDIT #10 and #11. Android can only respond to a reschedule today; this phase lets the client and the expert start one. Five surfaces:
> 1. The shared **Reschedule picker** (one layout, a client route and an expert route).
> 2. The **payment-conversion disclosure** dialog and the **error and saved-card recovery dialogs** that sit on the client picker.
> 3. The **client entry points**: a Reschedule button next to Cancel on Upcoming Booking Details, and next to Message on My Bookings upcoming cards.
> 4. The **expert entry points**: a Reschedule button next to Cancel on Expert Booking Summary, and on expert upcoming cards. Both are gated by `actions.can_reschedule`.
> 5. The **return path**: pop to the origin screen, refresh it, and show a "Reschedule request sent" snackbar (D-09, D-10).
>
> Out of scope and must not appear: accept and decline UI (shipped in Phases 8 and 11), any backend change, any gating of slots by `authorization_expires_at` (locked, non-gating), a SetupIntent or card-entry sheet inside the picker.
>
> **Baseline.** `01-UI-SPEC.md` (tokens, shapes, motion), `06-UI-SPEC.md` (Make a Booking calendar, slots, notes, book button), `07-UI-SPEC.md` (Payment Methods) and `08-UI-SPEC.md` (Reschedule card and dialogs, destructive color rule) are locked and not restated. Dark only, Material 3, Nunito 400 / 600, exactly four text sizes (12 / 16 / 20 / 28 sp), `Spacing` xs..xxxl, `ClickMeShapes`, `MaterialTheme.extras`. Every value below is an existing token unless marked "(new)".
>
> **Design source.** Google Stitch is not accessible. The stand-in is the iOS code: `Client Mode/Reschedule/**`, `Expert Mode/Reschedule/**`, `UpcomingBookingSecondaryActions.swift`, `UpcomingBookingCard.swift:270-274`, `UpcomingBookingsSessionCard.swift`, `ExpertBookingSummaryView.swift:194-215`. The iOS `RescheduleBrand` palette (#131318 bg, glass-dark cards, orange "current" accents, green glow) collapses to the Phase 1 tokens: orange becomes `tertiary`, glows are dropped. Copy is iOS verbatim unless marked "(Android)". Layout is ported, not pixel-matched.
>
> **Source of decisions.** CONTEXT D-01..D-15 for everything listed there. This spec fills "Claude's Discretion": the shared-picker composition, screen chrome, loading and error states, message-card limit, button styles and placement, string names, and the dialog copy that CONTEXT does not fix. Assumptions are recorded under "Assumptions and Open Items".

## Spacing Scale

Phase 1 tokens, all multiples of 4: xs 4, sm 8, md 16, lg 24, xl 32, xxl 48, xxxl 64.

| Token | Used for in this phase |
|-------|------------------------|
| xs (4dp) | Gap between a card's name line and its sub-line; gap between the chip label and its "Current" caption; calendar day vertical padding (inherited) |
| sm (8dp) | Gap between the section header and the message field; gap between chips; icon-to-text gap in the banner and buttons; gap between stacked dialog fields |
| md (16dp) | Screen horizontal padding (iOS 20); gap between every block on the picker (iOS 16); card inner padding (iOS 14); avatar-to-text gap; gap between the two buttons in the Reschedule + Cancel / Reschedule + Message rows; banner horizontal padding |
| lg (24dp) | Top padding under the app bar on the picker (matches Make a Booking); gap above the Reschedule + Cancel row (matches the standalone Cancel gap) |
| xl (32dp) | Bottom scroll padding on the picker (plus the navigation-bar inset); empty and error spacing (inherited) |
| xxl (48dp) | Minimum touch target: calendar day cell, month arrows, slot chip |
| xxxl (64dp) | Not used |

Exceptions (component dimensions and platform minimums, not layout spacing):
- Touch targets stay at least 48dp: calendar day cells 48 high (circle 36, inherited), month arrow `IconButton` 48, slot chips `heightIn(min = 48.dp)` (grows to two lines for the Current chip), dialog buttons, Retry.
- Controls (Submit Reschedule Request, Reschedule, Cancel Booking, Message) use `heightIn(min = 56.dp)` (inherited; iOS 44 to 54).
- Avatar 56dp (matches Make a Booking expert card; iOS 60).
- Open-day dot 4dp (inherited). Stroke widths 1dp resting, 2dp focused (hairlines).
- Message field `minLines = 4` (inherited).
- Skeleton shapes copy the real component dimensions.

## Color

Dark only. All colors come from the Phase 1 ColorScheme and `MaterialTheme.extras`. No hex literal appears in this phase's code (`scripts/check-design-rules.sh`). Tinted fills are `color.copy(alpha = ...)` of a scheme color.

| Role | Value | Usage in this phase |
|------|-------|---------------------|
| Dominant (60%) | `#131313` `surface` | Picker background, app bar |
| Secondary (30%) | `#1C1B1B` `surfaceContainerLow` and `#201F1F` `surfaceContainer` | Booking card, calendar card, slots card: `surfaceContainerLow`, `medium`, 1dp `outlineVariant`. Message field fill: `surfaceContainer`. Dialogs: `surfaceContainerHigh`. Reschedule action button fill: transparent with a 1dp `outline` border (same as `MessageButton`) |
| Accent (10%) | `#44F697` `primary` | See reserved list |
| Warning / current | `#FFB833` `tertiary` | Current-session banner (fill 10% alpha, 1dp border 45% alpha, icon `tertiary`, text `onSurface`), the "Current" slot chip (1dp border `tertiary` 55% alpha, caption `tertiary`, label `onSurface`). Replaces iOS orange |
| Destructive | `#FFB4AB` `colorScheme.error` | Only the existing Cancel Booking button beside the new Reschedule button. Nothing on the picker is destructive. Never a filled error button |

Accent reserved for (and nothing else in this phase):
1. Fill of the single primary CTA on the picker: "Submit Reschedule Request". Disabled it uses the disabled container, not the accent. "Retry" on the load-error state (via `EmptyStateAction`).
2. Fill of the selected day circle and the selected slot chip (with `onPrimary` text).
3. The 4dp open-day dots under days that have a selectable slot.
4. Focused border and cursor of the message field, and every `CircularProgressIndicator` (the submit spinner).
5. The "Continue" text button in the disclosure dialog and the "Add a Payment Method" text button in the payment-method dialog (the single primary action of each dialog).

Neutral, deliberately not accent: the Reschedule action buttons (outlined, `onSurface`), month arrows, today's ring (`outline`), the timezone and paid-window notes (`onSurfaceMuted`), the disabled (past-limit) days and chips (`onSurface` at 38% alpha).

Contrast: `onPrimary` on `primary` 9.3:1; `tertiary` on `surfaceContainerLow` about 9.5:1; `onSurface` on `surfaceContainerLow` above 12:1; `onSurfaceMuted` on `surfaceContainerLow` at least 5.9:1. Disabled content (past-limit days and chips) is exempt but stays legible. Status is never conveyed by color alone: the Current chip carries the word "Current", the banner carries the words "Current:", and past-limit chips are explained by the visible paid-window note plus a "Unavailable" state description.

## Motion

Phase 1 durations. All of it follows the system animator duration scale.

| Interaction | Duration / easing |
|---|---|
| Push / pop of the picker | Phase 1: horizontal slide + fade, 300 ms (`Motion.PUSH_POP_DURATION_MS`, `pushPopEasing`); predictive back drives pops (disabled while a submit is in flight) |
| Month change | 150 ms cross-fade of the grid (`Motion.CONTROL_STATE_DURATION_MS`, inherited from the calendar) |
| Day and chip selection colors | 150 ms `animateColorAsState` (inherited) |
| Current-session banner appearing | None (present from the first loaded frame) |
| Button press | Phase 1 press scale 0.96, 120 ms (`PressScaleButton`) |
| Submit label to spinner | Immediate swap inside the same footprint; the button never changes size |
| Loading to content | 150 ms cross-fade |
| Pending-reschedule state after returning to the origin | The origin's own 200 ms `AnimatedVisibility` (`Motion.STRENGTH_METER_VISIBILITY_MS`) swaps the Reschedule button for the "Awaiting expert's response" card |
| Snackbar | Material default, short duration |

No dimming of the form while a submit is in flight (Make a Booking pattern, not iOS's 0.55 opacity): controls stop responding and the Submit button shows the spinner.

## Navigation and Structure

```
Client shell (HomeClientScreen entryProvider):
  RescheduleKey(bookingId)         BottomBar.hidden()
Expert shell (expert entryProvider):
  ExpertRescheduleKey(bookingId)   BottomBar.hidden()
  (keys are @Serializable NavKey data classes, registered next to UpcomingBookingKey / ExpertBookingSummaryKey)

Origins (any of):
  Client:  Upcoming Booking Details  >  RescheduleKey
           My Bookings upcoming card  >  RescheduleKey
  Expert:  Expert Booking Summary     >  ExpertRescheduleKey
           Expert upcoming card       >  ExpertRescheduleKey
  RescheduleKey  >  PaymentMethodsKey (Phase 7), client only, from the recovery dialog
```

| Screen | App bar | Back behavior |
|---|---|---|
| Reschedule picker (client and expert) | `AuthTopAppBar`, title "Reschedule" (iOS `navigationTitle`), back arrow ("Back") | Pops to whichever screen pushed it. While a submit (including the saved-card retry) is in flight, system Back and the arrow are ignored and the arrow is disabled (`backEnabled = false`), because cancelling could hide a request the server already created. With edits made and no submit in flight, Back pops without a discard prompt |

**After a successful send (D-09, D-10).** Pop the picker to the screen that opened it (not the root, a deliberate deviation from iOS). The origin screen refreshes quietly so the "Reschedule pending expert's / client's response" state shows, and then shows a `Snackbar` "Reschedule request sent". The refresh trigger and the one-shot snackbar notice are carried the same way for all four origins (for example a one-shot field on the shared client / expert state read by the origin on resume), not as a nav result, so a recreated origin still shows it once. Plumbing is Claude's Discretion.

**Back from Payment Methods to the picker (D-08).** The picker is a covered entry, so its ViewModel state (date, slot, message, displayed month) survives. Nothing is retried automatically; the client taps Submit Reschedule Request again.

**Date and slot state on the stack.** Displayed month, selected date, selected slot start, message text and dialog flags are saved across rotation and process death (`SavedStateHandle` / `rememberSaveable`). In-flight network calls complete in the ViewModel; if the screen is gone when the call returns, the result is dropped silently except a success, which still triggers the origin refresh and snackbar notice.

Insets: pushed screen uses `safeDrawing`; the scroll column uses `imePadding` and `xl` bottom padding plus the navigation-bar inset, as Make a Booking. A tap outside the message field clears focus; a user drag clears focus (inherited behavior).

## Screen Specifications

### 1. Reschedule picker (client and expert, D-01, D-02, D-03, D-11, D-12, D-14, D-15)

Background `surface`. Scaffold with `AuthTopAppBar` ("Reschedule"). Scroll column capped with `contentMaxWidth()`, `md` horizontal padding, `lg` top padding, `md` between blocks, `xl` plus nav-inset bottom, `imePadding`.

| State | Rendering |
|---|---|
| Loading (booking detail, then the displayed month) | `SkeletonGroup` (description "Loading") copying the blocks: booking card 88dp, calendar card 360dp, slots card 168dp, message field 144dp, button 56dp. `md` gaps |
| Failed (booking detail) | `EmptyState` (`Outlined.ErrorOutline`): heading "Couldn't load booking", body = server message, else "Check your connection and try again.", action "Retry" (filled; re-runs the load). `liveRegion = Polite`. The app bar and Back stay |
| Loaded | Blocks below, in this order |
| Slot load failed (a month's availability) | The calendar renders with no open-day dots; the slots card shows `SectionError` (message, Retry) in place of the chips (`AvailabilityState.Failed`). The rest of the form stays usable and Submit stays disabled until a slot is selected |

Blocks, in order:

1. **Booking card** (`BookingExpertCard`). `surfaceContainerLow`, `medium`, 1dp `outlineVariant`, `md` padding. `Avatar` 56dp, `md`, column: name `titleMedium` `onSurface` (`maxLines = 2`), subtitle `bodyLarge` `onSurfaceMuted` (`xs` below; `maxLines = 2`), then `xs` below the current date and time `bodySmall` `onSurfaceMuted` ("{short date} · {time range}", iOS "Wednesday, July 10 • 10:00 AM - 10:30 AM", built with `formatShortDate` and `formatSessionTimeRange` in the device zone and time format). Client side: name = the expert's name, subtitle = the expert's title, else the topic title. Expert side: name = the client's name (fallback "Client"), subtitle = the topic title (fallback "Session"), per iOS `ExpertRescheduleViewModel.map`. Server text is plain `Text` only. Not clickable.

2. **Calendar card** (`BookingCalendarCard`, shared, no change in look). Month row with Previous and Next arrows, weekday header, 7-column grid of 48dp day cells. Behavior specific to this phase:
   - Opens on the month and day of the current booking (D-12): `displayedMonth` and `selectedDate` are seeded from the booking's start in the device zone. The time slot stays unselected.
   - Days before today are dimmed (38% alpha) and not selectable; the Previous arrow is disabled at the current month (inherited rules).
   - A 4dp `primary` dot marks a day that has at least one selectable slot (available, not held, starts after now, not the current slot, and within the paid limit when it applies). Forward navigation has no limit.
   - **Paid limit (D-01, D-02, D-03).** For a paid booking, days beyond now + 6 days stay selectable and visible exactly as in Make a Booking (they just show no dot), and their slot chips are dimmed and not tappable; the slots card shows the paid-window note (below). Free bookings have no limit and no note. A start exactly 6 days out is selectable (`PAID_BOOKING_MAX_LEAD`, inclusive boundary).
   - **`authorization_expires_at` never disables, dims or hides a day or a chip.** It only decides the disclosure dialog.
   - Choosing a different day clears the selected slot (iOS `select(date:)`). The chosen day is kept when the month changes.
   - Day semantics are inherited ("Today, Selected, Available").

3. **Current-session banner** (`CurrentSessionBanner`, D-12). Directly above the slots card (iOS order). Tinted row: `tertiary` 10% fill, 1dp `tertiary` 45% border, `small`, `md` horizontal and `sm` vertical padding, `Outlined.Update` 16dp `tertiary`, `sm`, text "Current: {Wed, Oct 28 · 2:00 PM}" `labelMedium` `onSurface` (`formatProposalSlot`, device zone and format), wraps to two lines at large font scale. Full width. Shown whenever the booking start is known (always, once loaded).

4. **Time slots card** (`BookingTimeSlotsCard`, shared, `title` = "Available Time Slots" as Make a Booking; see Assumptions A-3 for the iOS "Time Slots" difference). Contents top to bottom, `sm` between: card title `titleMedium` (heading), selected date line `bodyLarge` `onSurfaceMuted`, timezone note `bodySmall` (existing `timezoneNote` copy, client side uses the expert's `expert_timezone`; the expert picker passes the expert's own zone, so it reads "Times are in your time zone (EDT)." with no second clause), the paid-window note (paid bookings only), then the chips or an empty line.
   - **Chips.** The inherited pill chips in a `FlowRow` (`sm` gaps, `selectableGroup`). Selected: `primary` fill, `onPrimary` `titleMedium` label. Selectable: transparent, 1dp `outline` border, `onSurface` `bodyLarge`. Past-limit or unavailable (held): dimmed 38% alpha, not tappable, `stateDescription` "Unavailable".
   - **Past slots are hidden (D-12, deviation from Make a Booking, which dims them).** Slots whose start is not after now are removed from the list (`hidePastSlots`). If that leaves the day empty, show the empty line.
   - **Current slot (D-12).** If the response contains the booking's current start (compared to the second), its chip is shown but cannot be picked: 1dp `tertiary` 55% border, label `onSurface` (full strength, not dimmed), and a second line "Current" in `labelMedium` `tertiary` (`xs` below the label). `stateDescription` "Current session time". It never becomes selected, and a programmatic attempt to select it is ignored (guard in the ViewModel). If the response omits the current slot, no chip is synthesized; the banner above still anchors the user.
   - **Paid-window note.** `bodySmall` `onSurfaceMuted`, test tag `reschedule_paid_window_note`, text "Paid sessions can be rescheduled up to 6 days ahead." (Android, same wording family as the server message and as Make a Booking's note). Shown only for paid bookings.
   - **Empty day.** `bodyLarge` `onSurfaceMuted`: "No available slots on this day." (iOS and Make a Booking wording).
   - **Day outside the loaded window** (kept across month moves): "Pick a day to see its available times." (existing `make_a_booking_pick_a_day`).
   - **Loading** a month: the existing four skeleton chips. **Failed**: `SectionError` with Retry (a failed month shows only for the displayed month, as in Make a Booking).
   - Slots are fetched lazily per displayed month (and its two neighbours), regrouped client-local by the device zone with `groupSlots`, from `GET /experts/:id/availability`. The client picker uses the booking's expert id; the expert picker uses the signed-in expert's own id (D-14).

5. **Message** (`SectionHeader` + `BookingNotesField`). Header "Message Text (optional)" (iOS verbatim, `SectionHeader` style), `sm`, then the multi-line field with the Phase 6 styling (`surfaceContainer` fill, `medium`, 1dp `outline` border, 2dp `primary` focus border, `minLines = 4`), `bodyLarge` text, capped at 500 characters (`capNotes`, `NOTES_MAX_CHARS`; iOS has no cap, 500 matches the Make a Booking and decline fields), counter "{n}/500" `bodySmall` `onSurfaceMuted` at the end. Placeholder `bodyLarge` `onSurfaceMuted` (Android; iOS repeats the header text): client "Let the expert know why you'd like to move this session."; expert "Let your client know why you'd like to move this session." The text is trimmed on submit and omitted when blank (D-15). Read-only while a submit is in flight.

6. **Submit Reschedule Request.** `PressScaleButton` filled (`filledColors()`), full width, `heightIn(min = 56.dp)`, `CircleShape`, label "Submit Reschedule Request" (`labelLarge`; iOS verbatim), test tag `reschedule_submit`.
   - Disabled until a slot is selected (iOS `selectedTime == nil`): disabled container, `stateDescription` "Choose a new time first" (Android).
   - In flight (including the PAYMENT_METHOD_REQUIRED card lookup and the single retry): keeps the enabled fill, shows a 24dp `onPrimary` spinner (2dp stroke) in place of the label, `stateDescription` "In progress" (`a11y_in_progress`), taps ignored. The calendar, chips, message field, Back and the app-bar arrow stop responding; nothing is dimmed. iOS's "Submitting…" text is dropped in favor of the Make a Booking spinner-only pattern.
   - On tap: if the booking's call is live, the existing live-call guard (the same one Cancel uses) blocks it with the same notice, wording "reschedule this session" in place of "cancel" (iOS `attemptModifyBooking`). Then, if a disclosure applies (client only, D-11), open the disclosure dialog; otherwise submit.

7. **Client-only disclosure and recovery dialogs** (surface 2).

### 2. Dialogs on the client picker

All are Material `AlertDialog`, `surfaceContainerHigh`, `extraLarge` shape, title `titleLarge`, message `bodyLarge` `onSurfaceVariant` (scrolls if tall), buttons `labelLarge`. Dialog flags are `rememberSaveable`.

| Dialog | Spec |
|---|---|
| Payment-conversion disclosure (D-11, client only) | Shown on Submit, before any request, when the proposed session end is after `authorization_expires_at` (end = start + the original booking's duration, else the slot's `end_utc`; D-11 amended 2026-10-31). Title "Your card hold will be released" (iOS alert title). Message: "Because you're moving this session more than a few days out, we'll release the current payment hold on your card and instead charge it automatically about 24 hours before your new session time. You won't be charged today." When the proposed start is under 48 hours from now, append after a blank line: "If your new session is coming up soon, your card may be charged sooner than 24 hours from now." (reuse `reschedule_accept_dialog_charges_soon`). Buttons: dismiss `TextButton` "Cancel" (`onSurface`, leaves the picker untouched); confirm `TextButton` "Continue" (`primary`, submits). Never shown when `authorization_expires_at` is null (free, long-lead, captured). The expert picker never shows it (the expert is not charged) |
| Payment method needed (D-06) | The existing `PaymentMethodDialog`. Used for PAYMENT_METHOD_REQUIRED with an empty saved-card list. Title "Add a payment method". Message (new, Android): "Please add a payment method before rescheduling this session." Buttons: dismiss "Not now" (`onSurface`), confirm "Add a Payment Method" (`primary`), which opens `PaymentMethodsKey`. The existing accept-flow message says "before accepting this reschedule" and must not be reused here, so `RescheduleOutcomeDialog` / `PaymentMethodDialog` takes a message override or a propose-specific `RescheduleDialog` variant |
| Card could not be used (D-06, D-07) | Same two-button dialog. Used for a second PAYMENT_METHOD_REQUIRED after the single silent retry. Message (existing `reschedule_card_unusable_message`): "The card on file can't be used for this reschedule. Please add a new payment method and try again." |
| Errors | `AuthErrorDialog`, title "Couldn't reschedule booking" (iOS verbatim), one "OK", message per the Copywriting Contract. The picker stays on screen with the date, slot and message intact unless the table says otherwise |

**Recovery sequence the UI must show (D-06, D-07, D-08).** Submit shows the in-flight state throughout. On PAYMENT_METHOD_REQUIRED the app loads the saved cards (`GET /me/payment-methods`): a failed load shows the "Couldn't reschedule booking" error with "Couldn't check your saved payment methods. Please try again."; an empty list shows the Payment method needed dialog; otherwise it retries once, silently, with the default card (else the first), never showing the card id. A second PAYMENT_METHOD_REQUIRED shows the Card could not be used dialog. There is no loop and no picker for the card. Returning from Payment Methods does not retry.

## Interaction Contract (summary)

| Rule | Behavior |
|---|---|
| Opening | Tap Reschedule pushes the picker with the booking id. The picker loads the booking detail, then the month of the current booking. Only the first load shows a skeleton |
| Selecting | One day and one slot at a time. Changing the day clears the slot. The current slot, held slots, past slots and (paid) past-limit slots can never be selected |
| Local validation | No slot: Submit is disabled. Current slot: refused locally with "Please choose a different time than the current session." (unreachable through the UI, kept as a guard) |
| Disclosure (client) | Submit with a conversion-triggering slot opens the disclosure dialog first. Cancel leaves everything as it is. Continue submits once |
| One request at a time | While in flight a second tap does nothing; Back is blocked; the form is locked |
| Saved-card recovery | One silent retry at most; empty list or repeat failure opens the Payment method dialog; nothing retried after Payment Methods (D-08) |
| Not optimistic | The origin changes only after the quiet refresh that follows the pop. Nothing flips before the server answers |
| Success | Pop to the origin, quiet refresh, snackbar "Reschedule request sent" (both sides, D-09, D-10) |
| Failure | The relevant dialog; the picker keeps its selections except where the table in the Copywriting Contract says to clear the slot or leave the screen |
| Rotation / process death | Entry-scoped Hilt ViewModels with `SavedStateHandle`: booking id, displayed month, selected date, selected slot start, message and dialog flags are restored |
| Time passing | The clock is re-read on resume (`refreshClock`). A selected slot that has started meanwhile is cleared; a slot that has passed the paid limit is not re-evaluated until the next selection, and the server backstop (RESCHEDULE_TOO_FAR_AHEAD) covers the gap |

## Accessibility Contract

- Touch targets at least 48dp: day cells, month arrows, slot chips, dialog buttons, Retry. Controls are 56dp.
- The booking card reads as one group: "{name}, {subtitle}, {date}, {time range}". The current-session banner is announced as text with its icon decorative (`contentDescription = null`).
- The calendar and slots card keep their inherited semantics: month label is a heading and a polite live region, days announce "Today, Selected, Available", the slots title announces the count when a day is chosen. Each is its own traversal group so a swipe does not wander between them.
- The Current chip is focusable and disabled, with `stateDescription` "Current session time"; past-limit and held chips say "Unavailable". The paid-window note is plain text in reading order directly after the timezone note, so a screen reader hears why chips are dimmed.
- Submit exposes `stateDescription` "Choose a new time first" while disabled and "In progress" while in flight. Loading and error states use `liveRegion = Polite`.
- Dialogs are announced by the platform; focus returns to the Submit button when a dialog closes. Error dialogs do not move focus into the form.
- The Reschedule action button has `contentDescription` "Reschedule session with {name}" on cards (the label alone on the details screens) and its own `testTag` per entry point (`upcoming_booking_reschedule`, `booking_card_reschedule`, `expert_summary_reschedule`, `expert_bookings_reschedule`).
- 200% font scale: the booking card text wraps (`maxLines = 2`), the banner wraps to two lines, chips wrap in the `FlowRow` and the Current chip grows to two lines, the Reschedule + Cancel and Reschedule + Message rows stack, dialogs scroll. Check the picker with a paid booking (note visible), a Current chip, the disclosure dialog, and the details screen with both buttons.
- A full TalkBack pass is out of scope (Phase 15 owns it); this phase must not regress the inherited calendar semantics.
