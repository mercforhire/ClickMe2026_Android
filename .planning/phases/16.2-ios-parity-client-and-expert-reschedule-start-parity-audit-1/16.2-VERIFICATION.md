### WR-04 assessment

WR-04 (`canClientStartReschedule` is a deny-list, so Reschedule shows on `cancelled`, `declined`, `expired` and similar when the details screen reloads into that status) is real in the code but does not undermine the goal. It is advisory, for these reasons:

- The goal is "start a reschedule as on iOS". iOS has no status gate at all on the details screen (`UpcomingBookingView.swift` always renders `UpcomingBookingSecondaryActions`). The user decided on 2026-11-01 to match iOS and hide only while pending. The deny-list is that decision, not a regression from it.
- Reaching the state needs a realtime `BookingUpdate` moving the booking to a terminal status while the client has the details screen open. The upcoming-list entry points never list terminal bookings.
- It fails safe. Nothing is sent without a Submit tap, the server refuses a dead booking with `INVALID_STATUS`, and the D-13 mapping turns that into the leave dialog.
- Cost: a dead booking briefly offers a button that cannot succeed, and `canCancel` is already false on that screen, so the inconsistency is visible. A small allow-list fix with negative tests is cheap and I recommend it before the Phase 16 device run, but it is not a gate for 16.2.
