# Phase 16.2 Plan 04: Propose strategy and error mapping Summary

Money-sensitive propose step as an injectable `RescheduleProposing` strategy: the client sends one PATCH and retries once with a saved card only on PAYMENT_METHOD_REQUIRED, the expert sends one card-free PATCH, and a propose-specific error table maps every code to its UI-SPEC copy and after-OK action.

## What was built

1. **Client proposer (4857c7ad, tracer):** `ProposeOutcome { Sent, NeedsPaymentMethod, CardUnusable, CardsUnavailable, Failed }`, `RescheduleProposing`, and `ClientRescheduleProposer`, mirroring `RescheduleResponder.accept`. Structurally at most two PATCH calls and one card-list call, no loop, no SetupIntent. Eight tests pin first-try success, default-else-first retry, empty vault, list failure, second PMR (CardUnusable, exactly two PATCH), and other errors before and after the retry.
2. **Expert proposer (e1f1b176):** `ExpertRescheduleProposer` depends only on `ExpertBookingsRepository`; its request type cannot carry a card id. PAYMENT_METHOD_REQUIRED is just `Failed`; every test asserts `getPaymentMethodsCalls == 0`.
3. **Error mapping (337af3e9):** `ProposeFailure { Silent, Show(message, clearSlot, reloadSlots, leave) }` with `toClientProposeFailure` and `toExpertProposeFailure`. RESCHEDULE_OUTSIDE_AUTH_WINDOW shows the fixed per-role copy regardless of server text (D-13); TOO_FAR_AHEAD and VALIDATION_ERROR show server text else fallback and clear the slot; slot/expert-unavailable clear and reload; INVALID_STATUS and 404 leave; ACCOUNT_SUSPENDED is silent. Thirteen tests cover the table.
