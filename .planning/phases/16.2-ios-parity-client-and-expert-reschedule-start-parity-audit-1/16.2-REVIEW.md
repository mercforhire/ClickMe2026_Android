# Phase 16.2: Code Review Report

**Reviewed:** 2026-10-31

## Summary

The shared `ReschedulePickerController` is the center of the phase. The picker's money path holds up: the `ClientRescheduleProposer` makes at most two PATCH calls and one list call, and the card id is never stored or logged. The sealed error mapping branches on `ErrorCode` and status rather than message text. The savedState restore re-validates the date, the month and the slot. `needsSeed` and `disclosureRestorePending` are initialised before `_state`, so the property-init-order trap is avoided. The `coroutineScope`/`async` fan-out in `loadMonths` propagates a centre-month failure correctly and swallows neighbour failures.

No security or data-loss defects were found. There are three correctness warnings, all in the one-shot, single-flight and restore handling of the controller, and six lower-severity items. The call-guard gap you flagged is rated Info below, with the reasoning.

## Warnings

### WR-01: Single-flight is released on success, so the screen is live again during the pop animation (duplicate PATCH or double pop)

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:415-431` (also `:338-360`, `:454-456`; `RescheduleScreen.kt:34-39`, `ExpertRescheduleScreen.kt:30-35`)
**Issue:** `send()` clears `isSubmitting` in a `finally` for every outcome, including `ProposeOutcome.Sent`. The route's `LaunchedEffect(state.sent)` calls `consumeSent()`, which resets `sent` to false at once, and then `onBack()`.

After that, the exiting picker stays composed for the Nav3 pop transition with `isSubmitting == false`, a selected slot and an enabled Submit button. `submit()` does not check `sent`, and `sent` is already consumed, so it could not guard anyway.

A tap on Submit or Continue during the transition can therefore:
1. issue a second PATCH (and a second card retry) for a booking that was just moved. The server will most likely answer `INVALID_STATUS`, which maps to an error dialog with `leave = true`. Dismissing it calls `onBack()` again, and `Navigator.goBack()` pops the top of the stack, which is now the opener screen. That is a double pop; or
2. if the backend ever accepts a replacement proposal, silently send a second one.

The top-bar Back is likewise enabled again (`backEnabled = !state.isSubmitting`), so a tap during the animation pops the opener as well. The "Back is blocked while a send is in flight" guarantee in the `RescheduleScreen` KDoc ends one frame too early.

**Fix:** Keep the picker locked once the send has succeeded. Do not reset `isSubmitting` on `Sent`:
```kotlin
scope.launch {
    var sentOk = false
    try {
        when (val outcome = proposer.propose(bookingId, slotStart, zone, note)) {
            ProposeOutcome.Sent -> {
                sentRequest.onSent(opener, bookingId)
                sentOk = true
                _state.update { it.copy(sent = true) }   // isSubmitting stays true
            }
            // ... other outcomes unchanged
        }
    } finally {
        if (!sentOk) _state.update { it.copy(isSubmitting = false) }
    }
}
```
The ViewModel is cleared with the entry, so the stale flag cannot leak. The existing `ReschedulePickerControllerTest` that asserts `isSubmitting == false` after `Sent` would need updating.

### WR-02: Disclosure "Continue" can be a silent no-op, and the open dialog is not tied to the slot it describes

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:284-296, 363-368, 408-412`
**Issue:** `refreshClock()` (every `ON_RESUME`) clears `selectedSlotStart` when the held slot has started. It does not touch an open `ReschedulePickerDialog.Disclosure`. The sequence is:
1. The user opens the disclosure and backgrounds the app until the slot start passes.
2. On return, the slot is cleared (`persistSlot()` removes the saved slot), but the dialog is still on screen.
3. Continue calls `confirmDisclosure()`, which sets `dialog = null`, removes `KEY_DISCLOSURE_OPEN`, and calls `send()`.
4. `send()` hits `val slotStart = s.selectedSlotStart ?: return` and returns without any feedback.

The user pressed Continue on a money-related confirmation and sees the dialog vanish with nothing sent and no message.

`confirmDisclosure()` also skips the checks `submit()` runs: it does not re-test that the slot is still pickable at `clock.instant()`, and it does not refresh `now`. `chargesSoon` in the dialog can therefore be stale. The server's `VALIDATION_ERROR` or `RESCHEDULE_TOO_FAR_AHEAD` backstop catches the stale case, but the silent no-op is a real hole.

**Fix:** Close or re-route the dialog whenever the slot is dropped, and make the no-slot case in `confirmDisclosure()` visible:
```kotlin
// refreshClock(), when clearing the slot:
_state.update {
    it.copy(
        selectedSlotStart = null,
        dialog = if (it.dialog is ReschedulePickerDialog.Disclosure) null else it.dialog,
    )
}
savedState.remove<Boolean>(KEY_DISCLOSURE_OPEN)
persistSlot()

// confirmDisclosure():
if (_state.value.selectedSlotStart == null) {
    _state.update { it.copy(dialog = null) }
    savedState.remove<Boolean>(KEY_DISCLOSURE_OPEN)
    showError(R.string.reschedule_start_error_no_slot)
    return
}
```

### WR-03: A restored disclosure can pop up later, unprompted, if the first availability load fails or the user changes the selection first

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:94, 189-193, 233-237, 393-401`
**Issue:** After process death with the disclosure open, `disclosureRestorePending` is true and only `applyAvailability()` consumes it, once, after the first successful month load.
- If that first `loadMonths` fails, the `catch (e: ApiException)` branch leaves the flag set. The user can retry, pick a different day or slot, or change the month. The next successful `applyAvailability()` then calls `restoreDisclosure()`, which opens the Continue/Cancel dialog for whatever slot is now selected. The dialog comes from a stale save, not from a Submit tap.
- No user action (`selectDate`, `selectSlot`, `moveToMonth`, `updateMessage`) clears the flag.

The user must still tap Continue, so D-08 ("never send without a tap") is not broken. But the dialog is unexpected, and its `chargesSoon` text describes a slot the user chose after the restore.

**Fix:** Drop the pending restore as soon as it can no longer be trusted: on load failure and on any user selection change.
```kotlin
private fun dropRestoredDisclosure() {
    if (!disclosureRestorePending) return
    disclosureRestorePending = false
    savedState.remove<Boolean>(KEY_DISCLOSURE_OPEN)
}
// call from: the ApiException catch in loadMonths, selectDate, selectSlot, moveToMonth, updateMessage
```

## Info

### IN-01: Call guard is not re-asked on the Continue and restore paths (advisory; rated Info)

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:351, 363-368, 393-401`
**Issue:** `callGuard.attemptModifyBooking` runs only in `submit()`. `confirmDisclosure()` and `restoreDisclosure()` reach `send()` without it. The disclosure is client-only, and the client's entry points are gated to a start at least 24 hours away (`canClientStartReschedule`). A live call on that booking is not reachable from the disclosure path in practice, so the gap is unreachable today. The risk is a future change to D-04 (the 24-hour rule is described as a UX rule that is easy to delete). The expert path has no disclosure and always goes through `submit()`.
**Fix:** One line makes it robust. Put the guard at the top of `send()`, or call it in `confirmDisclosure()` before `send()`:
```kotlin
if (!callGuard.attemptModifyBooking(bookingId, RestrictedAction.RescheduleBooking)) return
```
The guard queues a dialog and is idempotent, so calling it from `submit()` as well is harmless.

### IN-02: `PickerBooking.originalDuration` is non-null, so the `slotEnd` fallback in `disclosureSessionEnd` is dead and a non-positive duration silently skips the disclosure

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerUiState.kt:38-40`; `RescheduleRules.kt:100-109`
**Issue:** `originalDuration` is a computed `Duration.between(currentStart, currentEnd)`, never null. `disclosureSessionEnd` takes `Duration?` and only reaches its `slotEnd` and `proposedStart` branches when it is null, which cannot happen on the real path. If `currentEnd <= currentStart` (bad server data, or a client detail with `endTime == null` and a zero or negative `topic.durationMins`), the computed end is at or before the proposed start. `rescheduleDisclosure` then reports `showsPaymentDisclosure = false` and the card-hold release goes ahead without the disclosure. This is the money path the amendment was written to protect.
**Fix:**
```kotlin
val originalDuration: Duration?
    get() = Duration.between(currentStart, currentEnd).takeIf { !it.isZero && !it.isNegative }
```
`disclosureFor` already passes it through as nullable, so the `slotEnd` fallback becomes live.

### IN-03: `ReschedulePickerUiState.canSubmit` is not used by production code

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerUiState.kt:129-131`; `ReschedulePickerScreen.kt:303-307`
**Issue:** The screen computes `enabled = state.selectedSlotStart != null` itself. `canSubmit` is exercised only by a unit test, so the test asserts a rule the UI does not use. The two can drift (the test passes while the button logic changes).
**Fix:** Pass `enabled = state.canSubmit || state.isSubmitting` to `RescheduleSubmitButton` (it already treats `submitting` as enabled), or delete `canSubmit` and its test.

### IN-04: The hand-off consume-in-`init` plus collector block is copy-pasted four times

**File:** `MyBookingsViewModel.kt:152-164`, `UpcomingBookingViewModel.kt:116-132`, `ExpertBookingSummaryViewModel.kt:118-134`, `ExpertBookingsViewModel.kt:129-145`
**Issue:** Each ViewModel has the same consume-now, then collect-`pending`, then consume-and-reload block, differing only in the slot, the booking-id filter and the load mode. The repo already has a fifth copy of the shape for review thanks. A fix to the hand-off semantics (for example the non-atomic check-then-consume in `RescheduleSentRequest.consumeFor`, lines 57-65) has to be applied in four places.
**Fix:** Add one helper such as `RescheduleSentRequest.observe(opener, bookingId, scope, onSent)`, which does the init-time consume and the collector.

### IN-05: A stale `KEY_DISCLOSURE_OPEN` survives a rejected saved date

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:88-94`
**Issue:** When the restored date is in the past, `savedDate` is null, `disclosureRestorePending` becomes false, but `KEY_DISCLOSURE_OPEN` stays true in the SavedStateHandle. After the user picks a new slot, a second process death restores `disclosureRestorePending = true` and reopens a disclosure that was not open when the process died. Narrow (it needs two process deaths), but the cleanup is one line.
**Fix:** In `initialState()`, when `savedDate == null`, also remove `KEY_DISCLOSURE_OPEN` and `KEY_SLOT_START`.

### IN-06: An in-flight send is cancelled with the ViewModel scope when the stack is reset programmatically

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/ReschedulePickerController.kt:415-431`
**Issue:** The `BackHandler` and the disabled arrow stop user back navigation while submitting, but `Navigator.resetAndSelect`, `openChatThread`, a push deep link, a mode switch or a logout can clear the entry's ViewModel mid-PATCH. `viewModelScope` is cancelled and OkHttp cancels the call. The server may already have committed the move (and, on the client path, converted the card hold). The user gets no result, and `sentRequest.onSent` is never posted, so the opener is not told to reload. The opener reloads on its next resume, so state converges, but the user may resubmit blindly. Not a data-loss bug.
**Fix:** If this window matters, run the propose call under `withContext(NonCancellable)`, or post the hand-off from an application-scoped coroutine so the opener always reloads.
