## Summary

Incremental re-review of quick task 261031-v84. The diff makes `canClientStartReschedule` an allow-list and moves the avatar fallback color to `ClickMePalette.avatarFallback`.

I checked the new `canClientStartReschedule(status, end, now)` against the backend `canReschedule` in `backend-reference/src/utils/reschedule.js`. It matches.
- `confirmed` and `pending_approval` have no time gate. They map to the server's `NO_TIME_GATE_STATUSES` with `pending_reschedule` removed on purpose (D-04).
- `in_progress` and `completed` return true only while `now < end`. The server uses `now < new Date(booking.end_time)`, and `isBefore` is the same strict comparison.
- Every other status fails closed: cancelled, declined, missed, expired, unknown and empty. This fixes the prior WR-04.

Both call sites (`MyBookingsScreen.kt:361` and `UpcomingBookingScreen.kt:448`) pass the ticking `joinNow` clock and the booking's own end. The old single-argument signature has no remaining callers.

The color token is correct. `Color(0xFF1F2E24)` is (0.12, 0.18, 0.14) rounded, which is what iOS `ClientProfileBrand.avatarFallback` uses. The old `SearchAvatarFallbackColor` has no remaining references, and the only remaining `1F2E24` literal is the token itself. The `AvatarTest` change keeps the test tied to the real token.

I found no bugs or security issues. The findings below cover test coverage and consistency.

## Warnings

### WR-01: No test pins the My Bookings wiring of the new reschedule gate

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/mybookings/MyBookingsScreen.kt:361`
**Issue:** The gate change is covered by pure-function tests in `RescheduleRulesTest` and by the Upcoming Booking Details screen tests (cancelled hides, completed-after-end hides, rejoinable completed shows). `MyBookingsScreen` is the second call site, and nothing in `app/src/test/.../clientmode/mybookings/` exercises `onReschedule` or the Reschedule tag. A later edit that goes back to `canClientStartReschedule(item.status, item.startTime, joinNow)`, or drops `joinNow`, would pass the whole suite. The `end` parameter is a bare `Instant`, as is `now`, so swapping them or passing the wrong field compiles. This is also the surface WR-04 was about: an Upcoming card for a booking that went cancelled or ended must not offer Reschedule.
**Fix:** Add a My Bookings screen or card test with three cases, using whatever Reschedule tag `UpcomingBookingCard` already exposes:
- `confirmed` shows the button.
- `completed` with `endTime <= joinNow` hides it.
- `pending_reschedule` hides it.

Separately, consider a named parameter or value type for `end` and `now` so they cannot be silently transposed.

## Info

### IN-01: Status-literal cleanup is only partly applied

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/mybookings/TodaysSessions.kt:13` (also `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/push/PushDestinationResolver.kt:32`)
**Issue:** This change adds `STATUS_CONFIRMED` and `STATUS_IN_PROGRESS` and uses them in `BookingStatusDisplay.kt` and `RescheduleRules.kt`. `JOINABLE_BOOKING_STATUSES = setOf("confirmed", "in_progress", "pending_reschedule")` and `CANCELLABLE_BOOKING_STATUSES + "in_progress"` still use raw strings. Two spellings of the same wire value invite drift. `UpcomingBookingStatusRow.kt:146` and `UpcomingBookingCard.kt:328` also use raw strings, but those are previews.
**Fix:** Use the constants in `TodaysSessions.kt` and `PushDestinationResolver.kt`. Keep literals in tests, as `RescheduleRulesTest` already does to pin the wire values.

### IN-02: `canClientStartReschedule` KDoc is long and carries review-ticket references

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/RescheduleRules.kt:35-65`
**Issue:** The doc block is about 25 lines of lettered clauses (a) to (g). It references ticket IDs (WR-04, D-04, G-16.2-1) and a dated amendment. Clauses (e) and (g) describe motivation or history rather than the contract. The ticket IDs will age badly once the planning docs are archived.
**Fix:** Trim the KDoc to the contract: the allow-list, the end bound, the `pending_reschedule` exclusion and why, and the "server is the authority" note. Keep the history in the commit message or planning docs.

### IN-03: Local clock drives the end bound on a server-gated rule

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/reschedule/RescheduleRules.kt:60-68`
**Issue:** For `in_progress` and `completed`, visibility depends on the device clock via `joinNow`, while the server compares against its own clock. A skewed device can briefly show or hide the button wrongly. This is acceptable because the server is the authority and refusals map through `ProposeErrors`. It is only worth noting because the Expert side gates purely on the server's `actions.can_reschedule`.
**Fix:** No change needed. If the booking payloads carry an `actions.can_reschedule` field, preferring it for the client as well would remove the duplicated rule. That would be a design decision beyond this task.
