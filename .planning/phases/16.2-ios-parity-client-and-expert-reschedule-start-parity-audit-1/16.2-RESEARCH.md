## User Constraints (from CONTEXT.md)

### Locked Decisions

**Paid-booking 6-day calendar limit**
- **D-01: For a paid booking, the reschedule calendar stops at now + 6 days.** Days past that are not selectable. Reuse the existing `PAID_BOOKING_MAX_LEAD` / `PAID_BOOKING_MAX_LEAD_DAYS` (`screens/clientmode/makeabooking/BookingSlots.kt:24-32`), including its boundary rule (a start exactly 6 days out is allowed). Free bookings have no limit.
  - This is a **deliberate deviation from iOS**. iOS predates the backend change of 2026-10-28 (261028-uph), which makes a paid move past 6 days return `422 RESCHEDULE_TOO_FAR_AHEAD` on propose and on accept.
  - Keep mapping `RESCHEDULE_TOO_FAR_AHEAD` as the server backstop. The time can pass between picking and submitting, and accept re-checks against the current time. `RescheduleErrors.kt` / `ExpertRescheduleErrors.kt` already map it.
  - Research must confirm how the app tells "paid" from "free" for an existing booking. The backend defines paid as "has a payment intent or a non-`none` payment state" (`STRIPE-INTEGRATION.md` §2.5).
- **D-02: The expert's reschedule calendar applies the same limit to paid bookings.** It is one shared rule in the shared picker.
- **D-03: The limit looks the same as Make a Booking's paid limit.** Reuse whatever greyed-out day styling and explanatory copy Make a Booking already shows, so the two calendars behave alike.
- **Locked from the backend, not up for discussion:** `authorization_expires_at` is **non-gating** (`RESCHEDULE-PAYMENT-CONVERSION.md` §1). Never disable, grey out or filter slots because of it. It only decides whether the disclosure in D-11 is shown.

**Client Reschedule button visibility**
- **D-04: Hide the client's Reschedule button when the move is known to be blocked.** On Upcoming Booking Details and on My Bookings upcoming cards, hide it when any of these is true:
  - a reschedule is already pending (`pending_reschedule`, so the Accept/Decline UI shows instead),
  - the booking is still awaiting the expert's approval,
  - the session starts in less than 24 h (the server refuses those moves).

  Show it on every other upcoming booking. This deviates from iOS, which always shows the button.
- **D-05: On My Bookings upcoming cards, Reschedule sits next to the existing Message button**, as in the iOS card's "Reschedule + message" secondary-button row (`UpcomingBookingCard.swift:270-274`). On Upcoming Booking Details it pairs with Cancel, as in iOS `UpcomingBookingSecondaryActions`.
- **Locked:** The expert's Reschedule button (Booking Summary and upcoming cards) is shown only when `actions.can_reschedule` is true. Add `can_reschedule` to `ExpertBookingActionsDto` (`model/responses/ExpertBookingsPayload.kt:126`).

**Saved-card recovery (client propose)**
- **D-06: When no card can be used, reuse the accept flow's dialog.** This covers PAYMENT_METHOD_REQUIRED with an empty saved-card list, and a second PAYMENT_METHOD_REQUIRED after the retry (card unusable). Show the existing `PaymentMethodDialog` (`components/RescheduleResponseCard.kt:550-561`, `RescheduleDialog.PaymentMethodNeeded` / `CardUnusable`) with its "Add a payment method" action, which opens Payment Methods. This replaces iOS's error-only text that points at Settings > Payment. If loading the saved cards fails, use the existing cards-unavailable error (`reschedule_error_cards_unavailable`).
- **D-07: When saved cards exist, retry silently with the default card, or the first card if none is default.** Retry exactly once; there is never a loop. This matches iOS `RescheduleViewModel.submit` and Android `RescheduleResponder.accept` (Phase 8 D-02). Never log the `pm_` id. Per §3.1, PAYMENT_METHOD_REQUIRED does **not** mean "no card", and the app never goes straight to a SetupIntent.
- **D-08: Do not retry automatically after the user returns from Payment Methods.** The selected date, time and message stay in place, and the client taps Reschedule again. Nothing that moves money happens without a tap.
- **Locked:** Experts never send `stripe_payment_method_id` and are never gated on a card (§4, §6).

**After a successful send**
- **D-09: After the client sends a reschedule request, go back to the screen they came from** (Upcoming Booking Details or My Bookings) and refresh it, so the "Reschedule pending expert's response" state shows. Then show a "Reschedule request sent" snackbar. This deviates from iOS, which pops to the My Bookings root with no message.
- **D-10: The expert gets the same behavior.** Go back to Expert Booking Summary or the upcoming list, refresh it, and show a "Reschedule request sent" snackbar.

**Carried forward / locked by iOS and backend specs**
- **D-11: Payment-conversion disclosure.** When `proposed start + session duration > authorization_expires_at`, a Material `AlertDialog` appears before submitting, with the §2 copy ("Your card hold will be released…"). Continue submits; Cancel leaves the picker unchanged.
  - Add the "card may be charged sooner" line when the proposed start is less than 48 h away (iOS `chargeWillFireSoon`).
  - The session end comes from the slot's `end_utc` if it has one, otherwise from the original booking's duration.
  - Free, long-lead and captured bookings (`authorization_expires_at == null`) never show it.
- **D-12: Current-slot guard.** The calendar opens on the month and day of the current booking. The current slot is shown but cannot be picked, and the current-session label shows above the slots. Submitting the current slot is refused locally. Slots whose start has already passed are hidden.
- **D-13: Error copy follows iOS `RescheduleViewModel.rescheduleErrorMessage`.** RESCHEDULE_OUTSIDE_AUTH_WINDOW → "This time is past the payment hold on your original booking. Please cancel and book again to authorize a new payment." (terminal, not a field error). Anything else → the server message.
- **D-14: The expert picker uses the expert's own availability**, via `GET /experts/:id/availability` with the signed-in expert's id (iOS `ExpertRescheduleViewModel`), and the same per-month lazy fetch and client-local day grouping as the client picker.
- **D-15: The optional message is trimmed and sent as `note`, or omitted when blank.** `timezone` is the device zone id, and `proposed_start` is an ISO-8601 instant.

## Summary

This is a self-contained port. Nothing needs a new dependency. Every building block exists: the calendar, slot and notes cards in `screens/clientmode/makeabooking/subviews/`, the pure helpers `groupSlots`, `isSelectable`, `openDays`, `monthCells` and `isInLoadedWindow`, the `RescheduleResponder` saved-card retry, `RescheduleDisclosure.kt`, `PaymentMethodDialog`, the `OneShotSlot` hand-off pattern, and the Hilt assisted-ViewModel plus Nav3 key pattern. What is missing on the wire is two `PATCH` methods plus a request DTO, and `can_reschedule` on the expert DTOs. The backend contract is `.strict()`: `proposed_start` (ISO datetime), `timezone?`, `note?` (max 500) and, on the client only in practice, `stripe_payment_method_id?` (`pm_` prefix). The response is `{status, message, data:{booking_id, status}}`, which the existing `RescheduleResponseData` already decodes.

Reading the backend turned up four things CONTEXT does not say, and the planner should treat them as decisions to surface rather than silently follow (see Open Questions): (1) the backend does **not** refuse a propose because the *current* session starts in under 24 h. The "<24 h" refusal applies to the *proposed* start, and only when the move converts a live authorization, so D-04's third bullet is a UX choice whose stated reason is not what the server does; (2) `end_utc` on an availability slot is `start + 30 min` because Android never sends `topic_id`, so D-11's "use the slot's `end_utc` first" under-estimates the session end for any session longer than 30 minutes, whereas the backend's own conversion test uses the booking's original duration; (3) the availability endpoint accepts `exclude_booking_id`, added specifically so "the reschedule page does not gray the caller's own booking" (iOS never sends it); (4) the expert **list** payload already carries `actions.can_reschedule`, so the expert upcoming card needs no extra call.

The money path is small and already proven. The client propose is the existing accept recovery with a different verb: send once, on PAYMENT_METHOD_REQUIRED list the saved cards, retry once with the default (else first) card, and map a second PAYMENT_METHOD_REQUIRED to `CardUnusable`. Mirror `RescheduleResponder` (a `RescheduleProposing` interface with a client implementation that does the retry and an expert implementation that never touches cards), and keep it out of the ViewModel so it is testable with `FakeClickMeApi`. Leave `MakeABookingViewModel` (1087 lines, owns the live paid flow) untouched; share only the stateless cards and the pure helpers.

**Primary recommendation:** Add the two PATCH calls and `can_reschedule`, parameterize the existing Make a Booking cards in place (default values keep Make a Booking identical), build one picker state holder with two thin Hilt ViewModels and a `RescheduleProposing` strategy (client retries once with a saved card, expert never does), and hand the success notice to the origin through a new `OneShotSlot`-based singleton modeled on `ReviewLaunchRequest`.

### Pattern 1: Share the cards, not the ViewModel
**What:** Add optional parameters (defaults reproduce today's behavior) to `MakeABookingCalendarCard`, `MakeABookingTimeSlotsCard`, `MakeABookingNotesCard` and `MakeABookingExpertCard`. Call them from the picker. Do not edit `MakeABookingViewModel`.
**Parameters needed** (from UI-SPEC "Shared picker"): calendar `tagPrefix` (default `make_a_booking_day_`); slots card `title`, `paidWindowNote`, `hidePastSlots`, `currentSlotStart`, `tagPrefix`; notes `placeholder`, `tag`; expert card `detail`. The paid-window note text is hard-wired to `make_a_booking_paid_window_note` ("booked") today, so it must become a parameter (the picker needs "rescheduled").
**Why in place:** `MakeABookingFormCardsTest`, `MakeABookingCalendarSlotsTest`, `MakeABookingScreenTest` and `MakeABookingTopicCardsTest` reference these names and tags; defaults keep them green [VERIFIED: grep of `app/src` for the four composables and both tag helpers].
**Pure helpers stay where they are.** `groupSlots`, `isSelectable`, `openDays`, `monthCells`, `isInLoadedWindow`, `canGoToPreviousMonth`, `PAID_BOOKING_MAX_LEAD` are top-level functions; call them from the picker package.
**Month loading:** Make a Booking loads `month` plus both neighbours in parallel, flattens the days and calls `groupSlots` once, latest-wins (cancels the previous job), and only the centre month can fail the section [VERIFIED: MakeABookingViewModel.kt `loadAvailability`, read this session]. Copy that shape into a small `MonthAvailabilityLoader` owned by the picker controller (about 40 lines) instead of iOS's per-month cache. It satisfies D-14 ("per-month lazy fetch, client-local grouping") and avoids iOS's stale-response race.

### Pattern 2: One picker controller, two thin ViewModels
Mirror `RescheduleResponseController` (one controller, two VMs, strategy interface). The controller owns state (`ReschedulePickerUiState`: load state, `zone`, `today`, `now`, `displayedMonth`, `selectedDate`, `selectedSlotStart`, `message`, `availability`, `currentStart`, `originalDuration`, `authorizationExpiresAt`, `isPaid`, `submitting`, dialog flags, one-shot `sent`). The VMs differ only in: how they load the booking and expert id, which availability id they pass, and which `RescheduleProposing` they hold.
- **Client load:** `GET /client/bookings/{id}` → `ClientBookingDetail` has `startTime`, nullable `endTime` (fallback `startTime + topic.durationMins`, default 30, as `toUpcomingDetails` does), `authorizationExpiresAt`, `paymentStatus`, `topic.isFree`, `expert.id/fullName/title/avatarUrl`, `expertTimezone` [VERIFIED: ClientBookingDetail.kt, read this session]. Availability id = `expert.id`.
- **Expert load:** `GET /expert/bookings/{id}/details` → `ExpertBookingDetail` has `startTime`, `endTime`, `authorizationExpiresAt`, `client.name/avatarUrl`, `session.topicTitle`, `isPaid` (fee > 0), `actions` [VERIFIED: ExpertBookingsPayload.kt]. Availability id = the signed-in expert's own id: `userManager.me.value?.id ?: userManager.authUser.value?.id`, the same expression the app already uses for `CurrentUserIdProvider` [VERIFIED: di/ChatModule.kt:29-30]. Inject `CurrentUserIdProvider`. If it returns null, show the load error.
- State survives rotation and process death through `SavedStateHandle` (booking id, displayed month, selected date, slot start, message, dialog flags), like `MakeABookingViewModel`. A restored slot is applied only if it is still selectable after the first load.
- `refreshClock()` on resume re-reads `Clock`, clears a selected slot that has started, and does not re-evaluate the paid cap (UI-SPEC "Time passing"; the server backstop covers it).
- Seed `selectedDate = max(bookingStartDate, today)` and the month from it. A completed or in-progress session the expert can still move (`canReschedule` is true while the original `end_time` is in the future) can start before today; `canGoToPreviousMonth` and `isPastDay` assume nothing earlier than today.

### Pattern 3: Paid decision and the 6-day cap
Backend rule: `isPaidBooking` is true when `payment_intent_id` is truthy or `payment_status` is a non-empty string other than `'none'`. `assertRescheduleLeadTimeAllowed` throws only when `proposedStartMs - now.getTime() > LONG_LEAD_THRESHOLD_MS` (strict `>`, so exactly 6 days passes), where the constant is `6 * 24 * 60 * 60 * 1000`. [VERIFIED: backend-reference/src/utils/reschedule.js:59-86]
```js
function isPaidBooking(booking) {
  if (!booking) return false;
  if (booking.payment_intent_id) return true;
  const status = booking.payment_status;
  return typeof status === 'string' && status !== '' && status !== 'none';
}
```
`isPaid` for the client picker: the client detail's `payment_status` is a *derived display value* that is `'none'` when there is no `payment_intent_id` [VERIFIED: clientBooking.controller.js:73 `if (!booking.payment_intent_id) return 'none';`]. A paid booking with no payment intent (a pre-converted long-lead save-card booking, raw status `scheduled`) therefore reports `'none'` even though the server treats it as paid. So use the UI-SPEC rule: `isPaid = (paymentStatus != null && paymentStatus != "none") || topic.isFree == false`. The second term closes the long-lead gap; the first covers a topic that became free later. Android already uses `latestSelectableStartAt(now) = now + PAID_BOOKING_MAX_LEAD` with the inclusive boundary [VERIFIED: MakeABookingUiState.kt `latestSelectableStartAt`]; reuse `BookingTimeSlot.isSelectable(now, latestStart)` and add the current-slot exclusion on top.
Expert `isPaid`: `ExpertBookingDetail.isPaid` (fee amount > 0). `amount_paid_minor_units` is persisted at confirm [VERIFIED: booking.controller.js:906], so it is set for held bookings. The expert detail exposes no payment state, so this is the only signal; a wrong "free" is caught by the `RESCHEDULE_TOO_FAR_AHEAD` backstop.

### Pattern 4: Propose, disclosure and saved-card recovery
**Strategy interface** (same split as `RescheduleResponding`, Phase 8 D-18):
```kotlin
sealed interface ProposeOutcome {
    data object Sent : ProposeOutcome
    data object NeedsPaymentMethod : ProposeOutcome   // PMR + empty vault
    data object CardUnusable : ProposeOutcome         // PMR again after the one retry
    data object CardsUnavailable : ProposeOutcome     // PMR, then GET /me/payment-methods failed
    data class Failed(val error: ApiException) : ProposeOutcome
}
interface RescheduleProposing {
    suspend fun propose(bookingId: String, proposedStart: Instant, zone: ZoneId, note: String?): ProposeOutcome
}
```
`Failed` carries the `ApiException` so the controller maps it with the client or the expert mapper; this keeps the proposer free of copy.
**Client implementation** is `RescheduleResponder.accept` with a different verb: send once; if it is not `PaymentMethodRequired`, return `Failed`; else `paymentMethods.list()` (failure → `CardsUnavailable`); `cards.firstOrNull { it.isDefault } ?: cards.firstOrNull()` (null → `NeedsPaymentMethod`); retry once with that `id`; a second `PaymentMethodRequired` → `CardUnusable`; any other error → `Failed`. At most two PATCH calls and one list call. Never log the `pm_` id or the note.
**Disclosure** reuses `rescheduleDisclosure(proposedStart, proposedEnd, authorizationExpiresAt, now)` from `RescheduleDisclosure.kt` unchanged: `showsPaymentDisclosure = authorizationExpiresAt != null && proposedEnd != null && proposedEnd.isAfter(authorizationExpiresAt)` and `chargesSoon = Duration.between(now, proposedStart) < CHARGES_SOON_WINDOW` with `CHARGES_SOON_WINDOW = Duration.ofHours(48)` [VERIFIED: RescheduleDisclosure.kt:9,36-37]. Its copy and rules match iOS and §2. The caller supplies `proposedEnd` (see Open Question 2). Copy: reuse `reschedule_accept_dialog_charges_soon` for the caveat; the disclosure body for propose is the iOS string ("Because you're moving this session more than a few days out…"), which differs from the accept-side `reschedule_accept_dialog_disclosure`, so it needs its own resource.
**Dialogs:** the saved-card dialog `PaymentMethodDialog` is `private` and its message is chosen inside `RescheduleOutcomeDialog` from `reschedule_payment_needed_message` ("…before accepting this reschedule"). UI-SPEC requires a propose-specific message. Make `PaymentMethodDialog` internal/public with its `message` parameter (already a parameter) or add a message override to `RescheduleOutcomeDialog`; do not reuse the accept string. `RescheduleDialog.Error` is titled "Couldn't update booking" (`reschedule_error_title`); the picker's errors use "Couldn't reschedule booking", so use `AuthErrorDialog` directly with the new title, as UI-SPEC says.

### Anti-Patterns to Avoid
- **Gating, dimming or filtering slots by `authorization_expires_at`.** Locked non-gating. It only decides the dialog.
- **Retrying the PATCH automatically after returning from Payment Methods** (D-08), or a loop on repeated PAYMENT_METHOD_REQUIRED (D-07).
- **Routing PAYMENT_METHOD_REQUIRED straight to "add a card" or a SetupIntent** (§3.1).
- **Reusing the accept-side error mappers** (`toRescheduleFailure`, `toExpertRescheduleFailure`) for propose. Their copy is accept-worded, they reload instead of clearing the slot, and `RESCHEDULE_OUTSIDE_AUTH_WINDOW` shows the server text where D-13 wants fixed copy.
- **Optimistic state.** Nothing on the origin changes before the quiet refresh that follows the pop.
- **Putting the proposer logic in the ViewModel.** Keep it in an injectable class so it is testable with `FakeClickMeApi` (as `RescheduleResponseTest` does).
- **Sending `stripe_payment_method_id` from the expert.** Use a request type without the field so it cannot be sent.

## Common Pitfalls

### Pitfall 1: Slot `end_utc` is not the session end
**What goes wrong:** the disclosure is skipped for a session longer than 30 minutes when the proposed end falls in the 30-minute band after `authorization_expires_at`.
**Why it happens:** Android never sends `topic_id` (iOS parity), so the backend uses `topicDurationMins = 30` and sets `end_utc = start + 30 min` [VERIFIED: availability.controller.js:304 `let topicDurationMins = 30;` and services/availability.js:180 `end_utc:     slotEndUtc.toISO(),`]. The backend's own conversion test uses the booking's original duration: `proposedEndMs = proposedStartMs + durationMs` [VERIFIED: utils/reschedule.js:140].
**How to avoid:** see Open Question 2. Compute `proposedEnd` from the original duration (or `max(slotEnd, start + duration)`).
**Warning signs:** a 60-minute booking moved to a start whose `start + 30 min` is before, but `start + 60 min` is after, `authorization_expires_at` shows no dialog.

### Pitfall 2: D-04's "<24 h" is not a server rule on the current start
**What goes wrong:** the planner or a reviewer believes the server refuses moves for sessions starting soon and tests against it.
**Why it happens:** the server's 24 h rule is on the *proposed* start (`charge_due_at <= now` → `RESCHEDULE_OUTSIDE_AUTH_WINDOW`) and only for conversion moves [VERIFIED: utils/reschedule.js:222-231 quoting `'The proposed session must be at least 24 hours away to move this booking that far out. ' +`]. `canReschedule` has no time gate for `confirmed`, `pending_approval`, `pending_reschedule` [VERIFIED: utils/reschedule.js:23 `const NO_TIME_GATE_STATUSES = ['confirmed', 'pending_approval', 'pending_reschedule'];`].
**How to avoid:** implement D-04 exactly as locked (it is the user's UX decision) but keep the rule in one pure function with a named constant, document the real server behavior in the code comment, and raise it as Open Question 1. Also keep the server `RESCHEDULE_OUTSIDE_AUTH_WINDOW` mapping, which the picker will still hit when a user moves a held booking to a slot under 24 h away.

### Pitfall 3: Propose errors the UI-SPEC table does not list
**What goes wrong:** an unmapped code shows a generic message, or the user is left with a stale slot.
**Why it happens:** the client propose can raise `VALIDATION_ERROR` (422, "proposed_start must be a future date and time."), `INVALID_PAYMENT_METHOD` (422, on the retry), `INVALID_STATUS` (409) and `NOT_FOUND` (404) [VERIFIED: clientBooking.controller.js reschedule(), read this session]. It does **not** call `assertUserAvailable`, so `EXPERT_UNAVAILABLE` and `SLOT_UNAVAILABLE` do not occur on propose (they occur at accept); the UI-SPEC rows for them are defensive only.
**How to avoid:** map `VALIDATION_ERROR` like `RESCHEDULE_TOO_FAR_AHEAD` (clear the slot, re-read the clock, show the server message or a "time has passed" string) and `INVALID_PAYMENT_METHOD` to the server text (stay).

### Pitfall 4: Navigation key collisions and covered entries
**What goes wrong:** a crash on duplicate content keys, or the origin showing stale data after the pop.
**Why it happens:** the shell flattens the start stack and the selected stack. Covered entries leave composition, so `ON_RESUME` is not reliable.
**How to avoid:** add `origin` to both keys (Pattern 7); on the origin use `LaunchedEffect(Unit)` plus `ON_RESUME` exactly as `UpcomingBookingScreen` does; consume the hand-off in the ViewModel, not in a composable.

### Pitfall 5: Retry loops and double submits
**What goes wrong:** two proposals, or a second card charge path.
**Why it happens:** a double tap, a retry that is not single-flight, or retrying after the Payment Methods screen.
**How to avoid:** a single `isSubmitting` guard that spans the whole proposer call (PATCH, card list, retry); disable Back and the form while it is set; after Payment Methods only the Reschedule button submits. Test: after `CardUnusable` and a simulated return, zero PATCH calls happen until `submit()` is called.

### Pitfall 6: Wrong request shape
**What goes wrong:** a 422 from the strict schema.
**Why it happens:** `proposed_start` must pass zod `datetime({ offset: true })`; the note max is 500; `stripe_payment_method_id` must start with `pm_`; unknown keys are rejected [VERIFIED: schemas/booking.schema.js:101-113]. `timezone` and `note` are optional.
**How to avoid:** send `slot.start.truncatedTo(ChronoUnit.SECONDS).toString()` (UTC `Z`; iOS sends `.withInternetDateTime`, which is seconds precision); trim the note, omit it when blank, cap with `capNotes`; Moshi omits nulls (the existing `AcceptRescheduleRequest` relies on that [VERIFIED: BookingActionRequests.kt KDoc "Null is omitted by the converter"]). `timezone = ZoneId.systemDefault().id`.

### Pitfall 7: Calendar seeding for a booking that already started
**What goes wrong:** the picker opens on a past day or a month before the current one, and `syncClock`-style logic fights it.
**Why it happens:** the expert can move an in-progress or early-ended session (`canReschedule` allows `in_progress`/`completed` until the original `end_time`).
**How to avoid:** seed from `max(bookingDate, today)`; keep the Current banner showing the real start.

### Pitfall 8: Card click-through and layout swap on My Bookings
**What goes wrong:** tapping Reschedule opens the details instead, or the card layout jumps when a reload crosses the 24 h mark.
**Why it happens:** the card surface is `clickable`; the action area changes shape with visibility (UI-SPEC A-6, accepted).
**How to avoid:** the buttons own their clicks like `JoinCallButton`/`MessageButton` do today; test both layouts in a list that mixes them.

### Pitfall 9: Rotation and process death mid-submit
**What goes wrong:** a proposal is sent and the screen restores as if nothing was sent, inviting a second tap.
**How to avoid:** the in-flight call runs in `viewModelScope`; on success post the hand-off and pop even if the composable is gone (UI-SPEC "Navigation and Structure"). Persist the selection but never persist `isSubmitting`, the `pm_` id or dialog results.

### 2. Client proposer (mirror of `RescheduleResponder.accept`)
```kotlin
class ClientRescheduleProposer @Inject constructor(
    private val bookings: ClientBookingsRepository,   // + suspend fun reschedule(id, body)
    private val paymentMethods: PaymentMethodsRepository,
) : RescheduleProposing {
    override suspend fun propose(bookingId: String, proposedStart: Instant, zone: ZoneId, note: String?): ProposeOutcome {
        val start = proposedStart.truncatedTo(ChronoUnit.SECONDS).toString()
        try {
            bookings.reschedule(bookingId, RescheduleProposalRequest(start, zone.id, note))
            return ProposeOutcome.Sent
        } catch (e: ApiException) {
            if (!e.isPaymentMethodRequired()) return ProposeOutcome.Failed(e)
        }
        val cards = try { paymentMethods.list() } catch (_: ApiException) { return ProposeOutcome.CardsUnavailable }
        val cardId = (cards.firstOrNull { it.isDefault } ?: cards.firstOrNull())?.id
            ?: return ProposeOutcome.NeedsPaymentMethod
        return try {
            bookings.reschedule(bookingId, RescheduleProposalRequest(start, zone.id, note, cardId))
            ProposeOutcome.Sent
        } catch (e: ApiException) {
            if (e.isPaymentMethodRequired()) ProposeOutcome.CardUnusable else ProposeOutcome.Failed(e)
        }
    }
}
// isPaymentMethodRequired(): this is ApiException.Http && code == ErrorCode.PaymentMethodRequired
```

## Open Questions

1. **D-04 third bullet ("the session starts in less than 24 h (the server refuses those moves)")**
   - What we know: the backend never refuses a propose because the current session starts soon. `canReschedule` is true for `confirmed`, `pending_approval`, `pending_reschedule` with no time gate. The only 24 h rule is on the proposed start, for conversion moves (`charge_due_at <= now`). Those are `confirmed`/`held` bookings authorized less than 6 days ago.
   - What's unclear: whether the user intends "hide when starting in <24 h" as a pure UX rule (product choice) or believes it mirrors a server rule.
   - Recommendation: implement D-04 as locked (one pure function, one constant), note in the plan that the real server rule differs, and surface it to the user at plan review. If the user drops it, the change is deleting one condition.

2. **D-11 "session end comes from the slot's `end_utc` if it has one"**
   - What we know: `end_utc` is `start + 30 min` for every slot because `topic_id` is never sent. The server decides conversion with the booking's original duration.
   - What's unclear: whether the user accepts a possible missed disclosure for sessions longer than 30 min in a 30-minute band.
   - Recommendation: compute `proposedEnd = start + originalDuration` when the duration is known (always known for both modes), falling back to the slot's `end_utc` only if it is not. Over-showing the dialog is safe; under-showing is a consent gap. Record it as a deviation from the D-11 wording.

3. **`exclude_booking_id` on the availability call**
   - What we know: the backend added it (quick 260804-qo6) so the reschedule page does not gray the booking's own slot; invalid values are ignored; iOS does not send it [VERIFIED: availability.controller.js:225,284; iOS `getExpertAvailability(id:month:)`]. Without it the booking's own slot and its 30-minute buffer cells come back unavailable, so moving a session by 30 minutes is impossible.
   - Recommendation: send it from both pickers (prescribed here). The Current chip is matched by start time, so it renders the same either way. Flag as a deviation from iOS.

4. **Fixed D-13 copy versus the server message for the under-24 h conversion case**
   - What we know: for a held booking moved under 24 h out, the server message says "Please choose a later time, or re-book", while D-13's fixed iOS text says "cancel and book again". The fixed text is wrong advice for that sub-case.
   - Recommendation: keep D-13 (locked), but the planner may want to ask whether the server message should win when it is the under-24 h variant. Not blocking.

5. **Grid built for 30-minute cells**
   - What we know: without `topic_id` the grid offers any free 30-minute cell, so a 60-minute booking can be proposed into a 30-minute gap; the conflict only surfaces at the counterparty's accept (`SLOT_UNAVAILABLE` for the expert, mapped already).
   - Recommendation: keep iOS parity (no `topic_id`); note it in the matrix as a known behavior.

## Security Domain

`security_enforcement` is not set to `false` in `.planning/config.json`, so this applies.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (no new auth) | Bearer attached by the existing interceptor; the two new paths are not public |
| V3 Session Management | no | — |
| V4 Access Control | yes | Server scopes both PATCH calls to the caller (404 otherwise) and is the authority on `can_reschedule`, paid cap and card gate. Client-side hiding is UX only, never a control |
| V5 Input Validation | yes | Client: trim, cap the note at 500 (`capNotes`), send `proposed_start` as UTC ISO seconds, `timezone` from the device. Server: zod `.strict()` (verified). Render all server text (names, topic, messages, errors) as plain `Text` |
| V6 Cryptography | no | The `pm_` id is an opaque Stripe reference, not a secret, but still never logged or persisted |
| V7 Error handling and logging | yes | No logging of the note, the `pm_` id or the booking-identifying payload; `ApiException` messages carry status and code only |
| V8 Data protection | yes | Hold the `pm_` id only for the one request; do not put it in `SavedStateHandle`, nav keys or state |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Duplicate or looping money-moving requests (double tap, auto-retry after returning) | Tampering / Repudiation | Single-flight across PATCH, card list and retry; one silent retry; no retry after Payment Methods (D-07/D-08); disable Back and form while submitting |
| Sending another user's card id | Spoofing / Elevation | Take the id only from the caller's own `GET /me/payment-methods`; the server also rejects foreign ids with `INVALID_PAYMENT_METHOD` (verified) |
| Expert attempting to supply a card | Tampering | Expert request type has no card field; server ignores it anyway (§4) |
| Stale or forged client-side eligibility | Tampering | Server re-checks status, paid cap and conversion on every call; map the 4xx codes |
| Information disclosure via logs or saved state | Information disclosure | Do not log or persist the note or `pm_`; do not save `isSubmitting` |
| Server text injection into UI | Tampering | Plain `Text` only (`FieldError.Text`), never HTML or markup |
