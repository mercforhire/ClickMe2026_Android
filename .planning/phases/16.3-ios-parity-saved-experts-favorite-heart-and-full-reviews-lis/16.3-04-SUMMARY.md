# Phase 16.3 Plan 04: Saved Experts state machine Summary

Saved Experts ViewModel with one-shot first load (page 1, limit 100), return-triggered silent refresh, pull-to-refresh, first-load error with Retry, optimistic remove that rolls back to the original index, a refresh/remove race guard, and the "View My History" Past-tab hand-off.

## What was built

- **Task 1 (tracer, 6f94f0af):** `FavoritesUiState.kt`, `FavoritesNavigation.kt`, and the first-load slice of `FavoritesViewModel` (`onScreenShown`, `onScreenHidden`). Rows map per iOS `FavoritesViewModel.map` (blank name -> null, headline -> "", blank tags dropped). `toProfileKey` seeds `StackOrigin.Profile` with null rating and review count.
- **Task 2 (cf6eabab):** `startLoad` with Loud/Pull/Quiet modes, `retry`, `refresh`, `consumeRefreshFailure`. A new load clears stale `isRefreshing`/`refreshFailed`; failure handling per mode via `toSectionMessage()`.
- **Task 3 (24029df4):** `remove` (optimistic drop, reinsert at original index on failure, one-shot `removeFailed`), `removing` and `removedSinceLoadStart` guards filtering every load result, `consumeRemoveFailure`, `viewHistory`.

## Deliberate iOS deviations

- D-09: refresh on return (iOS loads once).
- D-11: pull-to-refresh and Phase 15 states (iOS shows a spinner).
- D-12: `limit=100` (iOS uses default 20); favorites beyond 100 are not shown (accepted scope, RESEARCH A6).
- D-06: View My History is wired (does nothing on iOS).
- Remove failure is a snackbar message instead of the iOS alert.

## Deviations from Plan

None - plan executed as written, with two notes:

- **TDD RED:** the tests reference types and functions that do not exist before implementation, so they cannot compile; RED was therefore "does not compile" for Tasks 1 to 3 rather than a runnable failing test. Tests were written first each time.
- Task 3's `remove` computes `toFavoriteFailure()` once into a local (to satisfy the acceptance grep count of 1).

Known limitation (accepted by the plan's test spec): when two removals both fail, every row is restored exactly once but their relative order is not guaranteed to match the original list (each reinserts at its own recorded index into the then-current list).
