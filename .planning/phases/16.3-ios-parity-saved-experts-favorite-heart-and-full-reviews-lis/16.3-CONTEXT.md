# Phase 16.3: iOS parity: Saved Experts, favorite heart and full Reviews list - Context

**Gathered:** 2026-11-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Closes PARITY-AUDIT gaps #2, #2b and #3 (`.planning/PARITY-AUDIT.md`):

1. **Favorite heart on Expert Profile (#2b).** A client can favorite or unfavorite an expert from the Expert Profile app bar. The toggle is optimistic and rolls back on failure.
2. **Saved Experts screen (#2).** A client opens the list from a new "Saved Experts" row on the client Profile hub. The list opens an expert's profile, removes a favorite after a confirm dialog, and has an empty state with two action buttons and a Pro Tip card.
3. **Full Reviews list (#3).** "See all" on the Expert Profile Recent Reviews card opens a full Reviews screen: an overall rating card with the total count, then review cards.

New endpoints: `GET /client/favorites`, `PUT /client/favorites/:expertId`, `DELETE /client/favorites/:expertId`. `GET /experts/:id/reviews` already exists on Android (`ClickMeApi.kt`, `EXPERT_REVIEWS`).

Out of scope: anything else in the audit (16.4 and 16.5 cover the rest), favorites on any other surface (Explore and Search cards), and paging past the first page.

</domain>

<decisions>
## Implementation Decisions

### Favorite heart (Expert Profile)
- **D-01: The heart's starting state comes from `is_favorite` on `GET /experts/:id/details`**, which the screen already calls. Add `is_favorite` (default false) to the details DTO. Do **not** port iOS's extra `GET /client/favorites?limit=100` scan.
  - This is a deliberate deviation from iOS. The iOS comment ("`/experts/:id/details` doesn't include `is_favorite`") is out of date: the backend now computes it (`publicProfile.controller.js` `getExpertDetails`, best-effort, false on any lookup error and false for self-view).
- **D-02: The heart is a TopAppBar action placed just before the existing ⋮ Report/Block menu** (`ExpertProfileScreen.kt` `ProfileTopBar` `actions`). It is an outlined heart when not favorited and a filled heart when favorited. It is hidden whenever Book/Message would be hidden for self: `isSelfView`, or `chatEntry.isSelf(expertId)` as a backstop. iOS hides it on self-view (`ExpertProfileView.swift` toolbar).
  - Show it only once details have loaded (the starting state is unknown before then). The `showSafetyMenu` gate already works this way.
  - Accessibility: a content description that changes with state ("Save expert" / "Remove from saved"), plus selected/toggleable semantics. Exact strings are at Claude's discretion.
- **D-03: The toggle is optimistic.** Flip the heart, call `PUT` (add) or `DELETE` (remove) on `/client/favorites/:expertId`, then set the heart to the server's `data.is_favorite` (reconciling as iOS `toggleFavorite` does). **On failure: roll back to the previous state and show a snackbar with the server message.** This deviates from iOS, which shows a "Couldn't update favorites" alert.
- **D-04: Taps during a request are ignored**, as in iOS `isFavoriteInFlight`. There is no queue or "latest tap wins".
- **Locked by backend:** adding is **`PUT`**, not `POST` (PARITY-AUDIT says POST, which is wrong; `backend-reference/src/routes/favorites.js`). Both calls are idempotent and limited to clients (`roleCheck('client')`). The path id is a UUID (a malformed one returns 422).

### Saved Experts: empty state
- **D-05: "Explore Experts" switches to the Explore tab root**, the same tab switch the bottom bar does. On iOS this button does nothing (the hub opens `FavoritesView()` without wiring its callbacks). Wiring it here is a deliberate fix.
- **D-06: "View My History" switches to the Bookings tab and selects its Past segment.** On iOS this button also does nothing. Research how to select the Past segment from another tab (for example a navigation argument or a shared selection state on My Bookings).
- **D-07: The Pro Tip text says "heart icon".** The iOS text says "Tap the star icon on any expert's profile to add them to this list instantly.", but the control is a heart. This is a copy deviation.
- **D-08: The Pro Tip card appears only in the empty state**, as on iOS. The order is the glowing illustration, "No favorites yet", the subtitle, the 2 buttons, then the Pro Tip. The populated list shows only the tagline ("Manage your curated list of elite professionals.") and the cards.

### Saved Experts: list behavior
- **D-09: Refresh silently when the screen comes back into view.** Load fully the first time the screen opens. After that, whenever the screen comes back into view (for example, back from an Expert Profile opened from the list), reload in the background and keep the current rows on screen. Unfavoriting from the profile is then reflected when the user returns. iOS loads once and goes stale; this is a deliberate fix.
  - A background refresh that fails keeps the current rows and does **not** show the error view (Phase 15 D-05 spirit). Whether it shows the "Couldn't refresh" snackbar is at Claude's discretion (leaning toward silent for return-triggered refreshes and the snackbar for pull-to-refresh).
- **D-10: Removing asks for confirmation in a Material `AlertDialog` with the iOS copy.** Title "Remove {name} from favorites?", body "You can favorite this expert again anytime from their profile.", a destructive "Remove" and a "Cancel". The trigger is the filled heart on each card. Confirming removes the row optimistically and calls `DELETE /client/favorites/:expertId`. If that fails, the row goes back to its original position, as in iOS `removeFavorite`.
- **D-11: Loading follows the Phase 15 standard.** Skeleton cards on first load. Inline `ErrorState` with Retry and the iOS title "Couldn't load favorites" plus the server message. Pull-to-refresh, with the "Couldn't refresh" snackbar (`RefreshFailedSnackbar`) when a refresh fails over existing rows. This deviates from the iOS centered spinner and the missing pull-to-refresh.
- **D-12: One request with `limit=100`** (`GET /client/favorites?page=1&limit=100`). The backend caps the limit at 100 and defaults to 20 (`utils/pagination.js` `parsePage`). There is no load-more or infinite scroll, and no total-count UI.
- **Carried from iOS:** mapping per `FavoritesViewModel.map`. Name falls back to "Expert", headline to "", tags to [], avatar to none. The bio is always empty because the endpoint has none, so it is not shown. Tapping a card opens Expert Profile for `expert_id`. The TopAppBar title is "Favorite Experts" with a back arrow (iOS `navigationTitle`). The hub row is labeled "Saved Experts".
- **Hub row placement (from iOS `ClientProfileHomeScreen.swift:94-97`):** a new "Discovery" section holding one "Saved Experts" row with a heart icon, placed after the mode-switch card and before "Account".

### Reviews: "See all" and the full list
- **D-13: Always show the Recent Reviews card with its "See all" header, even with 0 reviews**, as on iOS (`ExpertProfileReviewsCard.swift`). This replaces the current Android rule (the caller hides the card when `reviews` is empty, `ExpertProfileReviewsCard.kt:28-29` KDoc). With 0 reviews the card shows only the header. "See all" then opens the full screen's "No reviews yet" empty state.
  - While reviews are still loading, keep the existing `ExpertProfileReviewsCardSkeleton`. If the reviews request fails, keep whatever the current error handling does. Claude's discretion, but don't show "See all" over a failed load in a way that reads as "0 reviews".
- **D-14: "See all" shows whenever the card shows**, even with 1–3 reviews (all already visible). This matches iOS.
- **D-15: Self-view keeps the reviews card and "See all"**, as on iOS. The expert sees their own full review list. Only Book, Message and the heart are hidden in self-view.
- **D-16: The full Reviews screen follows the iOS layout and the Phase 15 states.**
  - TopAppBar title: "{FirstName}'s Reviews" (first word of the trimmed name), falling back to "Reviews" when no name is known (iOS `ExpertReviewsViewModel.navigationTitle`). Back arrow.
  - Content: the overall rating card (overall rating to one decimal, stars, total count), then one card per review with the reviewer avatar, the name (falling back to "Anonymous"), stars, topic (`session_context.topic`), date label (`session_context.date_label`, hidden when null) and comment (iOS `ExpertReviewsCard`, `ExpertReviewsOverallCard`).
  - Loads **page 1 only** (iOS calls `getExpertReviews(id:)` with defaults). No paging.
  - States: skeleton on first load (iOS shows 1 overall card and 3 review placeholders). Inline `ErrorState` with Retry. Pull-to-refresh with the "Couldn't refresh" snackbar when a refresh fails over loaded content. "No reviews yet" shown inline below the overall card when the list is empty.
  - The screen takes `expertId` and `expertName` as its navigation key arguments.

### Claude's Discretion
- **Saved Experts card visuals.** Port iOS `FavoriteExpertCard` faithfully (72×80 rounded-rect photo with a person-icon fallback, bold name, green headline, a filled heart button on the right, wrapping tag pills, 16dp padding, a rounded 16 bordered card), as 16.1 D-05 did for `SearchExpertCard`. Reuse the shared `Avatar` only if it supports that shape cleanly. Press-scale on the card is fine.
- The empty-state illustration (`FavoritesGlowingStar` with a pulse) and the `GreenGlowBlobLayer` background, following the 16.1 `SearchExpertGlowingIllustration` precedent.
- How a failed remove on the Saved list is shown. Leaning toward the D-03 snackbar for consistency, instead of the iOS "Couldn't update favorites" alert.
- Repository shape. A new `FavoritesRepository` (list/add/remove), and whether the full reviews fetch reuses `ExpertProfileRepository`'s existing reviews call or moves to `ReviewsRepository`. DTO and Retrofit naming, and fakes and fixtures.
- Navigation keys and entry registration: `FavoritesKey` and `ExpertReviewsKey` in the Profile tab, and `ExpertReviewsKey` in every stack that can show Expert Profile (Explore, Search, Chats, the client Profile hub via Saved Experts, and the expert hub self-view). Make sure `ExpertProfileKey` is registered in the client Profile tab's stack.
- Whether the profile heart and the Saved list share state (for example a repository-level favorites flow) or rely only on D-09's refresh on return. D-09 is the minimum.
- String resource names and accessibility semantics (Phase 15 patterns).
- Test coverage. JVM tests are expected for: the optimistic toggle (success, server reconcile, rollback on failure, taps ignored during a request), the starting heart state from details, the optimistic remove and rollback to the original index, the refresh on return keeping rows on failure, the `limit=100` request, the reviews title fallback, and the mapping fallbacks.

</decisions>
