## Critical Issues

### CR-01: A booking started from Saved Experts leaves Request Sent parked on the Profile stack

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/home/ClientBookingManagementEntries.kt:35,43` (callers: `ClientBookingFlowEntries.kt:56-57`; new entry path: `FavoritesNavigation.kt:22`, `HomeClientScreen.kt:157-168`)
**Issue:** This phase adds a fourth stack that can host the Profile to Book Session flow: Profile tab, Saved Experts, Expert Profile (`origin = Profile`), Book Session (client shell `showBookSession = true`). When the booking succeeds, `replaceTop(RequestSentKey)` runs on the Profile stack. Then "View My Bookings" calls `showMyBookings()` = `resetAndSelect(ClientBookingsRoot, {Explore, Search, Bookings})`. "Back to home" calls `showExplore()` = `resetAndSelect(ExploreRoot, {Explore, Search})`. Neither set contains `ClientProfileRoot`.

Result: the Profile stack stays `[ProfileRoot, FavoritesKey, ExpertProfile(A, Profile), RequestSent(id)]`. The next time the user taps the Profile tab they land on a finished Request Sent screen with the bottom bar hidden, and need three Backs to reach the hub. This is the same defect the Search tab fix removed (see the KDoc on `showMyBookings`: "a booking started from Search must not leave Request Sent parked there"). The 16.3 RESEARCH A3 accepted "Saved Experts stays on the Profile stack" only for the empty-state buttons. It did not consider that the booking flow can now start on this stack. `HomeShellsTest` cannot catch it, because it only drives stand-ins for favorites and profile.

The same gap already exists for the Chats stack (`StackOrigin.Chats` profile to Book). That is out of scope for 16.3 but is the same class of bug.

**Fix:** Add the Profile root to both reset sets. Doing so also resolves RESEARCH A3 in favor of its listed alternative, so "Explore Experts" and "View My History" drop Saved Experts from the Profile stack, which is arguably the better behavior.
```kotlin
fun Navigator.showMyBookings() =
    resetAndSelect(ClientBookingsRoot, setOf(ExploreRoot, SearchRoot, ClientProfileRoot, ClientBookingsRoot))

fun Navigator.showExplore() =
    resetAndSelect(ExploreRoot, setOf(ExploreRoot, SearchRoot, ClientProfileRoot))
```
If keeping Saved Experts open after the two empty-state switches is intentional, reset the Profile stack only from the booking-flow callbacks (`onViewBookings` and `onBackToHome` in `clientBookingFlowEntries`) and leave `FavoritesRouteActions` on the current behavior. Add a `HomeShellsTest` case: Profile, Saved Experts, profile, Book, Request Sent, View Bookings, then tap the Profile tab and assert the hub is shown.

### WR-02: The favorite heart is shown in Expert mode, where the backend answers 403

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/expertprofile/ExpertProfileScreen.kt:191` and `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/expertmode/home/HomeExpertScreen.kt:319-330`
**Issue:** `showFavorite = !isSelfView && !chatEntry.isSelf(...) && details is Loaded`. The expert shell passes `showBookSession = false` but has no equivalent gate for the heart. The backend routes `GET/PUT/DELETE /client/favorites*` are `roleCheck('client')`, and the phase's own tests use `403 "Client role required"` as the failure fixture. In the expert shell a non-self profile is reachable through Chats, "View profile" (`openChatPeerProfile`). When the details call succeeds, the heart renders, the optimistic flip happens, and the tap ends in a rollback plus an error snackbar for an action the user cannot perform. Reachability is narrow (a peer whose details load), but the screen already models this distinction for Book Session.
**Fix:** Add `showFavorite: Boolean = true` to `ExpertProfileScreen`, AND it into the `showFavorite` expression, and pass `showFavorite = false` from `expertProfileEntry`. That `isSelfView` already hides the heart does not cover the chat-peer case.

### WR-03: Two failed removes can restore rows out of their original order, and the test locks nothing

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/favorites/FavoritesViewModel.kt:122-148`; `app/src/test/java/com/uptrendinvestments/clickmeapp/screens/clientmode/favorites/FavoritesViewModelTest.kt` (`twoRemovalsBothFailingRestoreOrderWithoutDuplicates`)
**Issue:** `index` is the position in the list at the time of the call. From `[A,B,C]`: `remove(A)` gets index 0, `remove(B)` sees `[B,C]` and also gets index 0. If A fails first the list is `[A,C]`, and when B then fails it is inserted at 0, giving `[B,A,C]`. The executor accepted this, but the test name says "restore order" while the assertion is `restored.sorted()`, so it passes for any permutation, including the broken one.
**Fix:** Remember the full ordered id list at remove time and, on rollback, insert the row before the first later id that is currently present (else append):
```kotlin
val order = rows.map { it.expertId }          // captured at remove time
// on rollback:
val after = order.drop(order.indexOf(expertId) + 1).toSet()
val at = current.indexOfFirst { it.expertId in after }.let { if (it < 0) current.size else it }
```
Then make the test assert `listOf("a","b","c")` for both failure orders. If the current behavior is kept deliberately, rename the test so it does not claim order.

Add a test that drives `Lifecycle.Event.ON_PAUSE` then `ON_RESUME` (a `TestLifecycleOwner` with `LocalLifecycleOwner`) and asserts a second `getClientFavorites` call.
