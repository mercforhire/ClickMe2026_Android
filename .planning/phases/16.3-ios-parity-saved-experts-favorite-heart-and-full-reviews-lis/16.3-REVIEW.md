## Summary

**CR-01 is resolved by this diff.** I traced both Request Sent exits.

- `viewBookingsFromRequestSent` and `backToHomeFromRequestSent` check `key in state.backStacks[ClientProfileRoot]`. This is stack membership, not the selected tab, so it is correct even if the tab changed.
- When the key is on the Profile stack, `reselect(ClientProfileRoot)` pops that stack to the hub. That removes Request Sent, the booking form's predecessor and Saved Experts.
- The shared `showMyBookings` / `showExplore` then run. `reselect` sets `lastTransition = Pop`, but `resetAndSelect` always overwrites it with `TabSwitch` or `Pop`. The target tab is never the Profile tab, so it becomes `TabSwitch`. The tests assert this.
- When the key is not on the Profile stack, the helper behaves exactly like the shared function. A Profile stack with Saved Experts open, or an Expert Profile left open, is untouched.
- `RequestSentKey` is a data class, so `in` compares by `bookingId`.
- The shared sets were not changed. "Explore Experts" and "View My History" in Saved Experts keep Saved Experts open (RESEARCH A3, D1.FV4), and `sharedSwitchesLeaveSavedExpertsOnTheProfileStack` plus `savedExpertsExploreButtonKeepsSavedExpertsOpenOnTheProfileTab` lock that in.
- Test coverage matches the claims. The `HomeShellsTest` cases use the real `clientFavoritesEntry` and `clientBookingFlowEntries`. The parameterized Explore / Search / Chats / Bookings flows compare the helper against the shared function, and assert the parked Profile stack is untouched.
- I found no regression, crash path, or ordering problem in the new helpers. No build or test run was done.

Two items remain. Neither blocks the fix.

## Warnings

### WR-05: The Profile fix is a point patch; Request Sent can still be parked on the Chats stack and on the Bookings stack

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/home/ClientBookingFlowEntries.kt:61-94` (shared sets at `ClientBookingManagementEntries.kt:39,51`)
**Issue:** The KDoc admits the gap: "The Chats stack on both exits and the Bookings stack on 'Back to home' still keep their Request Sent". It is real and reachable. `ChatEntries.kt:71` pushes an Expert Profile with `StackOrigin.Chats`, so a booking can end on the Chats stack. After "View My Bookings" or "Back to home", the Chats tab reopens on a finished Request Sent screen with the bottom bar hidden. A booking on the Bookings stack (the test's own fourth flow) has the same effect after "Back to home".

This is pre-existing and not introduced by 16.3-08. But the diff now fixes the identical defect for Profile and Search and leaves the other two. It also adds `parkedProfileStack` tests that treat the remaining behavior as normal. The helper's per-stack special case will need to be edited again for each fix.

**Fix:** Generalize the helper to every stack that holds the key, instead of only the Profile stack. Keep the shared sets unchanged so Saved Experts' own buttons still keep it open.
```kotlin
private fun Navigator.resetStacksHolding(key: RequestSentKey) {
    state.backStacks.forEach { (tab, stack) ->
        if (key in stack) reselect(tab)
    }
}
```
This also covers Explore and Search, where the shared reset already runs, so it is harmless there. Then add Chats and Bookings cases to the parameterized tests. For those two cases the expected result is a reset stack rather than equality with the shared function. If out of scope for 16.3, track it as a follow-up.
