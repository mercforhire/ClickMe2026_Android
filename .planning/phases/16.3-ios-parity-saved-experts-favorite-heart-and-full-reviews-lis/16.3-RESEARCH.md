## User Constraints (from CONTEXT.md)

### Locked Decisions

### Favorite heart (Expert Profile)
- **D-01: The heart's starting state comes from `is_favorite` on `GET /experts/:id/details`**, which the screen already calls. Add `is_favorite` (default false) to the details DTO. Do **not** port iOS's extra `GET /client/favorites?limit=100` scan.
  - This is a deliberate deviation from iOS. The iOS comment ("`/experts/:id/details` doesn't include `is_favorite`") is out of date: the backend now computes it (`publicProfile.controller.js` `getExpertDetails`, best-effort, false on any lookup error and false for self-view).
- **D-02: The heart is a TopAppBar action placed just before the existing ⋮ Report/Block menu** (`ExpertProfileScreen.kt` `ProfileTopBar` `actions`). It is an outlined heart when not favorited and a filled heart when favorited. It is hidden whenever Book/Message would be hidden for self: `isSelfView`, or `chatEntry.isSelf(expertId)` as a backstop. iOS hides it on self-view (`ExpertProfileView.swift` toolbar).
  - Show it only once details have loaded (the starting state is unknown before then). The `showSafetyMenu` gate already works this way.
  - Accessibility: a content description that changes with state ("Save expert" / "Remove from saved"), plus selected/toggleable semantics. Exact strings are at Claude's discretion.
- **D-03: The toggle is optimistic.** Flip the heart, call `PUT` (add) or `DELETE` (remove) on `/client/favorites/:expertId`, then set the heart to the server's `data.is_favorite` (reconciling as iOS `toggleFavorite` does). **On failure: roll back to the previous state and show a snackbar with the server message.** This deviates from iOS, which shows a "Couldn't update favorites" alert.
- **D-04: Taps during a request are ignored**, as in iOS `isFavoriteInFlight`. There is no queue or "latest tap wins".
- **Locked by backend:** adding is **`PUT`**, not `POST` (PARITY-AUDIT says POST, which is wrong; `backend-reference/src/routes/favorites.js`). Both calls are idempotent and limited to clients (`roleCheck('client')`). The path id is a UUID (a malformed one returns 422).

### Saved Experts: empty state
- **D-05: "Explore Experts" switches to the Explore tab root**, the same tab switch the bottom bar does. On iOS this button does nothing (the hub opens `FavoritesView()` without wiring its callbacks). Wiring it here is a deliberate fix.
- **D-06: "View My History" switches to the Bookings tab and selects its Past segment.** On iOS this button also does nothing. Research how to select the Past segment from another tab (for example a navigation argument or a shared selection state on My Bookings).
- **D-07: The Pro Tip text says "heart icon".** The iOS text says "Tap the star icon on any expert's profile to add them to this list instantly.", but the control is a heart. This is a copy deviation.
- **D-08: The Pro Tip card appears only in the empty state**, as on iOS. The order is the glowing illustration, "No favorites yet", the subtitle, the 2 buttons, then the Pro Tip. The populated list shows only the tagline ("Manage your curated list of elite professionals.") and the cards.

### Saved Experts: list behavior
- **D-09: Refresh silently when the screen comes back into view.** Load fully the first time the screen opens. After that, whenever the screen comes back into view (for example, back from an Expert Profile opened from the list), reload in the background and keep the current rows on screen. Unfavoriting from the profile is then reflected when the user returns. iOS loads once and goes stale; this is a deliberate fix.
  - A background refresh that fails keeps the current rows and does **not** show the error view (Phase 15 D-05 spirit). Whether it shows the "Couldn't refresh" snackbar is at Claude's discretion (leaning toward silent for return-triggered refreshes and the snackbar for pull-to-refresh).
- **D-10: Removing asks for confirmation in a Material `AlertDialog` with the iOS copy.** Title "Remove {name} from favorites?", body "You can favorite this expert again anytime from their profile.", a destructive "Remove" and a "Cancel". The trigger is the filled heart on each card. Confirming removes the row optimistically and calls `DELETE /client/favorites/:expertId`. If that fails, the row goes back to its original position, as in iOS `removeFavorite`.
- **D-11: Loading follows the Phase 15 standard.** Skeleton cards on first load. Inline `ErrorState` with Retry and the iOS title "Couldn't load favorites" plus the server message. Pull-to-refresh, with the "Couldn't refresh" snackbar (`RefreshFailedSnackbar`) when a refresh fails over existing rows. This deviates from the iOS centered spinner and the missing pull-to-refresh.
- **D-12: One request with `limit=100`** (`GET /client/favorites?page=1&limit=100`). The backend caps the limit at 100 and defaults to 20 (`utils/pagination.js` `parsePage`). There is no load-more or infinite scroll, and no total-count UI.
- **Carried from iOS:** mapping per `FavoritesViewModel.map`. Name falls back to "Expert", headline to "", tags to [], avatar to none. The bio is always empty because the endpoint has none, so it is not shown. Tapping a card opens Expert Profile for `expert_id`. The TopAppBar title is "Favorite Experts" with a back arrow (iOS `navigationTitle`). The hub row is labeled "Saved Experts".
- **Hub row placement (from iOS `ClientProfileHomeScreen.swift:94-97`):** a new "Discovery" section holding one "Saved Experts" row with a heart icon, placed after the mode-switch card and before "Account".

### Reviews: "See all" and the full list
- **D-13: Always show the Recent Reviews card with its "See all" header, even with 0 reviews**, as on iOS (`ExpertProfileReviewsCard.swift`). This replaces the current Android rule (the caller hides the card when `reviews` is empty, `ExpertProfileReviewsCard.kt:28-29` KDoc). With 0 reviews the card shows only the header. "See all" then opens the full screen's "No reviews yet" empty state.
  - While reviews are still loading, keep the existing `ExpertProfileReviewsCardSkeleton`. If the reviews request fails, keep whatever the current error handling does. Claude's discretion, but don't show "See all" over a failed load in a way that reads as "0 reviews".
- **D-14: "See all" shows whenever the card shows**, even with 1–3 reviews (all already visible). This matches iOS.
- **D-15: Self-view keeps the reviews card and "See all"**, as on iOS. The expert sees their own full review list. Only Book, Message and the heart are hidden in self-view.
- **D-16: The full Reviews screen follows the iOS layout and the Phase 15 states.**
  - TopAppBar title: "{FirstName}'s Reviews" (first word of the trimmed name), falling back to "Reviews" when no name is known (iOS `ExpertReviewsViewModel.navigationTitle`). Back arrow.
  - Content: the overall rating card (overall rating to one decimal, stars, total count), then one card per review with the reviewer avatar, the name (falling back to "Anonymous"), stars, topic (`session_context.topic`), date label (`session_context.date_label`, hidden when null) and comment (iOS `ExpertReviewsCard`, `ExpertReviewsOverallCard`).
  - Loads **page 1 only** (iOS calls `getExpertReviews(id:)` with defaults). No paging.
  - States: skeleton on first load (iOS shows 1 overall card and 3 review placeholders). Inline `ErrorState` with Retry. Pull-to-refresh with the "Couldn't refresh" snackbar when a refresh fails over loaded content. "No reviews yet" shown inline below the overall card when the list is empty.
  - The screen takes `expertId` and `expertName` as its navigation key arguments.

## Summary

All three features sit on a backend that is already complete. `GET/PUT/DELETE /client/favorites` and the `is_favorite` flag on `GET /experts/:id/details` are live, and `GET /experts/:id/reviews` already returns `session_context` per review. Android needs: three Retrofit methods plus DTOs, one DTO field (`is_favorite`) and one DTO addition (`session_context` on `ReviewItemDto`), a `FavoritesRepository`, an `ExpertReviewsViewModel`/screen, a `FavoritesViewModel`/screen, a heart in `ExpertProfileViewModel`/`ExpertProfileScreen`, a "See all" header action on the existing reviews card, a hub row, and navigation keys. No new Gradle dependency is needed.

The three highest-risk items are not in the features themselves but in the seams they touch. (1) **Duplicate Nav3 content keys.** `toDecoratedEntries` flattens the Explore stack with the selected tab's stack, so an `ExpertProfileKey` or `ExpertReviewsKey` for the same expert on Explore and on the Profile tab (Saved Experts) would crash `NavDisplay`. Fix: add `StackOrigin.Profile` and make `ExpertReviewsKey` carry an `origin` that is copied from the profile key it was opened from. (2) **A pile of existing tests encode the old behavior** (reviews card hidden when empty, no "See all", the `ClientProfileHubActions` positional constructor, the `StackOrigin.entries` list, `ExpertProfileViewModel(key, repo)`), and `FakeClickMeApi` stops compiling the whole test source set until it overrides the three new interface methods. (3) **Optimistic remove vs. refresh race.** D-09's silent refresh-on-return can resurrect a row that is mid-removal; the VM must filter in-flight removals out of any refresh result.

D-06 (select Past on My Bookings) needs no new mechanism: `BookingsLaunchRequest` plus `Navigator.showMyBookings()` already do exactly this for the cancel flow. D-05 uses `Navigator.showExplore()`. D-09 copies the `MyBookingsViewModel.onScreenShown` / `onScreenHidden` pattern and its three-effect screen wiring.

**Primary recommendation:** Build in this order: (a) network + DTOs + repositories + `FakeClickMeApi` + `StackOrigin.Profile` + the two keys, with wire tests; (b) ExpertProfile changes (heart, reviews-card header, `onSeeAllReviews`), which all touch `ExpertProfileScreen.kt` and so belong in one plan; (c) Favorites screen/VM; (d) Reviews screen/VM; (e) one final wiring plan for `HomeClientScreen.kt`, `HomeExpertScreen.kt`, hub actions and `HomeShellsTest`, because those files are touched by every other plan.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Favorite state of record (add / remove / list) | API / Backend (`discovery_interactions` rows) | — | Server is authoritative; the client only mirrors it and reconciles to `data.is_favorite` |
| Initial heart state | API / Backend (`is_favorite` on details) | Client VM | D-01: no list scan; the flag arrives with the details response the screen already makes |
| Optimistic toggle + rollback | Client ViewModel | — | Pure UI state machine over two idempotent calls |
| Saved list ordering | API / Backend (newest favorited first) | Client (keeps order, re-inserts on rollback) | Client never sorts |
| Pagination cap | API / Backend (`limit` clamped to 100) | Client sends `limit=100` | D-12 |
| Reviews data (summary, per-review, `session_context`) | API / Backend | Client DTO | Client adds the missing `session_context` fields |
| Past-segment selection on My Bookings | Client (`BookingsLaunchRequest` singleton) | Navigator | Existing one-shot hand-off |
| Tab switching | Client Navigator | — | `showExplore()`, `showMyBookings()` |
| Self-view / role gating | API (`roleCheck('client')`, 403) | Client hides the heart for self | Server rejects; client avoids showing a control that cannot work |

### Pattern 1: Heart in `ExpertProfileViewModel` (D-01..D-04)

**What:** Add `isFavorite: Boolean = false` and a private in-flight guard to the VM; `mergeDetails` seeds `isFavorite` from `data.isFavorite`; `onToggleFavorite()` flips, calls PUT/DELETE, reconciles, rolls back.
**Key rules**
- Guard first: ignore the tap if a request is in flight, or if details are not `Loaded` (heart is not rendered then, but keep the VM safe).
- `previous = state.isFavorite`; set `isFavorite = !previous` immediately; choose `remove` when `previous` is true, else `add`.
- On success set `isFavorite = response.isFavorite` (server wins, as iOS does).
- On `ApiException`: `isFavorite = previous`, set a one-shot `favoriteError: FieldError` = `e.userMessage?.let(FieldError::Text) ?: FieldError.Res(R.string.favorites_update_failed)` (UI-SPEC: server message, fallback "Couldn't update favorites"). Always clear the in-flight flag in `finally`.
- `mergeDetails` must not overwrite `isFavorite` while a toggle is in flight (cheap guard; a Retry cannot actually overlap because the heart is hidden when details are `Error`).
- Inject `FavoritesRepository` as a second constructor dependency. The class is `@AssistedInject`, so Hilt needs no module change.

```kotlin
// Shape only. Source: ExpertProfileViewModel.kt (read this session) + iOS ExpertProfileViewModel.toggleFavorite
fun onToggleFavorite() {
    val current = _uiState.value
    if (favoriteInFlight || current.details !is DetailsState.Loaded) return
    val previous = current.isFavorite
    favoriteInFlight = true
    _uiState.update { it.copy(isFavorite = !previous) }
    viewModelScope.launch {
        try {
            val result = if (previous) favorites.remove(current.expertId) else favorites.add(current.expertId)
            _uiState.update { it.copy(isFavorite = result.isFavorite) }
        } catch (e: ApiException) {
            _uiState.update { it.copy(isFavorite = previous, favoriteError = e.toFavoriteFailure()) }
        } finally {
            favoriteInFlight = false
        }
    }
}
```

### Navigation keys and the duplicate-content-key hazard
- `FavoritesKey`: `@Serializable data object FavoritesKey : NavKey` (precedent: `HelpKey`, "Registered once in each shell"). Register only in the client shell, `BottomBar.hidden()` like every other hub destination (`clientSettingsEntries`).

### Anti-Patterns to Avoid
- **A repository-level favorites cache or StateFlow.** D-09 refresh-on-return is the locked minimum. A singleton cache has to be cleared on logout (the repositories here are deliberately stateless; `ReviewsRepository` documents "Stateless: nothing here is cleared on logout").
- **Using `POST` for add.** PARITY-AUDIT says POST; the backend is `PUT`.
- **Scanning `GET /client/favorites` from the profile.** D-01 forbids it.
- **Widening `ReviewRowUi`** with topic/date/avatar. Use a dedicated model.
- **Keying the favorites `LazyColumn` by anything but `expertId`**, or using index keys: `animateItem()` and removal animations need stable ids. (Unlike Search, where the tag-union RPC can repeat ids, `list_favorite_experts` joins on `discovery_interactions` which has a partial UNIQUE index on `(user_id, expert_id)` for favorites [CITED: favorites.controller.js header comment], so ids are unique.)
- **`FontWeight.Bold`.** UI-SPEC says use the 600 styles. (The 16.1 Search card uses it; do not copy that line.)
- **Hex literals, raw `fontSize`, or a `Scaffold` whose content padding is unused.** `scripts/check-design-rules.sh` fails the build on these.

## Common Pitfalls

### Pitfall 1: Duplicate Nav3 content key crashes `NavDisplay`
**What goes wrong:** `NavigationState.toDecoratedEntries` flattens `stacksInUse = [startRoute, topLevelRoute]`. With the Profile tab selected, the Explore stack and the Profile stack are both rendered; equal keys give duplicate content keys and a crash. Reachable by: open expert X on Explore (bottom bar visible), switch to Profile, Saved Experts, open X. Also for the reviews screen: Explore X -> See all, then Search X -> See all.
**Why it happens:** [VERIFIED: StackOrigin.kt KDoc, read this session] "It only keeps keys distinct across stacks, because `NavigationState.toDecoratedEntries` flattens the start stack with the selected one and two equal keys would produce duplicate content keys".
**How to avoid:** append `StackOrigin.Profile`; Saved Experts builds profile keys with it; `ExpertReviewsKey.origin` is copied from the `ExpertProfileKey.origin` it was opened from (so Explore/Default, Search, Chats, Profile all stay distinct). Add a navigator/shell test that pushes X on Explore then X with `origin = Profile` on the Profile tab and asserts no crash and both entries composed.
**Warning signs:** `IllegalArgumentException` about a duplicate key when switching tabs.
**Residual exposure (document, do not fix):** `BookingKey`/`RequestSentKey` carry no origin. The new Profile-origin profile can start the Book flow too. The bottom bar is hidden on those routes, so a UI tab switch cannot happen mid-flow; only programmatic tab changes (push-notification routing) could collide, as already documented in `StackOrigin.kt`.

### Pitfall 2: `FakeClickMeApi` stops the whole unit-test source set compiling
**What goes wrong:** `class FakeClickMeApi : ClickMeApi {` implements every interface method. Adding `getClientFavorites`/`addFavorite`/`removeFavorite` to `ClickMeApi` without overriding them in the fake is a compile error for every test in the module.
**How to avoid:** in the same plan (and commit) as the Retrofit methods add `getClientFavoritesHandler`, `addFavoriteHandler`, `removeFavoriteHandler` (default `{ notStubbed() }`), call counters, and recorded lists (queries as `(page, limit)`, ids), following the `searchExpertsHandler` / `_searchExpertsQueries` pattern.
**Warning signs:** `Class 'FakeClickMeApi' is not abstract and does not implement abstract member` at `compileDevDebugUnitTestKotlin`.

### Pitfall 4: Optimistic remove vs. silent refresh race
**What goes wrong:** the user confirms Remove; the row disappears; a return-triggered `Quiet` refresh that was already in flight (or one triggered while `DELETE` is pending) lands with the server still listing the favorite and the row reappears, then possibly disappears again.
**How to avoid:** keep a `removing: Set<String>` in the VM; filter every refresh result with it; on failure reinsert and clear. Test: start a `Quiet` refresh with a deferred, remove a row, complete the refresh with the old list, assert the row is still gone; fail the DELETE and assert it returns at the original index.
**Also:** two quick removals: reinsert with `index.coerceAtMost(size)` and skip if the id is already present.

### Pitfall 5: Heart state clobbered by a details reload
**What goes wrong:** `load()` (Retry) re-sets `details` and `mergeDetails` rewrites `isFavorite` from the server while a toggle is mid-flight.
**How to avoid:** do not apply `isFavorite` from details while `favoriteInFlight`. In practice the heart is hidden whenever details are not `Loaded`, so this is a small guard, but it makes the VM safe in tests that call `retry()` during a toggle.

### Pitfall 6: A cancelled pull leaves the spinner on
**What goes wrong:** a `Loud` load that cancels an in-flight `Pull` never clears `isRefreshing` or `refreshFailed`.
**How to avoid:** `startLoad` clears both flags before launching (16.1 Pitfall 4; `SearchExpertViewModel.runSearch` does `it.copy(isRefreshing = mode == Refresh, refreshFailed = false)`).

### Pitfall 7: Retrofit `PUT` with no body
**What goes wrong:** assuming `@PUT` without `@Body` fails or sends a `Content-Type` that the Express JSON parser rejects.
**How to avoid:** declare it like `joinCall` (no `@Body`) and add a MockWebServer test asserting `request.method == "PUT"`, `request.url.encodedPath == "/api/v1/client/favorites/<id>"` and an empty body. The backend route has no body validation (`router.put('/client/favorites/:expertId', roleCheck('client'), addFavorite)`), and global `express.json()` is the only parser [VERIFIED: backend src/app.js:179].

### Pitfall 8: Review comment clamp and TalkBack
**What goes wrong:** the card clamps the comment to 2 lines (iOS parity, user-confirmed in UI-SPEC E7) but the merged TalkBack node reads only the visible text.
**How to avoid:** build the merged description from the full untruncated comment, as UI-SPEC specifies. Render server text with plain `Text` only.

### Pitfall 9: Photo shape does not fit `Avatar`
**What goes wrong:** `Avatar` clips to `CircleShape`; the Saved Experts photo is a 72x80 rounded rect.
**How to avoid:** write `FavoriteExpertPhoto` with the same Coil `AsyncImage(ImageRequest.Builder(...).data(url).crossfade(200))` approach, `clip(shapes.extraSmall)`, `ContentScale.Crop`, and a fallback fill `ClickMePalette.avatarFallback` with `Icons.Filled.Person` shown under the image (so it is visible while loading, on error, and with no URL). Test tags like `AVATAR_FALLBACK_TAG` live on `Avatar`; add equivalents.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (no new auth) | Bearer attached by `AuthHeaderInterceptor` to every non-public path; `/client/favorites*` is not in `publicPaths` (assert in `ApiRequestUrlsTest`) |
| V3 Session Management | no | — |
| V4 Access Control | yes (server-enforced) | `roleCheck('client')` returns 403 for non-clients; the client hides the heart for self-view and does not rely on the UI for authorization |
| V5 Input Validation | yes | Expert ids come from server payloads and nav keys and are sent as Retrofit `@Path` (encoded); the server validates the UUID (422). Render all server text (names, headlines, tags, reviewer names, topics, comments) as plain `Text` only |
| V6 Cryptography | no | — |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IDOR on `/client/favorites/:expertId` | Tampering | `user_id` always comes from the JWT on the server; the client sends only the expert id |
| Logging review comments or names | Information disclosure | Never log comment text; the repo's `ApiException.Http` message carries status and code only (T-02-08). `ReviewPrefillDto.toString()` shows the precedent of redacting user text |
| Persisting server text to `SavedStateHandle` | Information disclosure | The dialog target is stored as an id only; list data is reloaded after process death |
| Spoofed/duplicated navigation entries | Denial of service | `StackOrigin.Profile` and propagated `origin` prevent duplicate-key crashes |
| Rapid repeated taps on the heart | Denial of service / data races | D-04 in-flight guard; idempotent endpoints |
