# Phase 16.1: Code Review Report

**Reviewed:** 2026-10-30

## Summary

I reviewed the Search tab (ViewModel, repository, screen, subviews), the shared-file edits (Avatar `fallbackColor`, `StackOrigin.Search`, `ClickMeApi.searchExperts`, Explore "See all", the shell `searchRoot` slot and the `showMyBookings`/`showExplore` Search-stack reset), and the string resources. I checked them against the iOS `SearchExpertViewModel`, `SearchExpertView` and `SearchExpertCard`, and against the backend `/experts/search` schema and controller.

I found no critical defects:
- The ViewModel's latest-wins cancellation holds. `apiCall` rethrows `CancellationException` and wraps every other `Throwable` in `ApiException`, so the single `catch (e: ApiException)` is sufficient.
- The request contract matches the backend's strict Zod schema (`q`, `category`, `sort`, `page`, `limit`).
- `expertise_tags` is a list of label strings, as the DTO expects.
- Behaviour matches iOS except where the code documents a deliberate deviation.

There are two warnings, both about scroll position and stale UI. The remaining items are minor.

## Warnings

### WR-01: Hoisted `LazyListState` keeps the old scroll position across new searches

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/SearchExpertScreen.kt:141` (used at `:195`)
**Issue:** `listState` is hoisted above the `when` so that it survives tab switches (D-03). The same state object is also reused when the results go Loaded (list A) -> Loading -> Loaded (list B). `SearchResultsList` leaves composition during Loading, but `LazyListState` keeps its first-visible index and offset. A user who scrolls down 10 cards and then picks the "Highest rated" sort, taps a different chip, or edits the query will see the new result set open partway down the list instead of at the top. iOS recreates the `ScrollView` content on each state change, so it starts at the top. The pull-to-refresh path (rows kept, same positions) is the only case where keeping the position is right.
**Fix:** Reset the list to the top when a Fresh search lands, and leave tab switches alone. For example, add a `searchRevision: Int` to `SearchExpertUiState`, increment it in `runSearch` when `mode == Fresh`, and in the screen add:
```kotlin
LaunchedEffect(state.searchRevision) { listState.scrollToItem(0) }
```
Alternatively, key the list on the request (`key(state.searchRevision) { SearchResultsList(...) }`) so it gets a fresh `LazyListState`. Because the state is saveable, check that this does not break tab-switch restore.

### WR-02: A "Couldn't refresh" snackbar outlives the search that superseded it

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/SearchExpertViewModel.kt:129-134`, `SearchExpertScreen.kt:134-139`
**Issue:** `runSearch` clears the `refreshFailed` flag, but the snackbar is shown on a separate scope (`RefreshFailedSnackbarEffect`) and `onShown` consumes the flag straight away. A new search therefore does not dismiss a snackbar that is already visible. After a failed refresh the Long-duration snackbar stays up for about 10 s, even if the user types, changes the chip or sort, and the new results load successfully. Its Retry action then calls `onRefresh`, which re-runs whatever the current query is. The KDoc claim that a new search "never leaves ... a stale snackbar request behind" is only true of the flag, not the visible snackbar.
**Fix:** Dismiss the current snackbar when a new search starts or results arrive. For example, in `SearchExpertContent`:
```kotlin
LaunchedEffect(state.results, state.query, state.selectedCategorySlug, state.sort) {
    snackbarHostState.currentSnackbarData?.dismiss()
}
```
Alternatively, accept the behaviour and correct the KDoc.

## Info

### IN-01: `contentDescription` on the text field may hide the typed text from TalkBack

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/subviews/SearchExpertSearchBar.kt:63-66`
**Issue:** While `query` is non-empty, the field gets `contentDescription = placeholderText`. On editable nodes, a content description can replace the node text in TalkBack output, so the user may hear "Search for experts" instead of what they typed. The inline comment says the intent is "never the value", but this is the usual way to end up with a field whose value cannot be read back. I could not verify this on a device.
**Fix:** Prefer a semantics label that augments instead of replaces, such as `Modifier.semantics { hintText = placeholderText }` or an `OutlinedTextField(label = ...)` / `placeholder` that stays in the semantics tree. If keeping `contentDescription`, check it with TalkBack on the Samsung test device.

### IN-02: `ALL_CHIP_KEY` comment is wrong, and the key and test tag can collide with a category whose id is "all"

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/subviews/SearchExpertCategoryChips.kt:30, 56, 75-76`
**Issue:** The comment says "a category slug is never empty, so it cannot collide with one". The key actually used is the literal `"all"`, not the empty string, so it would collide with a category whose id is `"all"` (the `LazyRow` would then crash on a duplicate key). `searchChipTag("")` and `searchChipTag("all")` also map to the same tag. This is very unlikely with the current category data, but the comment gives false reassurance.
**Fix:** Use a key that cannot be a category id, for example a sealed or prefixed key such as `"__all__"` and `"cat_${it.slug}"`, and fix the comment.

### IN-03: `SearchExpertUi.bio` and the card's bio branch are dead code

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/SearchExpertUiState.kt:21`, `subviews/SearchExpertCard.kt:81, 151-159`
**Issue:** `bio` always defaults to `""` because search rows carry none (D-05), so `bio` and the `if (bio != null)` rendering block (including `BIO_ALPHA` and `BIO_MAX_LINES`) never run. `ExpertSearchResultItem.totalReviews` is likewise parsed and never read. This mirrors iOS, but it is unreachable code with no test hook.
**Fix:** Either keep it intentionally (and note it in the KDoc as parity scaffolding) or remove `bio`, the bio branch and its constants until a backend field exists.

### IN-04: `toSearchMessage` has a redundant cast, and the Search ViewModel depends on a login-package type

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/screens/clientmode/search/SearchExpertViewModel.kt:8, 162-163`
**Issue:** `ApiException.userMessage` is already declared `open` on the base class (returns null by default), so `(this as? ApiException.Http)?.userMessage` is equivalent to `userMessage` and the cast is noise. Separately, `FieldError` lives in `screens.login`, so a client-mode Search screen now imports from the login feature package. That is a cross-feature coupling that other screens may already share, so it is not a regression.
**Fix:** `private fun ApiException.toSearchMessage() = userMessage?.let(FieldError::Text) ?: FieldError.Res(R.string.error_state_body)`. Consider moving `FieldError` to a shared package.

### IN-05: The "one bad row cannot fail the list" claim does not hold, and Search/Explore stacks can still share un-keyed booking-flow routes

**File:** `app/src/main/java/com/uptrendinvestments/clickmeapp/model/responses/ExpertsSearchPayload.kt:6-9, 16-22`; `navigation/StackOrigin.kt`
**Issue (a):** The KDoc says every field except `expertId` is nullable "so one bad row cannot fail the list". A row with a missing or null `expert_id` still throws a `JsonDataException` and fails the whole response, so the user sees the inline error. The RPC returns the id as a non-null PK `uuid`, so this is unreachable today. The comment overstates the guarantee.
**Issue (b):** `StackOrigin.Search` keeps `ExpertProfileKey` distinct per stack, but `BookingKey`, `RequestSentKey` and `PaymentMethodsKey` carry no origin. Those routes hide the bottom bar, so a user cannot switch tabs while one is on a stack. A programmatic tab change (push-notification routing via `navigateInTab`) while mid-booking on Explore, followed by the same expert's booking on Search, could put equal keys on both stacks and produce duplicate content keys in `toDecoratedEntries`. The risk existed before this phase, but the Search tab adds a second stack that can host the same Profile -> Book flow.
**Fix:** (a) Soften the KDoc, or make `expertId` tolerant and filter null-id rows in the repository. (b) Optionally thread `origin` through `BookingKey`, or note the residual exposure in the Pitfall 2 comment.
