# Phase 16.1: iOS parity: Search tab and Explore See all Verification Report

**Phase Goal:** The client Search tab matches iOS SearchExpertView: debounced text search, category chips, sort row, result cards, empty and error states, via `/experts/search`; Explore's "See all" on Featured Experts and Featured Topics switches to the Search tab as on iOS.
**Verified:** 2026-10-30
**Status:** human_needed
**Re-verification:** No, initial verification

## Goal Achievement

The goal is achieved in the code. The Search tab is no longer a placeholder. It renders `SearchExpertScreen` through a Hilt entry, backed by `SearchExpertViewModel` and `SearchRepository`, which call `GET experts/search`. Both Explore headers carry "See all" and select the Search tab. I read the sources and ran the relevant test classes myself (225 tests, 0 failures, 0 errors, 0 skipped). Nothing found falsifies a must-have. The status is `human_needed` because device checks were deferred and two review warnings are still open.

Note on the roadmap wording: the goal says "Featured Experts". The Android and iOS section is titled "Recommended Experts" (the CONTEXT and plans use that name). It is the same section.

### Gaps Summary

No gaps block the phase goal. Every roadmap clause and every plan must-have is implemented, wired and covered by a passing test I ran. The phase is `human_needed` rather than `passed` because (a) the device and live-backend checks are deferred by project policy and listed above, and (b) two code-review warnings remain open.

The two warnings are real behavior, confirmed by reading the code, and both are small and cheap to fix:
- **WR-01 (scroll offset):** `listState` is created once in `SearchExpertContent` and survives Loaded -> Loading -> Loaded. Fix by scrolling to item 0 when a Fresh search lands (for example a `searchRevision` counter in `SearchExpertUiState` plus `LaunchedEffect(searchRevision) { listState.scrollToItem(0) }`). Keep the position across tab switches (D-03).
- **WR-02 (stale snackbar):** dismiss `snackbarHostState.currentSnackbarData` when `results`, `query`, `selectedCategorySlug` or `sort` change, or correct the ViewModel KDoc claim.

Neither contradicts a locked decision. D-03 only requires the scroll position to survive tab switches, and D-09 only requires the snackbar with Retry after a failed refresh. If they are not fixed in this phase, set their disposition to accepted with a reason, or carry them to a follow-up.
