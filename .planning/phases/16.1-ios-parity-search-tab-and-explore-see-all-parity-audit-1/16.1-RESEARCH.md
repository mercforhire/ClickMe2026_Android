## User Constraints (from CONTEXT.md)

### Locked Decisions

**See all → Search handoff**
- **D-01: "See all" only switches to the Search tab, as on iOS.** It passes nothing: Explore's active category filter is **not** carried into Search, and Search is not reset. Search shows whatever state it already had. On the first visit that is the fresh state: empty query, "All" chip, "Most popular". Both Explore headers (Recommended Experts and Featured Topics) use the same action. Remove the "See all waits for Search" comment in `ExploreFeaturedTopicsSection.kt`.
- **D-02: Search state (query, selected category slug, sort, results) lives as long as the tab's ViewModel, as on iOS.** It survives tab switches and config changes (the ViewModel is retained). It is **not** written to `SavedStateHandle`, so after process death the tab comes back fresh and reloads. This is a deliberate, user-chosen exception to the Phase 15 POL-02 restore standard for this screen.
- **D-03: Re-tapping the Search tab uses only the existing `Navigator.reselect` rule.** It pops the Search stack to its root (for example from an Expert Profile opened from results). Query, results and scroll position stay. There is no extra scroll-to-top or clear behavior.

**Results paging**
- **D-04: Load only the first page, as on iOS.** One request with `page=1&limit=20` per search. No infinite scroll, no "load more", and no total-count UI. The response's `total_count` / pagination fields can be ignored.

**Result card and screen chrome**
- **D-05: Port the iOS `SearchExpertCard` as a new Android composable.** Do not reuse Explore's `ExpertCard`. The card has: an 80dp circular avatar with the person-icon fallback on a dark green fill; the name (bold), with a star icon and a one-decimal rating aligned to the right; the headline; the bio (only when non-empty; search rows have none, so it is normally hidden); up to 3 tag pills; a 16dp padded, rounded (16), bordered card with press-scale. Tapping the card opens Expert Profile for `expert_id`. Mapping, as in iOS `map()`: name falls back to "Expert", headline to "", rating to 0, tags to [].
- **D-06: Faithful iOS chrome.** No `TopAppBar`: the search field sits at the top of the screen with 20dp top spacing. Below it come the chip row and then the sort row. `GreenGlowBlobLayer` is drawn behind the content. The empty state ("No Experts Found" / "Try adjusting your search or picking a different category.") uses a ported glowing illustration (`SearchExpertGlowingIllustration`, with a pulse) shown **inline in the results area**, so the search field and chips stay visible. It has no action buttons.

**Loading and error behavior**
- **D-07: Every new search (debounced text change, chip tap, sort change, first load) replaces the results area with 3 skeleton cards, as on iOS.** The search field, chip row and sort row stay visible and usable throughout. Use the existing skeleton idiom (`SkeletonBlock` / `SkeletonGroup`, Phase 15 D-08).
- **D-08: A failed new search shows the inline error in the results area**, even if older results were showing. It uses the shared `ErrorState(onRetry)` with the iOS copy: "Couldn't load results", the server message when there is one, and Retry. This counts as a first load for the new query (Phase 15 D-04). Stale results for a different query must never stay on screen under the new query.
- **D-09: A failed pull-to-refresh with the same query, chip and sort keeps the current results and shows the Phase 15 D-05 "Couldn't refresh" snackbar with Retry** (`RefreshFailedSnackbar`). This is a deliberate small departure from iOS, which wipes to the error view. If pull-to-refresh fails when there are no results, D-08 applies.
- **D-10: The latest search wins.** Each new search cancels the previous debounce or in-flight job, as iOS cancels its `searchTask`. A late response for an old query must never overwrite newer state. Text changes are debounced by 300 ms on the trimmed query. Chip and sort taps re-run immediately with the current trimmed query. The first load runs immediately with an empty `q`, which returns the default browse set.
- **D-11: Category chips load on their own and never block results**, as with iOS `loadCategories`. `CategoryStore.fetch()` runs in parallel with the first search. If it fails, the row shows just the "All" chip with no error. A chip sends the category **slug** as `category=<slug>`; "All" sends no `category`. Only one chip can be selected at a time.

## Summary

This phase is a self-contained port. Nothing needs new libraries. The Android codebase already holds every building block: `CategoryStore`, `ErrorState`, `RefreshFailedSnackbarEffect`, `SkeletonBlock`/`SkeletonGroup`, `Avatar`, `ExpertTagChip`, `pressScale`, `GreenGlowBlobLayer`, `PullToRefreshBox`, `SectionHeader(actionLabel, onAction)` and the `ExpertProfileKey` route. The one missing piece on the wire is a single `GET /experts/search` Retrofit method plus a DTO, which is also why the fake in the test tree (`FakeClickMeApi`) must be extended in the same plan or the whole test source set stops compiling.

The backend contract is unambiguous and `.strict()`: only `q`, `category`, `sort`, `page`, `limit` are accepted, and unknown params are rejected with a validation error. iOS sends `q` always (empty string for the browse set), `sort`, `page=1`, `limit=20`, and `category` only when a chip other than "All" is selected. The response is `{status, data: {experts: [...], pagination: {current_page, total_pages, has_more}}}`. The row field names differ from the Explore feed (`full_name`, `headline`, `avatar_url`, `avg_rating`, `total_reviews`, `expertise_tags`), so a new DTO is required; `RecommendedExpertDto` cannot be reused.

Three non-obvious risks decide whether this phase works in the real app. (1) Nav3 flattens the start (Explore) stack with the selected stack, so an `ExpertProfileKey` that is equal to one already on the Explore stack crashes the NavDisplay with duplicate content keys; the repo's existing fix is a `StackOrigin` value, and Search needs its own. (2) The shell must keep a Hilt-free `searchRoot` slot so `HomeShellsTest` keeps compiling and passing. (3) With no `TopAppBar`, edge-to-edge means the search field draws under the status bar unless the screen applies the top inset itself.

**Primary recommendation:** Build it as three plans in the audit's order (network + fake + fixtures; `SearchExpertViewModel` with a single `searchJob` and a `SearchMode` of `Fresh`/`Refresh`; screen + shell slot + Explore "See all"), add `StackOrigin.Search`, and model the ViewModel on `ExploreViewModel` (latest-wins jobs) and the screen on `ConversationsScreen` (`PullToRefreshBox` + scrollable centered states + content-level snackbar host with `imePadding`).

### Pattern 1: Single `searchJob`, latest wins (port of iOS `searchTask`)

**What:** one `Job?` field. Every trigger cancels it and starts a new one. Only the text trigger delays.
**When to use:** all five triggers (text, chip, sort, first load, retry/refresh).

```kotlin
// Source: ExploreViewModel.loadExperts() pattern (screens/clientmode/explore/ExploreViewModel.kt) + iOS SearchExpertViewModel
private var searchJob: Job? = null

fun onQueryChange(text: String) {
    _uiState.update { it.copy(query = text) }          // synchronous: the TextField reads this value
    runSearch(mode = Mode.Fresh, debounce = true)
}
fun onCategoryTap(slug: String) {                       // "" means All
    _uiState.update { it.copy(selectedSlug = slug) }
    runSearch(Mode.Fresh, debounce = false)
}
fun onSortSelected(sort: SearchSort) {
    _uiState.update { it.copy(sort = sort) }
    runSearch(Mode.Fresh, debounce = false)
}

private fun runSearch(mode: Mode, debounce: Boolean) {
    searchJob?.cancel()
    searchJob = viewModelScope.launch {
        if (debounce) delay(SEARCH_DEBOUNCE_MS)         // 300
        val s = _uiState.value
        val q = s.query.trim()
        _uiState.update { it.beginRequest(mode) }       // Fresh ⇒ results = Loading; Refresh ⇒ isRefreshing = true
        try {
            val rows = repository.search(q, s.selectedSlug.ifEmpty { null }, s.sort.apiValue)
            _uiState.update { it.copy(results = Results.Loaded(rows.map(::toUi)), isRefreshing = false) }
        } catch (e: ApiException) {                     // CancellationException is rethrown by apiCall
            _uiState.update { it.failed(mode, e) }
        }
    }
}
```

Why this is enough for "a late response never overwrites newer state" (D-10): `cancel()` makes the old coroutine's suspended `apiCall` throw `CancellationException` (rethrown untouched by `apiCall`, `network/ApiCall.kt`), so its `_uiState.update` never runs. No request-id token is needed as long as there is exactly one job field and nothing launches search work outside it.

State rules the planner must encode:
- `Mode.Fresh` (text, chip, sort, first load, Retry button on the error view): `results = Loading` (skeleton). On failure `results = Failed(message)` (D-08). Clears `isRefreshing`.
- `Mode.Refresh` (pull-to-refresh): applies only when `results is Loaded` with non-empty rows (D-09): keep rows, set `isRefreshing = true`, on failure `isRefreshing = false`, `refreshFailed = true` (one-shot, consumed by `RefreshFailedSnackbarEffect.onShown`). When `results` is `Failed` or `Loaded(empty)` or `Loading`, a pull behaves like `Fresh` (D-09: "If pull-to-refresh fails when there are no results, D-08 applies"). iOS wipes to loading on reload; here the same-query refresh keeps rows.
- A new `Fresh` search that cancels an in-flight refresh must reset `isRefreshing` (the cancelled coroutine never reaches its own reset). `beginRequest(Fresh)` sets `isRefreshing = false`.
- `refreshFailed` must be cleared by a new search so a stale snackbar request is not raised later.
- Retry from the snackbar calls the same `onRefresh`.
- Error message (iOS `message(for:)`): server message when present, else a generic. Android equivalent: `(e as? ApiException.Http)?.userMessage` else `R.string.error_state_body` ("Check your connection and try again."). This mirrors the private `toSectionMessage()` in `ExploreViewModel.kt`; copy the idea, do not depend on the private function.

### Pattern 2: First load and categories (D-10, D-11)

```kotlin
init {                       // iOS: .task { await viewModel.load() } on every appear; Android: once per VM
    loadCategories()         // separate job, never cancels/blocks searchJob
    runSearch(Mode.Fresh, debounce = false)   // q = "" ⇒ default browse set
}
private fun loadCategories() = viewModelScope.launch {
    val list = try { categoryStore.fetch() } catch (_: ApiException) { emptyList() }   // swallow ⇒ only "All"
    _uiState.update { it.copy(categories = list.map { c -> CategoryChipUi(c.id, c.name) }) }
}
```
Keep `loadCategories()` as its own job, not `searchJob`, or a chip tap would cancel the vocabulary load. On pull-to-refresh and the error Retry, call `loadCategories()` again only when `categories.isEmpty()`: `CategoryStore.fetch()` is cache-first (7 days), so this is cheap and repairs a failed first fetch, matching iOS `reload() → load()`.

Note the iOS view calls `load()` in `.task` on every appear, which re-fetches on every tab return. Android's VM is retained (D-02), so `init` loading once plus pull-to-refresh is the equivalent; do **not** reload on every tab return (it would also wipe the retained results, contrary to D-02/D-03).

### Anti-Patterns to Avoid
- **Writing query/chip/sort into `SavedStateHandle`.** D-02 forbids it; `ExploreViewModel` and `ConversationsViewModel` do it, so do not copy that line.
- **Letting two jobs touch `results`.** Categories live in a separate job and field; `searchJob` is the only writer of `results`.
- **Calling `load()` on every composition/appear.** Wipes retained state (D-02/D-03).
- **Sending `q` only when non-empty.** iOS always sends `q` (empty string for browse). Retrofit with a non-null `String` sends `q=`, which the schema accepts (`z.string().optional()`). Keep it for parity. [VERIFIED: ClickMeAPI+Discovery.swift sends `"q": q` unconditionally]
- **Reusing Explore's `ExpertCard` or `RecommendedExpertDto`.** D-05 says no; the field names differ (`profile_image_url`/`rating`/`review_count` vs `avatar_url`/`avg_rating`/`total_reviews`).
- **Adding `min_rate`/`max_rate` params "for completeness".** The schema is `.strict()`; this would make requests fail if ever populated.

## Common Pitfalls

### Pitfall 1: `FakeClickMeApi` stops the whole unit-test source set compiling
**What goes wrong:** `FakeClickMeApi : ClickMeApi` implements every interface method (test tree, 1160 lines). Adding `searchExperts` to `ClickMeApi` without overriding it in the fake is a compile error for all tests, not only the new ones.
**Why:** Kotlin interface with no default. [VERIFIED: `app/src/test/.../testing/FakeClickMeApi.kt:104 class FakeClickMeApi : ClickMeApi {`]
**How to avoid:** In the same plan (wave) as the Retrofit method, add `var searchExpertsHandler: suspend (SearchQuery) -> ExpertsSearchPayload = { notStubbed() }`, a call counter and a recorded list of `(q, category, sort, page, limit)` following the `clientHomeCategories` pattern (`_clientHomeCategories += category`, `ok(handler(...))`).
**Warning signs:** `Class 'FakeClickMeApi' is not abstract and does not implement abstract member` at `compileDevDebugUnitTestKotlin`.

### Pitfall 2: Duplicate Nav3 content key when the same expert is open on Explore and in Search
**What goes wrong:** `toDecoratedEntries` flattens `stacksInUse` = `[startRoute, topLevelRoute]`, i.e. the Explore stack plus the Search stack while Search is selected. If both hold an equal `ExpertProfileKey`, the entries share a content key and the NavDisplay throws. The feature makes this reachable: open expert X on Explore, tap Search (bottom bar is visible on Expert Profile), tap X in the results. Today the seed fields usually differ (Explore seeds `reviewCount` as an `Int`, Search would seed `null`), but a Featured Topic key vs a search key can collide on some data, and the protection must not depend on data.
**Why:** documented in `StackOrigin.kt`: "It only keeps keys distinct across stacks, because `NavigationState.toDecoratedEntries` flattens the start stack with the selected one and two equal keys would produce duplicate content keys". The enum is `enum class StackOrigin { Default, Chats }`. [VERIFIED: navigation/StackOrigin.kt; navigation/NavigationState.kt `stacksInUse` and `toDecoratedEntries`]
**How to avoid:** add `Search` to `StackOrigin` and build the key with `origin = StackOrigin.Search`. The enum is `@Serializable` and the new value is appended, so existing saved stacks still decode. No exhaustive `when` over `StackOrigin` exists in main code (grep of `StackOrigin.` found only constructors/defaults). Add a navigator test: push `ExpertProfileKey(X, origin=Default)` on Explore, switch to Search, push the Search-origin key for X, assert the entries list has no duplicate content keys.
**Same family:** the Book flow pushes `BookingKey` on whichever stack is current. The bottom bar is hidden on `BookingKey`/`RequestSentKey` (`BottomBar.hidden()`), so a tab switch cannot happen while one is open, which is why those keys carry no origin. No action needed beyond confirming Book from a Search-origin profile works.

### Pitfall 3: `SelectableChip` is the wrong chip
See "Alternatives Considered". Selected state draws a close icon; a single-select "All" chip must not. Use `FilterChip` (or a custom pill) with selected semantics. Keep 48 dp touch targets (M3 `FilterChip` applies `minimumInteractiveComponentSize` automatically). The a11y helper `assertActionablesNamed()` and the 48 dp check in `testing/A11yAudit.kt` will flag a small target.

### Pitfall 4: A cancelled refresh leaves the spinner on
`isRefreshing` is set by `beginRequest(Refresh)` and cleared in the same coroutine's completion. If the user types during a pull-refresh, the old coroutine is cancelled and never clears it. `beginRequest(Fresh)` must set `isRefreshing = false` and `refreshFailed = false`. Test it.

### Pitfall 5: Rating 0 and `reviewCount` seeding on the profile hero
`seedRatingOf(key)` returns `NoReviews` only when `reviewCount == 0`, `Shown(rating, count)` only when `rating != null && count != null && count > 0`, else `Pending`. [VERIFIED: ExpertProfileViewModel.kt `seedRatingOf`: `count == 0 -> HeroRating.NoReviews`, `rating != null && count != null && count > 0 -> HeroRating.Shown(rating, count)`, `else -> HeroRating.Pending`]. With D-05's mapping (`reviewCount = null`) the hero stays `Pending` until the reviews call resolves, which is the correct "unknown" behavior; seeding `reviewCount = 0` (iOS `reviewCount: 0`) would flash "No reviews" for an expert who has reviews. The search row does carry `total_reviews`, so seeding it is also valid; CONTEXT D-05 lists the seeded fields as name, headline, avatar, rating and tags, so default to `null` unless the user wants otherwise (Open Question 2).

### Pitfall 6: Text field state through a StateFlow
Update `_uiState` synchronously in `onQueryChange` before launching the job (see Pattern 1). If the field value is updated only after a `delay` or from a different dispatcher, the Compose `TextField` loses keystrokes or the cursor jumps. `ConversationsViewModel.onQueryChange` does the synchronous update. Also trim only for the request (`q = query.trim()`); keep the raw text in the field, as iOS does (`trimmedQuery` is derived).

### Pitfall 7: Per-state test tags and `testTag` on shared components
`SkeletonBlock` always carries the tag `skeleton_block` (internal const `SKELETON_BLOCK_TAG`), so a skeleton-count assertion is `onAllNodesWithTag("skeleton_block")` in `components`'s module. Because the constant is `internal` to the main module and the tests are in the same Gradle module, tests can import it. 3 skeleton *cards* may contain several blocks each, so assert the number of cards by giving each skeleton card its own tag.

### Pitfall 8: Avatar fallback color differs from iOS
iOS fallback fill is `Color(red: 0.12, green: 0.18, blue: 0.14)` (dark green) with a `person.fill` at 15% white. The existing Android `Avatar` fills `surfaceContainerLow` (neutral dark grey, Avatar.kt). D-05 asks for "the person-icon fallback on a dark green fill". Either add an optional `fallbackColor: Color? = null` parameter to `Avatar` (small, backwards compatible, used only here) or accept the shared neutral fallback. Do not fork `Avatar`. The choice is Claude's discretion; the cheap parity option is the optional parameter.

### Pitfall 9: Booking from Search leaves "Request Sent" on the Search stack
`Navigator.showMyBookings()` is `resetAndSelect(ClientBookingsRoot, setOf(ExploreRoot, ClientBookingsRoot))` and `showExplore()` is `resetAndSelect(ExploreRoot, setOf(ExploreRoot))`. [VERIFIED: screens/clientmode/home/ClientBookingManagementEntries.kt:28,31]. iOS mirrors this exactly (`showMyBookings` resets `explorePath` and `bookingsPath`; `returnToHome` resets `explorePath`; neither resets `searchPath`). So after Search → Expert Profile → Book → Request Sent → "View My Bookings", the Search stack still holds `[SearchRoot, ExpertProfile, RequestSent]`. Returning to the Search tab shows Request Sent with the bottom bar hidden (Request Sent uses `BottomBar.hidden()`); Back pops it. This is iOS-parity behavior but is a visible quirk on Android. See Open Question 1; the one-line fix is adding `SearchRoot` to both reset sets (must also update `NavigatorTest`/`BookingFlowNavigationTest` expectations if they assert the sets).

### Pitfall 10: Retrofit `@Query("q")` with an empty string
Retrofit encodes it as `q=` (the key is present with an empty value). The backend treats `''` like no search (`search_text IS NULL OR search_text = ''` in the RPC, quoted line 122 of the migration). [VERIFIED: migration line 122 `search_text IS NULL OR search_text = ''`]. A wire test should assert `request.url.queryParameter("q") == ""` and `querySize == 4` when no category is sent (q, sort, page, limit) and `5` with one.

## Open Questions

1. **Should "View My Bookings" / "Explore Experts" also reset the Search stack?**
   - What we know: iOS does not reset `searchPath`; Android mirrors iOS (D-13 of Phase 7/8) so a booking started from Search leaves Request Sent parked on the Search stack with the bottom bar hidden.
   - What's unclear: whether the user wants the iOS-faithful quirk or a one-line improvement.
   - Recommendation: add `SearchRoot` to the reset sets of `showMyBookings` and `showExplore` and update the affected navigator tests. It only matters when the booking was started from Search. Needs a one-line user confirmation because CONTEXT demands strict iOS behavior parity. If not confirmed, leave it and log it as a known iOS-parity quirk.

2. **Seed `reviewCount` from `total_reviews`?**
   - What we know: the row has `total_reviews`; D-05 lists only name, headline, avatar, rating, tags.
   - Recommendation: `null` (follows D-05, hero shows unknown until loaded). Switching to `totalReviews` is a one-line change if the user prefers an immediate review count.

3. **Trim-equal re-search.** iOS re-runs a search after every text change, including a trailing space (same trimmed query), which flashes the skeleton. Strict parity says keep it. Optional improvement: skip when the trimmed query equals the last requested one and the last result was not a failure. Not recommended without user sign-off (D-10 says each new search cancels and re-runs).

4. **Avatar fallback color** (Pitfall 8): optional `fallbackColor` on `Avatar`, or accept the neutral fill.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Query string injection / parameter smuggling via `q` or `category` | Tampering | Retrofit `@Query` encodes values; send the slug from `CategoryItem.id` only, never free text, in `category`; backend validates and splits |
| Mass-assignment style extra params rejected by server (`.strict()`) | Tampering | Do not add undeclared query params (`min_rate`, `max_rate`) |
| Logging search text (PII-ish user input) | Information disclosure | Do not log the query; the repo's `ApiException.Http` message already carries status and code only, never body text (T-02-08) |
| Persisting the query to `SavedStateHandle`/disk | Information disclosure | D-02 keeps it in memory only (a side benefit) |
| Request flood from per-keystroke search | Denial of service | 300 ms debounce + cancellation of the previous request (D-10) |
