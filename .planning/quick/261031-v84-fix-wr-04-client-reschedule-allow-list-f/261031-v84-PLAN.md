<objective>
Close review finding WR-04 (16.2-REVIEW.md) and the Phase 16.1 design-rule failure.

1. WR-04: the client's Reschedule entry is currently gated by a one-status deny-list, so it shows on cancelled, declined, missed, expired and unknown statuses. This is reachable: `UpcomingBookingViewModel` reloads on every `RealtimeEvent.BookingUpdate`, so an expert cancel while the client has the details open leaves Reschedule as the only action on a dead booking. Replace it with an allow-list that mirrors the server's `canReschedule` minus `pending_reschedule`, keeping the amended D-04 (2026-11-01) exactly: shown on confirmed and pending_approval with no time rule, hidden on pending_reschedule.
2. `scripts/check-design-rules.sh` fails on the hex color literal for the avatar fallback disc in `SearchExpertCard.kt:62` and `AvatarTest.kt:125`. Move it into `ui/theme/Color.kt` as a named token.

Decision on in_progress and completed (made from evidence at planning time; record it in the SUMMARY):
- Both statuses render on the Android client's upcoming surfaces. The server's Upcoming bucket is `UPCOMING_STATUSES = ['pending_approval', 'confirmed', 'pending_reschedule', 'in_progress']` (backend `src/controllers/clientBooking.controller.js:130`). `BookingBuckets.kt` `isRejoinableCompleted` moves `completed` rows whose `endTime` is after now into Upcoming (iOS `isRejoinableCompleted`). Upcoming Booking Details opens from those rows and from pushes (`PUSH_UPCOMING_STATUSES` includes in_progress), and a realtime reload can turn an open in_progress booking into completed.
- iOS shows Reschedule unconditionally on every Upcoming card (`UpcomingBookingCard.swift` `secondaryActions`, lines 270-274) and on `UpcomingBookingSecondaryActions`, so iOS offers it on in_progress and rejoinable completed rows.
- The server (`src/utils/reschedule.js` `canReschedule`) allows `NO_TIME_GATE_STATUSES` (confirmed, pending_approval, pending_reschedule) at any time and `TIME_GATED_STATUSES` (completed, in_progress) only while `now < end_time`. Everything else is refused.
- So in_progress and completed stay in the allow-list (iOS parity, and the server accepts them), but only while now is before the session's end. That end bound is the server's own refusal condition, closes the review's "completed after end" hole, and never touches confirmed or pending_approval, so the amended D-04 still holds. The rule takes `end` and `now` again. This is a different input from the start-minus-24 h rule that 16.2-13 removed. The KDoc must say so, so nobody reads it as that rule coming back.
- Terminal set from the backend `bookings.status` CHECK constraint (`supabase/migrations/20260605030000_create_bookings.sql`): cancelled, declined, missed, expired. There is no `no_show` booking status. `missed` is the server's no-show status, and `no_show_both` (a call end reason) is tested as an unknown string.

Purpose: Reschedule is never offered on a booking the server will certainly refuse, and the design gate is green again.
Output: allow-list rule plus tests, three Upcoming Booking Details screen tests, the WR-04 disposition row set to fixed, and the `ClickMePalette.avatarFallback` token.
